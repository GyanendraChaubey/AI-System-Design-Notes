    AI Logging & Observability Platform — System Design Case Study¶

    Consider a request that a traditional observability stack scores perfectly: HTTP 200, 300ms latency, correct token count, zero exceptions in the trace. In a microservice, that's the whole story — a system with a 0% error rate and stable latency is healthy by definition, because a function call has exactly two outcomes and every metric traditional observability collects is built to distinguish between them. Now put an LLM behind that same request. It can clear every one of those checks — 200 OK, 300ms, correct token count — and still return a confidently wrong answer, cite a document that doesn't exist, drift off-topic, or silently regress in tone from what shipped last week. Error rate and latency don't just under-describe that failure; they are structurally blind to it, because nothing about "did the process complete without throwing" encodes "was the output any good." That gap is why this chapter exists as its own category rather than a paragraph in a generic APM writeup: quality observability — tracking not whether an LLM system ran, but whether it produced good outputs — has no equivalent in Datadog, Grafana, or Splunk, because none of them were built for a component whose output is graded, not binary.

    This chapter is the meta-system of Case Studies: every other chapter in this section — Multi-Agent Research System's nested sub-agent fan-out, RAG System's retrieval pipeline, LLM Inference System's token-serving substrate, AI Recommendation System's experiment infrastructure, AI Notification System's delivery pipeline — depends on this platform to know whether it is operationally and qualitatively healthy. But it is not a rebrand of a general-purpose APM tool pointed at AI traffic. Everything below follows from three problems no conventional observability platform solves out of the box: (1) the trace shape itself is a DAG of parallel, nested, variable-depth agent and tool calls, not a linear request chain; (2) the content of the request — the prompt and the response — is the primary diagnostic artifact, not something to strip out for size; (3) whether the system is right is a continuous, sampled, judged property that has to be measured deliberately, because nothing about the transport layer will tell you.

    Requirements¶

    Functional

    • Ingest traces from every AI system component — LLM calls, tool executions, retrievals, agent loops — via an SDK that auto-instruments the calling application rather than requiring manual span creation.
    • Compute and attribute token cost in real time, at ingestion, across five attribution dimensions (user, tenant, product surface, model tier, feature) simultaneously.
    • Detect quality drift using two complementary signals: continuous embedding-distribution shift monitoring and sampled LLM-as-judge scoring, with a bridge from either signal into the offline evaluation suite for root-cause diagnosis.
    • Store prompt and response content with PII detection and redaction applied before any byte is persisted, across a tiered retention scheme that trades debug utility against compliance exposure deliberately rather than by default.
    • Provide trace search, quality dashboards, cost dashboards, and experiment-result views over the same underlying trace store.
    • Execute GDPR/CCPA deletion requests — including the pseudonymization hash key that makes redacted content re-identifiable — within 24 hours, with a verifiable deletion certificate.

    Non-functional

    Requirement Target Why this number
    Trace ingestion throughput 50,000 spans/second at P99 < 100ms ingestion latency Sized to peak load from Scale Estimation; a slower ingest path becomes the thing that needs its own observability platform to debug
    Trace detail query latency P95 < 500ms An on-call engineer mid-incident cannot wait multiple seconds per trace while triaging; the API's internal target is under 200ms, with the 500ms SLO absorbing tail latency on cold content-store lookups
    Cost metering accuracy Within 1% of the provider's actual invoiced amount This number is what finance and engineering both build budgets against; a metering pipeline that drifts from the real bill is worse than no metering, because it's trusted and wrong
    PII detection false-negative rate < 0.1% Missing PII in 1 span out of 1,000 is not a rounding error at 30M spans/day — it's roughly 30,000 unredacted PII exposures/day if the true rate sits at the ceiling
    Quality sampling coverage > 99% of sampled traces receive a quality_score within 5 minutes of the original request A drift alert is only as fast as the judge pipeline behind it; a slow or backlogged judge queue turns a same-day quality regression into a next-week discovery
    GDPR deletion turnaround Hot and warm tier purge complete within 24 hours; deletion certificate issued after verification Sized to leave room inside the regulatory 30-day response window even after accounting for verification and certificate generation

    Explicitly out of scope: application performance monitoring for non-AI services — a payments API's latency and error rate are covered by whatever general-purpose APM tool (Datadog, New Relic) the organization already runs, and duplicating that here would be redundant infrastructure, not a differentiated capability; user analytics and business metrics (funnel conversion, session length, revenue) — a separate product-analytics platform, distinct from this chapter's quality and cost metrics even where they correlate; model training pipeline observability — a separate MLOps concern covered in LLMOps and Continual Learning & Model Freshness, since training-time metrics (loss curves, gradient norms) answer a different question than "is the deployed system healthy right now."

    Capacity Planning¶

    Sized for a platform serving 10M LLM API calls/day across all client products — comparable in order of magnitude to the combined traffic of several chapters in this section.

    Step Assumption Result
    LLM API calls/day Platform-wide baseline 10M calls/day
    Spans per call Average across simple chat (1 LLMSpan) and agentic calls (LLMSpan + ToolSpan + RetrievalSpan, sometimes several) ~3 spans/call → 30M spans/day
    Span metadata size Timing, token counts, IDs — no content ~500 bytes/span → 30M × 500B = 15GB/day into ClickHouse
    Full-content capture rate Sampled for debug and quality-judge coverage, not every span 5% of spans (1.5M/day)
    Content size per captured span Prompt + response, averaged across short chat turns and long agentic contexts ~8KB/span → 1.5M × 8KB ≈ 12GB/day into the hot content tier
    Hot tier steady-state size 12GB/day × 7-day retention ~84GB resident in Elasticsearch
    Warm tier steady-state size (90-day, metadata + hashed PII, no raw content) Far smaller per-record than hot tier ~15GB/day compressed Parquet → ~1.4TB resident in S3
    LLM-as-judge evaluation volume 1% of spans sampled for continuous per-dimension quality tracking (broader than the statistical minimum — see Concept 3) 30M × 1% = 300K judge calls/day × ~$0.002/call ≈ $600/day
    PII detection compute 30M spans/day × ~5ms/span (regex + NER + context classifier combined) 150,000 CPU-seconds/day ≈ 2 CPU cores running continuously

    The row worth double-checking against intuition: content storage is small, judge evaluation is the larger recurring cost. 84GB of hot-tier content is a rounding error next to any vector index in this book; \(600/day for continuous quality sampling is a real, ongoing line item — and it buys per-tenant, per-feature, per-experiment quality breakdowns, not just one blended number. A team that samples only enough to hit the statistical minimum for one aggregate metric (Concept 3 works out ~800 samples/day, ~\)1.60/day) saves money but loses the ability to answer "is quality specifically bad for tenant X's summarization feature" — which is usually the question that actually gets asked during an incident.

    Scale Estimation¶

    Peak trace ingestion: 50,000 spans/second. Kafka absorbs this comfortably — 50K spans/sec × 500 bytes ≈ 25MB/sec, well inside a 3-broker cluster's sustained throughput. The Flink stream processor parses each span, routes it through PII detection (content-bearing spans only), computes cost_usd, and fans out writes to ClickHouse (metadata, cost) and the tiered content store (Elasticsearch hot, S3 warm).

    PII detection is the compute-bound stage, and its sizing has a real trap in it. Running the full three-stage detector (regex, NER, context classifier — Concept 4) on every span at peak: 50,000 spans/sec × 5ms/span = 250 CPU-seconds/second, i.e., 250 CPU cores to keep up with peak load if applied uniformly. That number looks alarming until you notice that roughly 70% of spans (ToolSpan results without free-text payloads, AgentLoopSpan aggregation records) carry no free-text content at all — there is nothing for a PII detector to scan. Restricting PII detection to content-bearing spans (LLMSpan and RetrievalSpan, ~30% of total volume) cuts the requirement to ~75 CPU cores at peak — a 3.3x reduction from one filtering decision, and the same class of "don't do the expensive thing on the majority case that structurally can't need it" optimization this book returns to repeatedly.

    Query-path sizing is comparatively light: trace-detail lookups (GET /v1/traces/{trace_id}) hit ClickHouse for spans and Elasticsearch for content by prompt_text_ref/completion_text_ref — both point lookups on indexed keys, not scans, so query throughput scales with dashboard and on-call usage patterns rather than with ingestion volume. The one aggregation path that matters at scale is the cost and quality rollup dashboards, which run GROUP BY queries over the five attribution dimensions across a rolling window — exactly the workload ClickHouse's columnar layout is built for, and the reason this system does not attempt those rollups in Elasticsearch.

    Four things happen off one Kafka topic, not four separately provisioned pipelines: ingestion (parse, redact, cost, persist), quality monitoring (sample, judge, detect drift, alert), query (serve dashboards and trace lookups), and evaluation integration (shadow eval, experiment rollups). Kafka as the single fan-out point means a slow consumer in one path — say, the judge worker pool falling behind during a traffic spike — degrades that path's freshness without blocking ingestion or query. The alternative, a single synchronous pipeline that redacts, meters, and judges before acknowledging a span, would make the slowest of those three operations the ingestion throughput ceiling for all of them, which is exactly the coupling this fan-out avoids.

    Detailed Design¶

    Five load-bearing concepts, in the order a trace actually flows through them: the schema that has to represent an agent system's real execution shape (Concept 1), the metering that turns token counts into dollars attributable to a specific feature and tenant (Concept 2), the judging that answers the question standard metrics can't (Concept 3), the redaction and retention that make storing any of this legally defensible (Concept 4), and the loop that connects a production quality signal back to a concrete, fixable cause (Concept 5).

    Concept 1 — The LLM trace schema: a DAG, not a chain¶

    OpenTelemetry's span model — a tree of parent_span_id references — was designed for microservice request-response chains: service A calls B calls C, each hop one span, the tree shape following the call stack exactly. An LLM agent system breaks that model in four specific ways, and a trace schema that doesn't account for all four will misrepresent what actually happened the first time it meets a real agentic workload like Multi-Agent Research System's orchestrator-and-sub-agents fan-out.

    Difference 1 — the execution graph is a DAG, not a chain. An agent makes several tool calls in parallel, waits for all of them, and re-prompts the LLM with their combined results — Multi-Agent Research System's sub-agent fan-out is this pattern at a larger scale, N sub-agents dispatched simultaneously and reconciled at one synthesis call. A parent-only span tree represents "these three tool calls happened during this agent turn" but cannot represent "this specific LLM call consumed the output of that specific retrieval, three turns ago." The schema needs a second edge type alongside parent_span_id: an explicit dependency_span_ids list on every span, naming which prior spans' outputs this span actually consumed as input — distinct from which span temporally or structurally contains it.

    Difference 2 — content is the primary diagnostic artifact, not something to exclude. A web service trace excludes the request body by convention: it's about timing and errors, and the body is privacy-sensitive dead weight. In an LLM trace, the prompt and response are the only way to diagnose most real failures. A latency spike is meaningless without seeing that the prompt grew from 800 tokens to 4,000. A quality regression is not reproducible without the exact prompt that produced the bad output. This is why prompt_text_ref and completion_text_ref are first-class schema fields, not an afterthought bolted onto a metadata-only span — with retention and redaction controls (Concept 4) doing the work that content exclusion did in a traditional trace.

    Difference 3 — timing decomposes into dimensions standard tracing doesn't have. Wall-clock span latency conflates two independent things in a streaming LLM response: TTFT (time to first token — the user-visible latency before anything appears on screen) and inter-token latency (the generation rate once streaming starts). A request can have low TTFT and slow generation (large batch, throughput-constrained — see LLM Inference System) or high TTFT and fast generation (long context processing, then a clear decode path). Cost attribution needs its own token breakdown too: input_tokens, output_tokens, cached_tokens (prefix-cache hits, billed at a reduced rate — see LLM Inference System's prefix caching), and thinking_tokens (extended-reasoning tokens for models like Claude with extended thinking, billed separately from visible output).

    Difference 4 — agent loops recurse, and each iteration needs its own full record. A single user-facing request to an agent system can generate 3-8 LLM sub-calls as the agent iterates — plan, call a tool, re-plan, call another tool, synthesize. Each sub-call is a complete LLMSpan with its own token counts and timing, not a footnote inside one aggregated "agent turn" record; the aggregation happens one level up, in a dedicated AgentLoopSpan that rolls up total_iterations, total_input_tokens, total_cost_usd, and termination_reason across every child.

    The schema:

    TraceRoot {
  trace_id, session_id, user_id, tenant_id,
  product_surface,   // "chat" | "copilot" | "search" | "agent"
  model_tier,        // "fast" | "standard" | "reasoning"
  started_at, ended_at, total_latency_ms, ttft_ms,
  total_input_tokens, total_output_tokens, total_cached_tokens,
  total_cost_usd,
  outcome,           // "success" | "error" | "quality_flagged" | "timeout"
  experiment_id,     // nullable; set by the experimentation framework for A/B participants
  spans: [LLMSpan | ToolSpan | RetrievalSpan | AgentLoopSpan]
}

LLMSpan {
  span_id, parent_span_id, dependency_span_ids: [],
  span_type: "llm",
  model_id, model_version,
  prompt_hash,               // SHA-256 of the raw prompt -- dedup, version tracking, compliance-safe reference
  prompt_tokens, completion_tokens, cached_tokens, thinking_tokens,
  ttft_ms, generation_latency_ms, total_span_latency_ms,
  finish_reason,             // "stop" | "max_tokens" | "tool_calls" | "content_filter"
  temperature, top_p,
  prompt_text_ref,           // pointer into the content store; null if redacted or purged
  completion_text_ref,
  quality_score,             // null at write time; set post-hoc by the quality sampling job (Concept 3)
  tool_calls_generated: []
}

ToolSpan {
  span_id, parent_span_id,
  span_type: "tool",
  tool_name, tool_version,
  input_hash, output_hash,   // full payloads live in the content store, keyed by hash
  latency_ms, success, error_code, error_message
}

RetrievalSpan {
  span_id, parent_span_id,
  span_type: "retrieval",
  query_text_ref, query_tokens,
  retrieval_strategy,        // "dense" | "bm25" | "hybrid"
  retrieved_chunk_ids: [], retrieved_chunk_scores: [],
  reranker_used, reranked_top_k,
  prefix_cache_hit,
  latency_ms
}

AgentLoopSpan {
  span_id, parent_span_id,
  span_type: "agent_loop",
  agent_type, iteration_count, max_iterations,
  total_input_tokens, total_output_tokens, total_cost_usd,
  termination_reason,        // "task_complete" | "max_iterations" | "error" | "user_abort"
  child_span_ids: []          // every LLMSpan and ToolSpan id within this loop
}

    prompt_hash earns its place on every LLMSpan for three separate reasons, not one: deduplication — a system prompt that fires 10,000 times a day is stored once, not 10,000 times; version tracking — a deploy that changes the system prompt shows up immediately as a shift in the distribution of prompt_hash values across traffic, before anyone manually notices a wording change; and compliance-safe reference — the hash survives in the trace record even after the underlying content is purged from the content store per retention policy (Concept 4), so a trace from 60 days ago can still confirm "this used the same prompt as trace X from yesterday" without holding onto text that's supposed to be gone.

    Worked example — a multi-turn RAG chat request. A user asks a follow-up question in an ongoing chat session; the system retrieves, answers, and the user asks a second follow-up that depends on what was retrieved and answered earlier — a realistic three-turn exchange, not a single-shot query.

    flowchart TB
    ROOT["TraceRoot: trace_id abc123"] --> LOOP["AgentLoopSpan: root chat loop"]

    LOOP --> R1["RetrievalSpan 1: turn 1 query"]
    LOOP --> L1["LLMSpan 1: turn 1 answer"]
    R1 -.dependency.-> L1

    LOOP --> R2["RetrievalSpan 2: turn 2 query"]
    LOOP --> L2["LLMSpan 2: turn 2 answer"]
    R2 -.dependency.-> L2
    R1 -.dependency.-> L2

    LOOP --> R3["RetrievalSpan 3: turn 3 query"]
    LOOP --> L3["LLMSpan 3: turn 3 answer"]
    R3 -.dependency.-> L3
    L2 -.dependency.-> L3

    Every span's parent_span_id points at the same AgentLoopSpan — solid arrows in the diagram — because all six child spans belong to one session-level loop, not a chain where each span's parent is the one before it. The dashed arrows are dependency_span_ids, and they tell a different story than the parent tree does: LLMSpan 2 depends on both RetrievalSpan 2 (its own turn's retrieval) and RetrievalSpan 1 (context carried forward from turn 1, because the second question references something surfaced earlier in the conversation), and LLMSpan 3 depends on RetrievalSpan 3 and LLMSpan 2 (the third answer builds on the second, not just on newly retrieved content). A parent-only tree would show six children of one loop and nothing about which turn's output actually fed which — exactly the information a debugging engineer needs when turn 3's answer is wrong and the question is whether the retrieval or the carried-forward context from turn 1 is the culprit.

    Concept 2 — Token and cost metering: accurate attribution at AI scale¶

    Token cost is the dominant variable cost line in an AI product — a single call can run $0.001 (Haiku-class, short prompt) to $5.00 (Opus-class, 100K-token context) — and without per-request attribution, engineering has no way to answer "is the new summarization feature cost-profitable," "which tenant is consuming 40% of the LLM budget," or "did last Tuesday's prompt change cause a 30% cost increase." All three questions require the same underlying capability: cost computed and attributed at the individual span, not estimated in aggregate after the fact.

    The metering pipeline applies pricing at ingest, not at query time. Every LLMSpan carries token counts from the provider's response metadata; the metering service looks those up against the current pricing table and writes cost_usd onto the span immediately, in the Flink stage from High Level Design. This ordering matters more than it looks: because the price is baked in at write time, a historical cost query never has to replay pricing logic against old spans, and a provider price change never silently rewrites yesterday's numbers. The pricing table itself is versioned — a new provider price gets a new pricing-table version with an effective_from timestamp; spans written before that timestamp keep the cost they were originally charged, spans after use the new table. Retroactive cost recalculation, and the "wait, why did last month's bill total change" confusion that comes with it, doesn't happen by construction.

    Every trace carries five attribution dimensions simultaneously, not one:

    Dimension What it identifies
    user_id The end user who triggered the request
    tenant_id The organization, in a multi-tenant platform
    product_surface The feature or UI surface — chat, search copilot, email draft
    model_tier Which model tier served the request — fast/standard/reasoning
    feature_name The specific code path within a surface — "summarization," "code_completion," "follow_up_generation"

    Storing cost against all five at once, rather than picking one primary key, is what makes GROUP BY on any subset answer the business question that's actually being asked that week — "cost per tenant" one week, "cost per feature within one tenant" the next. ClickHouse or BigQuery is the right home for this table specifically because it's columnar and built for fast aggregation over hundreds of millions of rows; a row-oriented OLTP store would make every rollup query a full scan. Cost-metering data outlives content: 2-year retention, independent of the 7-day/90-day content tiers in Concept 4, because billing disputes and contract renewals need cost history long after the prompts that generated it are gone.

    Real-time budget enforcement is a separate, synchronous path from metering. Every service dispatches its LLM call through check_budget(tenant_id, estimated_cost) first — estimated_cost computed from the known input token count plus a historical average output-token estimate for that endpoint, since output length isn't known until the call completes. If the tenant's rolling 24-hour spend plus this estimate exceeds their budget cap, the endpoint returns a budget-exceeded response and the caller decides how to degrade: route to a cheaper tier, serve a cached response, or return a graceful fallback. The counter behind this check lives in Redis and increments with INCRBY in millicents — integer arithmetic specifically to avoid the floating-point race conditions that plague a naive "read balance, subtract, write balance" pattern under concurrent access. Because the estimate used for real-time enforcement is necessarily approximate, a daily reconciliation job debits or credits the difference between estimated and actual cost into the next day's counter — the correction happens on a schedule, not synchronously, because getting the fast path exactly right on every call isn't the goal; keeping the estimate from drifting over days is.

    Five cost anomaly patterns, each with a distinct root cause and a distinct fix, are worth alerting on independently rather than folding into one generic "cost went up" signal:

    Pattern Signal Likely cause What the alert should surface
    Per-feature cost-per-request spike A feature's average cost/call rises > 2x vs. 7-day rolling average Prompt grew, a new tool call was added, model tier changed Which span type drove the increase — LLMSpan prompt-token growth vs. a new ToolSpan in the path
    Tenant cost velocity A tenant's rolling 1-hour spend rate hits 5x their normal rate Runaway agent loop, unrate-limited batch job, potential abuse The tenant's top cost-contributing traces, ranked by cost_usd
    Cached-token ratio drop cached_tokens / input_tokens falls below 50% of baseline Prefix cache evicted (model restart), system prompt changed, a new code path bypasses caching prompt_hash distribution before vs. after the drop
    Model-tier shift Share of requests on the reasoning tier rises with no corresponding quality-metric increase Routing misconfiguration, a new feature defaulting to the wrong tier Route-decision trace for the affected product_surface/feature_name
    Inter-tenant cost anomaly One tenant's share of total platform cost jumps from 5% to 40% overnight A tenant launched an unrate-limited batch job Per-tenant cost trend over the prior 7 days, for context

    The cached-token pattern is the one most likely to be missed by a metering system that only tracks total spend: a 50-80% cost increase for a prefix-cache-dependent workload can happen with total token volume unchanged, purely because the same tokens are now being billed at full price instead of the cached rate — a signal that only shows up if cached_tokens is tracked as its own dimension, exactly why it's a first-class field on LLMSpan rather than folded into input_tokens.

    Concept 3 — Quality drift detection: observability for non-deterministic outputs¶

    This is the concept with no equivalent anywhere else in this book's observability vocabulary, and it's worth being concrete about why standard metrics miss it before describing the fix. Imagine a product manager changes the system prompt from "be concise and factual" to "be helpful and engaging." Responses get measurably longer. Latency is unchanged. Error rate stays at 0%. Token counts rise ~40% — a cost signal, caught cleanly by Concept 2's per-feature cost-spike alert. But the question that actually matters — are users getting better or worse answers — is invisible to every metric discussed so far. Session engagement might dip three weeks later, by which point the prompt change is a distant memory and nobody connects the two. Standard metrics measure operational health: is the system running correctly. Quality drift detection measures product health: is the system producing good outputs. Neither substitutes for the other, and a platform that only builds the first has built half an observability system while believing it built the whole thing.

    Layer 1 — embedding distribution shift, continuous and cheap. Sample 5% of production responses and embed each one with a lightweight embedding model — deliberately not the production LLM, run instead in a background ingestion job so it never touches the serving hot path. Maintain a rolling 7-day reference distribution as a set of cluster centroids (k-means, k=50, recomputed weekly), and for each new day's sample, compute the distance between the new embeddings and that reference using Maximum Mean Discrepancy (MMD) — distribution-free, and interpretable directly as "how much has the shape of responses shifted in semantic space." An alert fires when MMD exceeds 2σ of its own historical variability, and the alert payload names which cluster gained or lost density (which topic area shifted) and when the shift started — joined against the deployment log, so the alert reads "MMD spike started at 14:32 UTC Tuesday, 7 minutes after deployment abc123" rather than a bare number with no context. Critically, this layer does not say whether quality got better or worse — only that it changed. It's a canary, not a verdict, and its entire job is to decide when Layer 2 is worth running.

    Layer 2 — LLM-as-judge quality sampling, sampled and moderate cost. For 1-5% of production traces, run a post-hoc evaluation: pull the full trace (user query, retrieved context from the RetrievalSpan, response from the LLMSpan), send it to a judge LLM from a different model or provider than production (avoiding the self-scoring bias a same-model judge introduces — see LLM-as-Judge for the general mechanics this system applies in production), and score it 1-5: 1 — incorrect or hallucinated, 2 — partially correct but missing key information, 3 — correct but incomplete, 4 — correct and complete, 5 — excellent, with appropriate citations, returned as structured JSON with a hallucination_detected boolean. The score writes back onto the originating LLMSpan's quality_score field. Three alert conditions: P25 quality score drops more than 0.5 points vs. the 7-day baseline (a shift at the 25th percentile catches degradation concentrated in a subset of traffic that a mean would dilute); hallucination_detected=true rate exceeds 5% of sampled traces; and any single score-1 response reaching a user fires immediately, because a score of 1 isn't a trend to watch — it's a specific bad response that already happened.

    Sizing the sample rate is a statistical-power question with a concrete answer, not a guess: to detect a 5% quality regression (P25 dropping from 4.0 to 3.8) with 95% confidence and 80% power, a standard one-sample t-test needs roughly 800 samples/day. At 1M responses/day, that's a 0.08% sampling rate — 800 judge calls/day at ~$0.002/call is \(1.60/day, trivially affordable as a statistical floor. Production systems in practice sample well above this floor (Capacity Planning above uses 1%, ~\)600/day at this platform's volume) not because the floor is wrong, but because 800 samples/day is only enough to detect one aggregate regression — it says nothing about whether quality dropped specifically for one tenant or one feature. The extra spend above the statistical minimum buys per-dimension breakdowns, which is usually the question an incident actually needs answered.

    Layer 3 — evaluation suite integration, triggered and high-precision. When Layer 1 or Layer 2 fires, run the offline golden-set eval suite (the pattern this bridges into is covered in full in LLM Evaluation Architecture) against the current system state. The mechanism that makes this genuinely useful rather than a second independent alert: when a golden-set benchmark example fails, embed its input, find production traces with the most similar user queries (cosine similarity > 0.9), and attach up to a dozen of them to the eval failure report. An engineer reading the report doesn't see an abstract "benchmark example 'multi-step arithmetic' regressed" — they see that failure plus twelve real production traces from the last 24 hours where real users hit a version of the same query and got the degraded response, which both quantifies the blast radius and hands over reproducible examples to debug against by replaying the attached trace through old vs. new configuration side by side.

    Concept 4 — PII redaction and compliance-safe retention¶

    Prompt and response logging is simultaneously the highest-value debug capability this platform has and its single largest compliance risk, and the two pull in opposite directions on every axis: debugging wants full content, indexed, immediately accessible, retained for as long as anyone might need it; compliance wants the opposite of all four. No single storage tier satisfies both, which is why the architecture doesn't try — it resolves the tension with a tiered store instead of a policy document, generalizing the pattern AI Healthcare Assistant established for PHI specifically into a domain-agnostic PII pipeline that runs ahead of every content write, not just healthcare ones.

    PII detection runs in the ingest path, before a single byte of content is persisted, as three cascading stages inside the Flink processor from High Level Design:

    • Stage 1 — regex, under 1ms. Emails, US phone numbers, SSNs, credit card numbers (Luhn-checked), IP addresses, ZIP codes in identifying context. High precision on structured PII, essentially free.
    • Stage 2 — Named Entity Recognition, under 5ms, CPU. spaCy en_core_web_sm or a fine-tuned BERT-NER model detecting PERSON, ORG, GPE, ADDRESS. Domain-agnostic by design; domain-specific PII (medical conditions, account numbers) is added as Stage 1 pattern extensions per deployment, not baked into the NER model itself.
    • Stage 3 — context-aware classification, under 10ms. Some entities are only PII in context — "John" in "John Adams was the second president" is a historical fact; "John" in "Hi, I'm John and my address is..." is PII. A lightweight classifier (logistic regression over surrounding-window features) disambiguates, catching what Stage 2's context-free entity tagging can't.

    Two redaction modes, chosen per deployment context, not per request:

    Hash-based pseudonymization, for internal debug environments: each detected entity is replaced with a deterministic hash keyed to the trace's session_id — John Smith → PERSON_a3f9b2c1, same name producing the same hash within one session, a different hash in a different session. This preserves structure for debugging (an engineer can see that a name appeared and track it across turns in the same conversation) while remaining re-identifiable only by someone holding the separate, access-restricted session hash key — useful for authorized incident response, useless to anyone who doesn't have that key.

    Full token replacement, for external vendor storage or after an erasure request: each entity is replaced with its type label — [PERSON_NAME], [EMAIL_ADDRESS], [PHONE_NUMBER] — with no re-identification path at all. Required whenever content leaves the organization's direct control (an external analytics vendor without a data processing agreement), whenever a user has exercised GDPR right-to-erasure, and by default in regulated domains — healthcare deployments of this platform use full replacement for all PHI-adjacent content, the same non-negotiable posture AI Healthcare Assistant applies to PHI encryption generally.

    The tiered content store, separate from the trace metadata store so retention policy can differ between "what happened" (long-lived) and "what was said" (short-lived):

    Tier Content stored Retention Storage Access
    Hot (debug) Full trace, pseudonymized content 7 days Elasticsearch Engineers, on-call — read
    Warm (audit) Trace metadata + hashed PII + quality scores 90 days S3, Parquet Incident response, audit team
    Cold (compliance) Aggregated metrics only, no raw content 7 years S3 Glacier Legal/compliance only

    Trace metadata (span timings, token counts, cost_usd, quality_score) outlives content by design — after content purges from the hot tier, the metadata record remains with prompt_text_ref = null, so a cost or quality trend line from 60 days ago is still queryable even though the exact prompt behind any single point in it is gone.

    GDPR deletion is a five-step, verified sequence, not a single delete statement: mark user_id as deletion_requested; purge all hot-tier traces for that user (immediate, or within 24 hours if volume requires batching); delete the pseudonymized content for that user's traces in the warm tier while leaving the metadata record with user_id nulled, so it still contributes to aggregate metrics without identifying anyone; delete the session hash key for that user, which makes every PERSON_a3f9b2c1-style reference to them permanently unresolvable even in records that technically still exist; and generate a deletion certificate — timestamp, user_id, trace counts deleted per tier, hash-key deletion confirmation — stored in the compliance audit log. The deletion is verified, not assumed: querying hot and warm tiers for the deleted user_id after the fact must return zero results before the certificate issues.

    Concept 5 — Evaluation integration and the trace-to-incident workflow¶

    The platform closes a loop rather than terminating at "alert fired": production traces feed offline evaluation, and offline evaluation results point straight back at the production traces they explain.

    flowchart LR
    PROD["Production Traces"] --> SAMPLE["Quality Sampler: 1 percent"]
    SAMPLE --> JUDGE["LLM Judge"]
    JUDGE --> WRITEBACK["Write quality_score to LLMSpan"]
    WRITEBACK --> DRIFT["Quality Drift Detector: MMD plus score trend"]
    DRIFT --> ALERT{"Drift or regression detected"}
    ALERT -->|No| PROD
    ALERT -->|Yes| SHADOWTRIG["Shadow Evaluation Trigger"]
    SHADOWTRIG --> EVALSUITE["Offline Eval Suite"]
    EVALSUITE --> LINK["Trace Linkage: embed benchmark failure, find similar prod traces"]
    LINK --> ENGINEER["Engineer: reproducible failure plus prod impact"]

    The shadow evaluation pipeline runs before any model version, prompt change, or retrieval parameter change ships: replay a sample of recent production traces (read from the 90-day warm tier) through the new configuration without touching the live system. For each replayed trace, capture the new response, compare it against the original using the same LLM-as-judge rubric from Concept 3 plus structural diffs (response length delta, embedding cosine distance from the original, citation count change), and roll the comparisons up into a shadow evaluation report — "the new configuration produces responses 15% longer, with quality scores 3% higher on average, differing significantly from the original in 12% of cases." This is where shadow evaluation earns its keep beyond what offline eval alone covers: prompt changes and retrieval parameter tweaks rarely have dedicated offline benchmark coverage the way a model swap does, so replaying real traffic through the candidate configuration is often the only pre-deploy signal available for exactly those changes. Deployment Strategies: Canary & Shadow covers the general shadow-deployment mechanics this pipeline is a specific application of.

    The trace-to-incident workflow is what an on-call engineer actually receives when an alert fires — a quality score drop, a cost spike, a latency P99 breach. Not just the metric and its deviation, but: the top 5 traces that contributed most to the deviation (lowest quality scores for a quality alert, highest cost for a cost alert, slowest for a latency alert), and a distribution diff — the current trace-metadata distribution against the 24-hours-before-incident distribution, specifically checking whether average prompt_tokens moved, whether retrieval hit rate dropped, or whether a new tool type appeared in the traces. That diff is the most actionable artifact in the whole alert: a quality drop with a simultaneous prompt_hash distribution shift points straight at a prompt change worth diffing; a quality drop with a simultaneous retrieval hit-rate drop points at RAG System's retrieval layer — an embedding model or index issue — not the generation step at all. Handing an engineer the metric alone forces them to re-derive this diff by hand; handing them the diff turns a triage session into a five-minute read.

    Experiment result integration. Every trace's experiment_id field (null for non-experiment traffic) lets the platform roll up quality score distribution, cost per request, and TTFT P50/P95 per experiment arm, joined against engagement signals pulled from the product analytics pipeline. A two-sample t-test with Bonferroni correction across the tracked metrics tells the experiment dashboard whether treatment differs significantly from control — the same statistical discipline AI Recommendation System applies to its own A/B testing. This platform, not the product analytics tool, is the source of truth for quality-bearing experiment outcomes specifically because LLM-as-judge scores and hallucination rates exist nowhere else in the stack — a product analytics platform can tell you engagement moved, but only this system can tell you whether the responses got better.

    API Design¶

    SDK design is the differentiating piece of this section, because engineers should never hand-write a span. The SDK wraps the application's LLM client via auto-instrumentation — monkey-patching the client library the same way OpenTelemetry's auto-instrumentation wraps HTTP clients — so every call the application makes through its normal client code generates a correctly-shaped span with no manual start_span/end_span calls anywhere in application logic. Context propagation carries trace_id and the current parent_span_id through the call stack implicitly (thread-local in Python, async context in both languages) so that a tool call nested three levels inside an agent loop — or a sub-agent's isolated context, as in Multi-Agent Research System — still reports a correctly linked span without the application explicitly threading an ID through every function signature. Batch export buffers spans locally for 100ms or 100 spans, whichever comes first, then flushes asynchronously in a background thread — the SDK never blocks the application's hot path waiting on the ingestion API, because an observability call that can slow down the thing it's observing has already failed at its one job. SDKs ship for Python (primary — the language essentially all AI workload code is written in) and TypeScript (for full-stack AI applications that instrument both client and server).

    Three external APIs:

    Retrieval Layer¶

    This platform's retrieval problem is different in kind from RAG System's — there's no semantic similarity search over documents — but the underlying split is the same shape: a columnar store for aggregation, a document store for full-text and content lookup, each doing what the other is bad at. ClickHouse handles every query that aggregates across the five cost-attribution dimensions or rolls up quality scores over a time window — GROUP BY tenant_id, feature_name over hundreds of millions of rows is exactly the workload columnar storage exists for, and it's also where prompt_hash lookups resolve for prompt-version tracking (Concept 1). Elasticsearch handles trace search by content — free-text search over redacted prompts and responses within the 7-day hot-tier window, and point lookups by prompt_text_ref/completion_text_ref when a trace-detail page needs to render actual content rather than just metadata. A trace-detail request (GET /v1/traces/{trace_id}) is a fan-out to both: span tree and cost/quality metadata from ClickHouse, content from Elasticsearch if it's still within retention — resolved in parallel, not sequentially, since neither lookup depends on the other's result.

    Agent Layer¶

    This platform has no agent loop of its own — it doesn't reason, plan, or call tools. What it has instead is the schema and SDK machinery that make someone else's agent loop observable, and that's a harder problem than it sounds once an agent system nests. Multi-Agent Research System's orchestrator dispatching N sub-agents, each running its own bounded search-read-summarize loop in an isolated context, produces a trace where one AgentLoopSpan (the orchestrator's) contains several more AgentLoopSpans (each sub-agent's) as children — recursion, not a flat list. The SDK's context propagation has to carry trace_id and the current parent_span_id across whatever boundary separates the orchestrator from a sub-agent, whether that's a thread, a process, or — in a distributed deployment — a network call to a separate service instance running the sub-agent's isolated context. Getting this wrong doesn't crash anything; it silently produces a trace where six sub-agent sessions all appear to be direct children of the root trace with no orchestrator span connecting them, which is a materially harder trace to debug a synthesis failure in, because the aggregation point (which sub-agent's output fed the final answer) has vanished from the record.

    Recursion depth itself becomes an observability signal, not just a schema detail: an AgentLoopSpan nesting deeper than the system's expected agent architecture (say, three levels when the product's deepest legitimate pattern is two — orchestrator, sub-agent) is either a bug in the calling application's loop-termination logic or a cost bomb in progress, and it's cheap to alert on directly from the span tree's structure, independent of anything Concept 2's cost anomaly detection would eventually catch from the dollar side.

    Model Role Footprint Key property

    The judge-model tiering mirrors LLM Inference System's tier-routing logic applied to evaluation rather than serving: a cheap, fast model handles the high-volume continuous sample (Layer 2), and the expensive, most-capable model is reserved for the low-volume, high-stakes runs — shadow evaluation before a rollout, benchmark scoring during an incident — where the cost per call matters far less than getting the judgment right.

    Observability Layer¶

    This platform has to watch itself, because a silent failure in the thing that's supposed to catch silent failures is the worst possible failure mode in the whole stack. Four self-monitoring metrics carry that weight:

    • Span ingestion lag — time between a span's generation by the application and its being indexed in ClickHouse. Target under 10 seconds; past 60 seconds means the Flink processor is backlogged, and every downstream signal (cost alerts, quality alerts) is now stale by exactly that much.
    • PII detection error rate — spans that failed PII detection and were dropped or, worse, stored unredacted. Target is zero, and unlike every other metric on this platform, this one has no acceptable non-zero baseline — any occurrence is a P0, not a trend to watch.
    • Quality judge queue depth — sampled traces waiting for a judge score. A growing queue means the judge worker pool is undersized for current sample volume, and every metric downstream of quality_score (Concept 3's drift detection, Concept 5's experiment dashboards) degrades in freshness until it's fixed.
    • Cost metering reconciliation error — the daily diff between cost_usd summed from ClickHouse and the provider's actual invoice. A discrepancy over 2% triggers investigation, because it means the 1% accuracy NFR from Requirements is being missed in practice, not just in theory.

    Two more, standard for any streaming ingestion system but worth naming explicitly given how much rides on them here: Kafka consumer lag per consumer group (ingestion path vs. quality-sampling path, tracked separately since they're independent consumers of the same topic), and ClickHouse/Elasticsearch cluster health — disk utilization, query latency P95, replication status — since both stores sit directly behind every dashboard and every alert this chapter has described.

    Security Layer¶

    Five concerns specific to this platform, arising directly from the fact that it is the repository of the most sensitive data any AI system in this book produces — the actual prompts and responses, not just metadata about them.

    1. Content access is role-gated, not just authenticated. Prompt and response text may contain trade secrets, confidential user data, or business-sensitive information wholesale. Engineers can search traces by metadata freely, but viewing content requires an explicit access request logged to an audit trail — read access to the hot tier is a deliberate, recorded action, not an implicit consequence of having engineer credentials.
    2. The judge pipeline is itself a third-party data flow. The LLM-as-judge in Concept 3 receives real (pseudonymized) production prompts. The judge provider needs a data processing agreement confirming it doesn't train on this traffic, the same BAA-chain discipline AI Healthcare Assistant requires for any vendor touching PHI — and regulated deployments run a self-hosted judge model specifically to avoid this dependency entirely.
    3. The budget endpoint fails open, deliberately. /internal/cost/check_budget sits on the serving hot path of every AI system in this platform; if its Redis backend is unavailable, the correct behavior is to allow the request through rather than reject all LLM traffic platform-wide over an observability dependency. Every fail-open event is logged for next-day cost reconciliation — the tradeoff is a bounded, recoverable cost-visibility gap, not a platform-wide outage over a non-critical-path failure.
    4. Trace injection is a live threat, not a hypothetical one. A malicious or manipulated LLM response could contain text engineered to look like span data, attempting to inject false records into the trace store — a prompt-injection variant aimed at observability data itself rather than the application. The SDK parses span structure exclusively from instrumented application code, never from LLM response content, closing this off at the source rather than trying to sanitize it downstream.
    5. Deletion is a high-privilege, rate-limited, audited operation. The /internal/deletion/request endpoint permanently removes data — it requires an authenticated token scoped to the requesting user's own user_id, a rate limit of 10 requests/user/day, and (for user-initiated requests) a confirmation step before processing, because a permanently destructive API with no friction is a bigger risk than the inconvenience of adding some.

    Failure Handling¶

    Failure Detection Response
    Kafka unavailable or the SDK's flush fails SDK export error, retried with backoff Spans buffer locally with a bounded queue; past the buffer limit, oldest spans are dropped rather than blocking the application — a gap in observability beats a stall in the product
    Flink processor backlogged Span ingestion lag metric exceeds 60s Scale out Flink task slots; ingestion continues from Kafka's retained offset, no data loss, only freshness delay
    PII detector fails on a span Exception during Stage 1-3 processing Fail closed: the span's content is not written to the content store at all (metadata still persists); never store unredacted content on a detector failure
    Budget-check Redis unavailable Health check failure on /internal/cost/check_budget Fail open — allow the LLM call through, log the fail-open event for next-day reconciliation (Security Layer)
    Judge LLM provider outage Judge worker error rate spikes Queue sampled traces for retry; if sustained, fall back to Layer 1 embedding-drift monitoring alone until the provider recovers, and flag quality dashboards as running on reduced signal
    ClickHouse or Elasticsearch unavailable Query-path health check failure Trace search and dashboards degrade or 503; ingestion is unaffected, since it writes independently and can buffer in Kafka until the store recovers
    GDPR deletion partially completes Post-deletion verification query returns non-zero results Do not issue the deletion certificate; retry the failed tier; escalate to the privacy officer if verification still fails past the 24-hour target
    Content-store tier transition fails (hot to warm) Scheduled tier-migration job error Content ages out of the hot tier on schedule regardless — a stalled warm-tier write is a warm-tier data-completeness gap, not a reason to extend hot-tier retention past its compliance-driven window

    The property tying these together: ingestion and the budget check are the two paths that must never become a dependency the rest of the platform can't survive losing — one fails open, the other buffers and drops the oldest data rather than blocking. Everything else on this list can degrade — slower dashboards, a delayed quality signal, a paused deletion — without taking down any AI system this platform observes.

    Q3 -->|Triggered, low volume| STRONG["Most-capable judge model,\nshadow eval and benchmark runs"]

    1. Quality-sampling rate. Higher sampling buys statistical power and faster drift detection at higher cost and (marginally) more judge-pipeline load; the floor for detecting a 5% regression within 24 hours at 95% confidence is typically 0.1-1% of traffic for a product doing 100K+ requests/day (Concept 3) — below that floor, a real regression can hide in noise for days.

    2. PII detection sensitivity. Higher sensitivity — a lower bar for what counts as PII — cuts privacy-incident risk but redacts more legitimate content as a false positive, directly reducing debug utility on exactly the traces an engineer most needs to read closely. Healthcare-adjacent deployments tune toward high sensitivity by default; a developer-tools product with low inherent PII density can run more leniently without meaningfully raising its exposure.

    3. Hot-tier retention window. 7 days is the default because it widens the privacy-exposure window for anything that slips past detection for every day it's extended, and because storage cost scales linearly with it. Extending it is a per-incident, justified exception — "I need 30 days to catch an intermittent bug" — not a platform-wide default raised because 7 days is occasionally inconvenient.

    4. Judge model capability. A more capable judge scores more accurately but costs more per call and adds latency to the quality feedback loop; a mid-tier model (Sonnet-class) is the right choice for the high-volume continuous sample specifically because it's accurate enough for most responses and affordable at the sample rate Concept 3 requires, while the most-capable model is reserved for shadow evaluation and benchmark runs, where call volume is orders of magnitude lower and getting the judgment exactly right matters more than per-call cost.

    5. Synchronous vs. asynchronous cost metering. Synchronous metering (block the response until cost is recorded) guarantees no missed cost record but adds 5-10ms to every response; asynchronous metering (fire-and-forget from the application, processed in the Flink pipeline) adds zero latency but risks losing a record if the pipeline backs up. This platform runs async for standard metering — the 2-year-retention cost table can tolerate a rare gap far better than every AI system in the platform can tolerate 5-10ms tacked onto every response — and reserves synchronous handling for the one place accuracy has to be immediate: the budget-enforcement check itself.

    Interview Discussion¶

    Most candidates asked to "design an observability system for an AI product" describe Datadog plus structured logs and call it sufficient. That answer is wrong in a specific, diagnosable way, and interviewers who use this prompt are testing for exactly one thing first: does the candidate understand that LLM quality is not captured by error rate and latency at all.

    The discriminating question: "Your system's error rate is 0% and latency is normal. How would you know if response quality degraded?" A candidate who can't answer this hasn't thought about LLM non-determinism as an observability problem, full stop — the honest failure mode of a candidate who has only ever operated conventional software. The right answer names the embedding-distribution-shift monitor as a cheap, continuous canary; LLM-as-judge sampling as the actual measurement; and the eval-suite bridge as the diagnosis step that turns "quality dropped" into "here's the specific benchmark that regressed and twelve production traces it explains" — Concept 3's three layers, produced unprompted and in that order.

    A weak answer describes trace collection, a cost dashboard, and a generic "quality score" with no mechanism behind it — no judge model, no sampling rate, no statement of what "quality score" is even measuring or how often it updates. It treats PII handling as "we'd redact sensitive fields" without a pipeline, a retention tier, or a deletion mechanism behind that sentence.

    A strong answer opens by naming the four ways an LLM trace differs structurally from a microservice trace (Concept 1) before describing any storage or dashboard — DAG rather than chain, content as diagnostic data rather than excluded payload, token-level timing decomposition, and agent-loop recursion — because getting the schema wrong makes everything built on top of it wrong in a way no dashboard can fix later.

    Staff-level probe: "The LLM-as-judge quality score drops from 4.1 to 3.3 over 48 hours. No deployments were made. Error rate is 0%, latency is unchanged, cost is unchanged. What happened and how do you find it?" The absence of a deployment rules out a prompt or model-version change; unchanged cost rules out prompt-length growth (token counts would move); unchanged latency rules out a routing change to a different tier. What's left, once those three are eliminated by the numbers already in hand, is either a shift in the user query distribution — users asking harder questions the system was never actually good at, which reads as a regression but is really a coverage gap that was always there — or a retrieval-quality degradation invisible to latency_ms (an embedding index gone stale, documents no longer current). The diagnostic move is to check embedding-distribution shift on the user queries, not the responses: if query distribution shifted toward harder questions, this isn't a regression to fix, it's a capability gap to prioritize; if query distribution is stable, the next check is RetrievalSpan chunk relevance scores — are retrieved chunks measurably less relevant than 48 hours ago, pointing at RAG System's retrieval-layer diagnostic tree rather than anything in this platform's generation-side monitoring.

    Staff-level probe: "Legal receives a GDPR deletion request for user 12345 and wants written confirmation within 48 hours that all personal data is gone. What does your system do, and what does the confirmation contain?" The candidate should walk the five-step sequence from Concept 4 without prompting: trigger deletion, purge hot-tier Elasticsearch documents for that user_id, null the user_id field and delete the pseudonymization hash key in the warm tier, purge referenced content-store objects, and verify with a query that returns zero records across every tier before generating anything. The confirmation itself is the deletion certificate — timestamp, counts deleted per tier, hash-key deletion confirmation, verification result — and every step is written to an immutable audit log independent of the certificate, because "trust me, it's deleted" is not an answer legal can forward to a regulator; a verified, timestamped record is.

    A candidate who volunteers the DAG-vs-chain trace-schema distinction unprompted, and who treats quality drift as a first-class observability category rather than an afterthought bolted onto error-rate dashboards, is operating at the depth this case study is built to surface.
