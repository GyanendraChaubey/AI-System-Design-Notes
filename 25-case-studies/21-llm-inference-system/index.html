    LLM Inference System — System Design Case Study¶

    Every other chapter in this section designs a product: a chat assistant, a coding agent, an enterprise search platform. This chapter designs the thing underneath all of them — the serving system that turns a set of trained weights sitting in object storage into a low-latency, high-throughput, streaming token API. ChatGPT, Claude, Cursor, and every agentic system in this book are callers of this system, not builders of it — but the engineers who build it are solving a fundamentally different problem than the engineers who build on top of it, and this chapter is the closest thing in this book to a systems-programming case study: batching algorithms, GPU memory management, hardware-aware parallelism, and fleet scheduling, rather than product features.

    The central claim this chapter makes, and returns to at every section: LLM serving is not a request-response API problem. Two properties break the standard playbook. First, generation is iterative — producing token 1,000 requires a forward pass that reads the cached state of tokens 1 through 999, so a "request" is not one unit of work but a variable-length chain of dependent steps whose length is unknown at arrival time. Second, the dominant resource is GPU VRAM, and VRAM is shared between two very different consumers — static model weights and dynamic per-request state — in a way that makes naive memory management catastrophically inefficient. Continuous batching, PagedAttention, tensor parallelism, and speculative decoding are not independent features to bolt on. Each one is the direct engineering response to one of these two properties. Understanding the failure mode each mechanism fixes is more valuable than memorizing the mechanism itself, and this chapter is organized to lead with the failure every time.

    This case study builds directly on GPU Fundamentals for AI Systems — read that first if the compute-vs-bandwidth distinction and the decode throughput formula are unfamiliar, because every mechanism below is shaped by them. A reader who doesn't understand why VRAM bandwidth, not Tensor Core count, is the binding constraint on decode will not understand why PagedAttention matters.

    Requirements¶

    Functional

    • Accept inference requests (prompt plus generation parameters: max tokens, temperature, stop sequences, streaming flag) and return generated tokens, streamed incrementally rather than as one blocking response — see Streaming & Real-Time AI for the API-level contrast this system's iteration loop makes possible underneath.
    • Schedule and batch concurrent requests at the token-generation level, not the request level, so that GPU utilization does not collapse under variable output lengths.
    • Manage GPU memory (model weights plus per-request KV cache) so that memory fragmentation does not artificially cap concurrency far below the hardware's real capacity.
    • Support multiple model tiers (fast/small, balanced/mid, quality/large) with a routing layer that assigns each request to a tier based on complexity, declared SLO, and system load — see Multi-Model Serving & Routing.
    • Shard models that exceed single-GPU VRAM capacity across multiple GPUs via tensor and pipeline parallelism, matched to the interconnect topology available.
    • Cache and reuse KV state for shared prompt prefixes (system prompts, few-shot templates) across requests and, where safe, across tenants.
    • Enforce per-request SLO classes (interactive/streaming vs. batch/async) with admission control and queue-timeout rejection rather than silent late delivery.
    • Autoscale the GPU fleet ahead of demand, accounting for the fact that GPU provisioning and model loading are minutes-scale operations, not seconds-scale.

    Non-functional

    • TTFT: P50 < 300ms, P95 < 800ms for Tier 1 (fast-tier) streaming requests. Reasoning/quality-tier requests carry a separate, looser TTFT budget — conflating the two tiers' latency SLOs into one blended number, as ChatGPT notes, either over-provisions the fast tier or hides real regressions in the slow one.
    • Throughput: sustained > 10,000 output tokens/second per 8-GPU node for a 70B-class model under continuous batching — this is the number a capacity plan is built from, and it must come from a load test of the actual model/precision/engine combination, not a spec sheet (see GPU Sizing & Capacity Planning).
    • GPU utilization: > 75% at steady state. Utilization below this is the single clearest sign that the batching or memory-management layer, not the hardware, is the bottleneck.
    • KV cache VRAM utilization: > 85% (the PagedAttention target — see KV Cache Management). Utilization meaningfully below this means the scheduler is leaving concurrency on the table; utilization above ~95% risks eviction storms under load spikes.
    • Model loading time: < 3 minutes on a warm instance joining the fleet; cold-provisioned capacity (new hardware from a cloud provider) is a 7–25 minute operation and must never be the primary response to a traffic spike.
    • Availability: no single GPU, node, or availability zone failure should take down a model tier; degraded tiers shed to cheaper tiers rather than fail outright.

    Explicitly out of scope: model training, fine-tuning, and RLHF pipelines (a separate ML research system — see Transformer Internals for Systems Engineers); model evaluation harnesses (see LLM Evaluation Architecture); and application-layer prompt engineering — this system serves raw prompts and returns raw tokens, and has no opinion on what an application does with either.

    Capacity Planning¶

    Using the method from GPU Sizing & Capacity Planning, sized for a platform serving a frontier-class model at production scale: 50M output tokens/day across all tiers, split 75% Tier 1 / 20% Tier 2 / 5% Tier 3 — a distribution calibrated so the cheap tier absorbs the bulk of everyday traffic and the expensive tier is reserved for requests that actually need it (see the routing classifier in Concept 4 below).

    Tier Share of daily tokens Daily output tokens Achievable tok/s/GPU (load-tested, illustrative) GPUs at average load Peak multiplier GPUs at peak
    Tier 1 — fast, 8B int8 75% 37.5M 200 37.5M ÷ (200 × 86,400) ≈ 2.2 3x ≈ 7
    Tier 2 — mid, 70B int8 20% 10M 40 10M ÷ (40 × 86,400) ≈ 2.9 3x ≈ 9
    Tier 3 — quality, 405B-class or MoE 5% 2.5M 10 2.5M ÷ (10 × 86,400) ≈ 2.9 3x ≈ 9
    Total ≈ 8 ≈ 25

    Roughly 25 GPUs at peak across all three tiers — an order-of-magnitude planning estimate, not a load-test result. The real number depends on batch efficiency (Concept 1), KV cache headroom (Concept 2 and the Scale Estimation below), and how tightly the routing classifier's actual traffic split matches the 75/20/5 assumption it was planned against. Note the shape of this table: Tier 1 carries 75% of tokens but needs the fewest peak GPUs (7), while Tier 3 carries only 5% of tokens but needs comparable GPU count (9) — a direct consequence of per-GPU throughput collapsing by 20x from Tier 1 to Tier 3. This is the same dynamic ChatGPT's capacity planning surfaces: the reasoning/quality tier's KV cache and compute profile, not raw token share, dominates fleet sizing.

    Scale Estimation¶

    KV cache budget per 8-GPU node, worked for Tier 2 (70B at int8, TP=2): each TP pair holds 70GB of weights split across 2× A100 80GB = 160GB total, leaving 90GB for KV cache, activations, and framework overhead. At ~2.6MB of KV cache per 1,000 tokens of sequence length for a 70B-class model (2 × 80 layers × 64 heads × 128 head_dim × 2 bytes ÷ 1,000, matching the formula in KV Cache Management):

    • Usable KV budget per TP pair: ~90GB × 0.85 (reserving headroom for CUDA context and activations) ≈ 76.5GB
    • Total KV cache capacity per TP pair: 76.5GB ÷ 2.6MB × 1,000 ≈ 29.4M tokens of aggregate sequence length
    • At 4 TP pairs per 8-GPU node: ~117.6M tokens of concurrent KV cache capacity
    • At an average 1,500 tokens/request (a mixed short-chat/moderate-context workload): ~78,400 concurrent request-tokens' worth of headroom, translating in practice to on the order of 80–100 concurrent requests per node once prefix-cache reservation and safety margin are subtracted
    • Prefix cache reservation: 20% of the KV budget set aside for shared-prefix pages (system prompts, few-shot templates) — roughly 15GB per TP pair, enough to hold a 500-token system prompt plus a dozen other less-common cached prefixes at the ~512KB-per-page granularity Concept 2 describes below.

    This is the arithmetic that determines whether a fleet sized by the Capacity Planning table above actually holds its SLOs — a node that is throughput-adequate on paper but under-provisioned on KV cache will hit the eviction failure mode described in Concept 2 long before it hits a compute ceiling.

    High Level Design¶

    flowchart TB
    CLIENT["Caller: chat app, agent runtime, RAG pipeline"] --> ROUTER["Request Router\nSLO class assignment + tier selection + load balancing"]
    ROUTER --> SCHED["Scheduler\ncontinuous batching + KV page allocation + queue management"]
    SCHED --> WORKERS["Inference Workers\nTP groups, each running one model shard"]
    WORKERS --> KV[("KV Cache\nPagedAttention + prefix cache + free page pool")]
    KV --> WORKERS
    WORKERS --> STREAMER["Token Streamer\nstreams tokens back per iteration"]
    STREAMER --> CLIENT

    AUTOSCALER["Autoscaler\nwatches TTFT + queue depth"] -.-> SCHED
    AUTOSCALER -.-> WARMPOOL["Warm Pool Manager\npre-loaded standby instances"]
    WARMPOOL -.-> WORKERS

    Four components, four distinct responsibilities. The router is a thin, fast layer (target: single-digit milliseconds) that assigns an SLO class and a model tier and picks a target pool — it does not touch GPU memory. The scheduler is where continuous batching and KV page allocation live — it decides, every single decode iteration, exactly which requests are in the active batch. Inference workers are the TP/PP-sharded model processes that actually run forward passes. The KV cache is drawn as its own box deliberately, even though it physically lives inside the workers' VRAM, because it is managed as an independent resource with its own allocator, its own free-page pool, and its own eviction policy — not a side effect of running the model.

    Detailed Design¶

    The five subsections below are the load-bearing mechanisms of this system. Each one starts from a specific failure mode and ends at the mechanism production systems use to fix it.

    Concept 1 — Continuous batching: why naive batching destroys GPU utilization¶

    The failure mode. A traditional serving system batches N requests together, runs one forward pass over all N, returns results, and starts the next batch — static batching. This is fine for fixed-output-size workloads (classification, embeddings). It fails catastrophically for autoregressive generation because output length is variable and unknown at request time. Request A might stop after 12 tokens; request B might generate 800. Under static batching, the batch cannot complete until B finishes — for the 788 tokens B generates after A is done, the GPU is computing forward passes for A that serve no purpose whatsoever, because A's output was ready 788 iterations ago and its caller is just waiting on a batch that hasn't returned. This is head-of-line blocking, and it is not a rare edge case — it is the default outcome any time output lengths vary, which in production traffic is always. Measured GPU utilization under static batching on realistic traffic: 30–45%.

    The fix. Continuous batching (also called iteration-level scheduling — the mechanism Batching & Continuous Batching covers in full depth) moves the scheduling unit from the request to the single decode step. After every token-generation iteration, the scheduler:

    1. Checks which active requests hit a stopping condition (EOS token or max-length limit) this step, and evicts them — their KV pages return to the free pool immediately, their caller receives the final token, and their slot is now open.
    2. Admits waiting requests from the queue into the freed slots, bounded not by a fixed batch size N but by how much KV cache VRAM is currently free.
    3. Runs the next iteration on the updated batch composition.
    sequenceDiagram
    participant Q as Queue
    participant S as Scheduler
    participant KV as KV Page Allocator
    participant G as GPU Workers

    Q->>S: Requests A, B, C, D admitted
    S->>KV: Allocate initial pages for A, B, C, D
    loop Every decode iteration
        S->>G: Run one forward pass, batch = current active set
        G-->>S: One token per active request
        alt A hits EOS this step
            S->>KV: Free A's pages immediately
            S->>Q: Admit next queued request E into A's freed slot
        end
    end

    The result: a request completes and a new one joins within a single decode iteration — typically under 50ms — and the GPU is never idling on behalf of a finished request. Measured GPU utilization under continuous batching on the same traffic: 70–90%. The batch size at any given iteration is not a config constant; it is bounded dynamically by available KV cache VRAM, which is exactly why Concept 2 (KV cache paging) is a prerequisite for Concept 1 to work at all — a scheduler that wants to admit a new request mid-batch cannot pre-reserve contiguous VRAM for an unknown future sequence length, so continuous batching requires paged, non-contiguous KV allocation underneath it.

    This is also the mechanism that makes token streaming possible in the first place, not just an optimization layered on top of it: because the scheduler already operates at one-token-per-iteration granularity, each generated token is immediately available to hand to the token streamer and push to the caller over the open connection — the iteration-level loop and the token-by-token streaming cadence are the same loop, not two separate systems that happen to cooperate.

    Concept 2 — KV cache management: the memory problem that determines serving capacity¶

    Why the cache exists. Autoregressive attention at step T requires the keys and values of every prior token 1 through T−1. Recomputing them from scratch at every step is O(T²) per full generation — untenable. The KV cache stores each token's K and V exactly once, computed during that token's own forward pass, and reused for every subsequent step. This is what turns generation from a quadratic into a linear-cost operation, and it is why the KV cache is not optional infrastructure — it is the mechanism that makes multi-thousand-token generation computationally possible at all.

    Why it's expensive. For a 70B-class model at fp16: 2 × n_layers × n_heads × head_dim × T × 2 bytes. At representative dimensions (80 layers, 64 heads, 128 head_dim), this works out to roughly 2.6MB per 1,000 tokens of sequence length. A single request generating 4,000 tokens accumulates ~10.5MB of KV cache; at 100 concurrent such requests, that's ~1.05GB — small compared to model weights at first glance, but the number that actually matters is concurrency at scale and long context, where KV cache overtakes weight memory as the dominant VRAM consumer (see the worked arithmetic in KV Cache Management). An H100 with 80GB, after loading a 70B model's weights (~140GB at fp16 — already requiring tensor parallelism across 2 GPUs before a single request is served), has a hard, fixed remaining budget for everything else.

    The fragmentation failure mode. Before any paging scheme, serving engines pre-allocate a contiguous VRAM block per request sized for its maximum possible length, because CUDA memory allocation requires contiguity. Two forms of waste result: a request allocated for 4,096 tokens but generating 500 holds ~3,600 tokens' worth of reserved-but-unused memory for its entire lifetime (internal fragmentation), and completed requests free blocks of varying sizes scattered through VRAM that a new request's contiguous-allocation requirement cannot reuse even when aggregate free memory is sufficient (external fragmentation). Measured VRAM utilization under naive allocation on variable-length production traffic: 40–60% — meaning nearly half the GPU's memory is provisioned but unusable at any given moment.

    PagedAttention. vLLM's foundational contribution applies OS virtual-memory paging directly to the KV cache. The cache is divided into fixed-size pages (16–32 tokens each, ~512KB per page for a 70B model at the dimensions above). Each request holds a logical page table mapping its sequence positions to physical page locations in VRAM — pages need not be contiguous, exactly as a CPU's MMU maps virtual addresses to arbitrary physical RAM frames.

    end

    A request needing more capacity pulls the next page from a global free pool; a completed request's pages return to that same pool immediately, available to any other request regardless of size or shape, because every page is uniform and interchangeable. Fragmentation collapses to near-zero — bounded only by, at most, one partially-filled page per request. Measured VRAM utilization with PagedAttention: > 90%.

    The attention kernel itself must be rewritten to read from these non-contiguous physical pages via the page table during the attention computation — this is precisely why PagedAttention required a custom CUDA kernel rather than a pure-PyTorch reimplementation; standard attention kernels assume a single contiguous KV tensor, and teaching the kernel to gather scattered pages on the fly is the actual engineering contribution, not the paging idea in the abstract. Page size is a real tradeoff: smaller pages (16 tokens) minimize internal fragmentation — at most 15 wasted token-slots per request — but increase page-table bookkeeping overhead per request; larger pages reduce that overhead but waste more at each sequence's tail. Production systems converge on 16–32 tokens per page as the practical sweet spot.

    Prefix caching. When many requests share an identical prefix — a long, static system prompt reused across an application's traffic — that prefix's KV cache can be computed once and shared. Each prefix cache entry is keyed by a hash of its token IDs; on a new request, the engine hashes the incoming prefix, checks for a hit, and if found, attaches the prefix's pages as read-only, reference-counted shared pages rather than duplicating them, computing fresh KV only for the tokens after the shared prefix. Eviction is LRU, bounded by a configured fraction of the KV VRAM budget (the Scale Estimation above reserves 20%). The payoff compounds with traffic volume: a 500-token system prompt reused across 10,000 daily requests saves 4,995,000 tokens of redundant KV computation; at ~2ms per token of KV computation on one A100 for a 70B model, that is roughly 9,990 seconds (2.8 hours) of GPU time saved per day from prefix caching alone, on that one prompt.

    Concept 3 — Tensor and pipeline parallelism: serving models larger than one GPU¶

    A 70B model at fp16 needs ~140GB — more than one H100's 80GB. A 405B model needs ~810GB — more than an entire 8-GPU node's combined VRAM if run naively. Large models physically cannot run on a single accelerator; they must be sharded. Tensor & Pipeline Parallelism and Multi-GPU Topologies & Interconnects cover the full mechanical and interconnect-bandwidth depth behind what follows; this section covers the deployment-facing consequences.

    Tensor parallelism (TP) — splitting within a layer. Individual weight matrices are split across GPUs: a 64-head attention layer split TP=4 gives each GPU 16 heads, computed independently with no communication needed during the matrix multiply itself. But every layer's output must be synchronized before the next layer can begin — an AllReduce across all TP-participating GPUs, once per layer, every single forward pass. For a 70B model at TP=4, that's roughly 160 AllReduces per token generated. Each AllReduce's traffic scales with 2 × (TP_degree − 1) / TP_degree × layer_output_size — at TP=4 for a 70B model, on the order of 1.5GB of AllReduce traffic per forward pass. This is why TP requires NVLink and is strictly an intra-node technique: at NVLink's ~900GB/s intra-node bandwidth, that traffic costs microseconds and is negligible against the ~10–40ms decode step it rides alongside; at PCIe's ~64GB/s, the same AllReduce would take longer than the compute it's synchronizing, making TP net-negative. Higher TP degree buys lower per-request latency (more GPUs sharing each layer's work) at the cost of more communication overhead and lower throughput per GPU — production deployments of 70B-class models on NVLink-connected A100s or H100s typically land at TP=2 or TP=4; past TP=8, communication overhead routinely exceeds the latency benefit.

    Pipeline parallelism (PP) — splitting across layers. Different contiguous blocks of transformer layers are assigned to different GPUs — layers 1–20 on GPU 0, 21–40 on GPU 1, and so on for an 80-layer model across 4 GPUs. The forward pass flows sequentially: GPU 0 computes its block, hands activations to GPU 1 over the network, GPU 1 computes its block, and so forth. While GPU 3 is computing on micro-batch 1, GPUs 0–2 sit idle unless the batch is split into micro-batches that keep the pipeline full — the classic pipeline bubble, with bubble fraction (PP_degree − 1) / (PP_degree + micro_batches_per_batch − 1). Because only activations cross the wire between adjacent stages — not a full-layer AllReduce — PP's communication volume is far lower than TP's, which is why PP is the technique that can cross node boundaries over InfiniBand (~200GB/s bidirectional), where TP cannot.

    Model TP PP Nodes GPUs total
    7B 1 1 1 1× A100 80GB
    70B 2 1 1 2× A100 80GB
    70B, high-throughput 4 1 1 4× A100 80GB
    405B 8 2 2 16× A100 80GB

    The right configuration balances three constraints simultaneously: VRAM capacity (weights + max KV cache budget + activations + framework overhead must fit within total VRAM across all TP-sharded GPUs — the same budget arithmetic as the Scale Estimation section above, just re-run per candidate TP degree), TTFT SLO (higher TP lowers per-request latency), and throughput (more total GPUs raises aggregate throughput, but AllReduce overhead grows with TP degree, eating into per-GPU efficiency). A configuration that fits VRAM but ignores the TTFT/throughput tradeoff is incomplete — always check all three before committing to a topology.

    Concept 4 — Model routing, quantization, and the quality-cost-latency triad¶

    A production system routes each request to the cheapest model tier that still clears its quality bar, because serving every request on the largest available model is not a viable cost structure at scale.

    Tier Example TTFT Throughput Cost per 1M tokens
    Tier 1 — fast, small 8B int8 < 150ms > 200 tok/s/GPU $0.05–0.20
    Tier 2 — balanced, mid 70B int8 < 500ms 30–60 tok/s/GPU $0.50–2.00
    Tier 3 — quality, large 405B fp8 or MoE 1–3s 5–15 tok/s/GPU $5–15

    Routing. A lightweight classifier (< 5ms, CPU-resident — see Multi-Model Serving & Routing for the full classifier-design tradeoff space) evaluates input complexity, the caller's declared SLO class, and request type, and is calibrated empirically to land at roughly the 75/20/5 tier split this chapter's Capacity Planning table assumes. The classifier's cost must be strictly lower than the compute it's deciding whether to spend — using the large model to decide whether to use the large model defeats the entire exercise.

    Quantization is the other half of this lever, and its effect is not merely "smaller model, same behavior at lower fidelity" — because decode is memory-bandwidth-bound (see GPU Fundamentals), shrinking the model directly increases tokens/second, independent of any other change:

    • Int8 (AWQ/GPTQ): 50% memory reduction, < 1% quality degradation on standard benchmarks. Standard for Tier 1/2 — the freed VRAM goes straight into more concurrent KV cache, doubling effective concurrency per GPU.
    • Int4 (GPTQ): 75% memory reduction, 2–5% degradation — acceptable for Tier 1 on simple tasks, and enough to fit a 70B model on 2 GPUs instead of 4.
    • FP8 (H100/H200 native, Transformer Engine): 50% memory reduction with < 0.5% degradation, applied dynamically at inference with no offline calibration step — the current default for new H100 deployments, per Quantization & Compression.

    The quality hit from quantization is not uniform across task types — a model showing < 1% degradation on MMLU can show 5% degradation on the specific flavor of code generation a given product actually serves. Calibrate on production-representative data and evaluate on task-specific benchmarks (see LLM Evaluation Architecture) before shipping a quantized tier — perplexity alone hides exactly this failure mode, because quantization error concentrates in rare, high-information tokens that a perplexity average over common words doesn't surface.

    Speculative decoding is the latency lever layered on top, covered at full mechanical depth in Speculative Decoding at Scale: a small draft model (3B–7B) proposes k≈5 candidate tokens per round; the main model verifies all k in a single parallel forward pass — cheap, because verifying k tokens costs about the same as generating one. When 3–4 of 5 proposed tokens are accepted on average, the number of expensive main-model forward passes needed per output token drops proportionally, yielding 2–3× latency reduction for typical 50–500 token conversational outputs with zero change to output quality — accepted tokens are, by construction, identical to what the main model would have generated unassisted. It requires a draft model from the same family (same tokenizer, similar distribution) to hit high acceptance rates, and its acceptance rate must be monitored per request type in production: below ~70%, the verification overhead costs more than the skipped forward passes save, and speculative decoding should be disabled for that traffic.

    Concept 5 — SLO enforcement, autoscaling, and cold-start management¶

    Why this is harder than standard autoscaling. A stateless web service can spin up a new container in seconds. GPU capacity cannot: cloud-provider GPU instances take 5–15 minutes to provision, and loading a 140GB model from storage into VRAM takes 2–10 minutes even at NVLink-class bandwidth. Total cold start: 7–25 minutes — by the time freshly provisioned capacity comes online, the traffic spike that triggered the scale-out has already breached every TTFT SLO it was meant to protect.

    The warm pool pattern. A configurable number of GPU instances are kept in standby with the model already loaded but not serving traffic — consuming GPU memory and cost, but able to join the routing table within 30–60 seconds instead of 7–25 minutes. Pool size is an explicit cost-vs-responsiveness decision, not a default: at ~$0.30/GPU-hour, a 10-H100 warm pool costs roughly $3,000/day for capacity that may sit idle. The right size is set by the expected spike magnitude (P99 peak vs. average traffic), the cost of an SLO breach (churn, contractual penalty), and the current traffic trend (a product launch warrants a larger pool than steady state).

    SLO classes.

    SLO class TTFT target Queue timeout Tier routing
    streaming_user < 500ms reject after 300ms queued Tier 1 or 2
    batch_quality < 10s wait up to 5 min Tier 2 or 3
    async_bulk < 60s wait up to 30 min Tier 1, cheapest

    The scheduler enforces queue timeouts directly: a streaming_user request queued past 300ms will breach its 500ms TTFT even if it's admitted to the batch the instant it times out — the correct response is a 503, letting the caller retry or degrade, not a late 200 that silently blows the SLO it promised.

    Traffic shedding under overload. P95 TTFT is monitored continuously on a rolling 60-second window. Crossing 80% of the SLO threshold triggers warm-pool activation and begins shedding async_bulk traffic to a slower or cheaper tier; crossing 100% pages on-call. This is backpressure applied to LLM serving: protect the SLO classes that matter by shedding the ones that can tolerate delay, rather than letting overload degrade every tier uniformly.

    Data Flow¶

    sequenceDiagram
    participant C as Caller
    participant R as Router
    participant S as Scheduler
    participant KV as KV Page Allocator
    participant PC as Prefix Cache
    participant W as Worker (Tier 2 TP group)

    C->>R: Request, streaming, Tier 2 hint
    R->>S: Assigned SLO class + tier
    S->>KV: Request initial page allocation
    KV-->>S: Pages granted, VRAM headroom OK
    S->>PC: Hash prompt prefix, check cache
    PC-->>S: HIT - 500 tokens of system prompt already cached
    S->>W: Admit to active batch, prefill only new tokens
    loop Each decode iteration
        W-->>S: One token generated
        S-->>C: Stream token immediately
    end
    W-->>S: EOS token generated
    S->>KV: Free this request's pages
    S->>S: Admit next queued request into freed slot

    The detail worth dwelling on: KV page allocation and the prefix-cache check both happen before admission to the active batch, not after — a request is never placed into the decode loop until the scheduler has confirmed it has somewhere to put its growing KV state. Deferring that check would mean discovering an out-of-memory condition mid-generation, which is a far worse failure than a request waiting an extra iteration in the queue.

    Retrieval Layer¶

    Not applicable in the traditional sense — this system is the foundational layer that retrieval systems like RAG System and the Enterprise RAG Platform sit on top of; it has no retrieval concept of its own. The one retrieval-adjacent mechanism worth naming explicitly is the prefix cache lookup described in Concept 2: a hash-based, exact-match retrieval operation over cached KV state, conceptually identical in shape to a cache lookup in any other system even though the thing being retrieved (attention key/value tensors) is specific to this domain.

    Agent Layer¶

    Not applicable — this system serves individual, independent inference requests and has no agentic loop, no tool use, and no multi-step reasoning of its own. It is a dependency that agentic systems call into, potentially many times per user-visible turn (see the tool-fan-out multiplier discussed in ChatGPT and the agentic capacity-planning worked example in GPU Sizing & Capacity Planning). The distinction matters for capacity planning: an agentic caller can turn one user action into 5–15 separate calls into this system, each with its own TTFT and its own KV cache footprint, and this system has no visibility into that fan-out — it only ever sees independent requests.

    Model Layer¶

    Four sub-layers operate within this system itself, distinct from the "which foundation model" question every other case study in this section answers:

    1. Router classifier — the < 5ms, CPU-resident model from Concept 4 that assigns SLO class and tier.
    2. Draft model — the 3B–7B speculative-decoding proposer from Concept 4, co-located with its corresponding main model and sharing its deployment lifecycle.
    3. Primary serving models — one deployment per tier, each running under the quantization scheme calibrated for that tier (int8/int4 via AWQ or GPTQ, or FP8 dynamic quantization on H100-class hardware).
    4. Quantization as a first-class deployment artifact, not a one-time preprocessing step — the calibration dataset, the target precision, and the task-specific quality validation are all versioned alongside the model weights themselves, because re-quantizing without re-validating is how silent, task-specific quality regressions ship (see Quantization & Compression).

    Observability Layer¶

    • TTFT P50/P95/P99, per SLO class — the primary user-facing metric; alarms fire at 80% and 100% of the class's SLO threshold, mirroring the shedding logic in Concept 5.
    • Token generation throughput per GPU — low throughput at otherwise-healthy utilization signals the batch is too small or the workload has become unexpectedly memory-bound (e.g., an unusually large fraction of long-context requests).
    • KV cache VRAM utilization per node — target > 85%; below 70% means the scheduler is admitting too conservatively and leaving concurrency on the table; above 95% risks eviction-driven latency spikes.
    • Prefix cache hit rate — a sudden drop on a workload known to share system prompts is the first signal to check before assuming a broader regression; it usually means the cache capacity or TTL was tuned too aggressively, not that traffic patterns genuinely changed.
    • GPU compute utilization, tracked separately from KV VRAM utilization — a system can be memory-comfortable and still compute-starved, or vice versa, and conflating the two hides which constraint actually binds (see GPU Fundamentals).
    • Queue depth per tier — the leading indicator that real demand has exceeded provisioned capacity, ideally caught here before it becomes a TTFT breach.
    • Batch size distribution (histogram, not just an average) — a distribution clustered at small batch sizes despite plenty of queued traffic indicates continuous batching isn't packing well, independent of whether raw throughput looks acceptable.
    • Speculative decoding acceptance rate, per request type — tracked separately by task category because acceptance rate (and therefore whether speculative decoding is net-positive) varies sharply between predictable, templated outputs and high-entropy generation.

    Security Layer¶

    This system is largely security-transparent by design: it serves prompts as opaque token sequences and returns generated tokens, with no opinion on their semantic content. Three concerns are specific to this layer rather than the application layer above it:

    • Resource-exhaustion protection: content-level abuse detection belongs at the application layer, but this system enforces per-caller token limits and rate limits directly, because an unbounded prompt or output length is a denial-of-wallet and denial-of-service vector against shared GPU capacity regardless of what the content says — see the long-context and agentic resource-exhaustion discussion in GPU Sizing & Capacity Planning.
    • Tenant isolation in multi-tenant deployments: prefix cache pages must only be shared between requests from the same tenant. A prefix cache that shared pages across tenants would let one tenant's cache-hit timing (or, in a worse bug, cache contents) leak information about another tenant's traffic — the same isolation principle Enterprise RAG Platform applies to retrieval indexes applies here to KV cache pages.
    • Model weight integrity: weights pulled from a model registry must be cryptographically verified before being loaded into a worker, closing off model-poisoning as a supply-chain vector — a compromised or substituted weight file is a far more severe and far less detectable failure than a bad prompt.

    The single largest lever, by a wide margin, is routing accuracy: because Tier 3 costs roughly 20–30× what Tier 1 costs per token (per the tier table in Concept 4), a routing classifier that leaks even a few extra percentage points of traffic into Tier 3 has an outsized effect on total spend — precisely the dynamic ChatGPT's cost model quantifies for its own fast/reasoning split, and the same argument Cost Engineering makes generally: fix the routing/caching levers before reaching for hardware upgrades or vendor discounts.

    Failure Handling¶

    Failure Degradation strategy
    KV cache pool exhausted, new request needs pages Reject at admission with a clear "capacity" error rather than evicting an in-flight request — an admitted, mid-generation request that gets evicted pays a full re-prefill penalty and a much worse experience than a request that never started
    A tier's GPU pool fully saturated Shed lower-priority (async_bulk, then batch_quality) traffic first; streaming_user traffic is protected last and hardest
    Cold-start scale-out too slow for a real spike Warm pool absorbs the first minutes of the spike; if the warm pool is also exhausted, shed traffic rather than let TTFT silently blow through SLO
    Speculative decoding acceptance rate collapses (e.g., after a model or draft-model update) Auto-disable speculative decoding for the affected request type once measured acceptance rate on production traffic drops below ~70%, falling back to standard decode rather than paying verification overhead for no benefit
    Prefix cache eviction under memory pressure Falls back to full prefill for the affected requests — a TTFT regression, not a correctness failure; monitor prefix cache hit rate to catch this before it's mistaken for a broader load regression
    A specific GPU or node fails mid-batch In-flight requests on that node are lost and must be retried from the caller side (this system does not currently checkpoint in-flight generation); the scheduler routes future requests away from the failed node immediately via health checks
    Quantized tier shows a task-specific quality regression post-deployment Roll back to the previous precision for the affected tier while re-calibrating quantization on production-representative data — do not attempt to "fix forward" a quality regression that's already reaching users

    Tradeoff Analysis¶

    flowchart TD
    Q1{"Batch size vs TTFT?"} -->|"Larger batch"| THROUGHPUT["Higher throughput\nWorse TTFT for late-queued requests"]
    Q1 -->|"Smaller batch"| LATENCY["Better TTFT\nLower aggregate throughput"]
    Q2{"TP degree?"} -->|"Higher TP"| LOWLAT["Lower per-request latency\nMore AllReduce overhead, lower throughput/GPU"]
    Q2 -->|"Lower TP"| HIGHTPUT["Higher throughput/GPU\nHigher per-request latency"]
    Q3{"Quantization aggressiveness?"} -->|"INT4"| CHEAP["75% memory reduction\n2-5% quality loss - Tier 1 only"]
    Q3 -->|"FP8/INT8"| BALANCED["50% memory reduction\nunder 1% quality loss - Tier 2/3 safe"]

    Five tradeoffs recur across every design decision in this system:

    1. Batch size vs. TTFT. Larger batches amortize the fixed weight-read cost across more requests, raising throughput, but requests that queue while a large batch fills pay for it in TTFT. The scheduler tunes batching aggressiveness per SLO class rather than globally — streaming_user traffic runs smaller, more responsive batches; async_bulk traffic runs at or near the KV cache ceiling.
    2. TP degree vs. throughput-per-GPU. More TP GPUs lowers latency by splitting each layer's work further, but AllReduce cost climbs with TP degree; past TP=8, communication overhead routinely dominates, making additional GPUs a net loss for throughput even as latency keeps improving.
    3. INT4 vs. INT8/FP8 quantization. INT4's 75% memory reduction is attractive but its 2–5% quality loss is workload-dependent and sometimes concentrated exactly where a product's task distribution is most sensitive — appropriate for Tier 1 simple tasks, not for code generation or multi-step reasoning where the loss is measured, not assumed.
    4. KV page size. Smaller pages minimize internal fragmentation (at most one partially-filled page's waste per request) but add per-request page-table bookkeeping; larger pages simplify management but waste more per sequence's tail. 16–32 tokens is the practical middle production systems land on.
    5. Prefix cache size. A larger reservation raises hit rate but shrinks the KV budget available for active generation, reducing concurrency; a smaller reservation protects concurrency but misses on frequently reused prefixes. The 20% split used in this chapter's Scale Estimation is a starting point to be tuned against measured hit rate, not a fixed constant.

    Interview Discussion¶

    This case study is one of the few in this book that separates candidates who have actually built inference infrastructure from candidates who have only ever consumed an inference API. It specifically tests three things no application-layer case study reaches: (1) whether the candidate can explain why naive batching fails for autoregressive generation — the variable-output-length mechanism, not just the word "batching" — and state the before/after GPU utilization numbers (30–45% vs. 70–90%) that make the failure concrete rather than hand-wavy; (2) whether the candidate understands the KV cache well enough to describe PagedAttention as a mechanism (fixed-size pages, a per-request page table, non-contiguous physical allocation, a custom attention kernel to read it) rather than a name to drop; (3) whether the candidate can distinguish tensor parallelism from pipeline parallelism by their communication pattern and interconnect requirement — specifically, that TP needs NVLink because it does an AllReduce every layer, while PP tolerates InfiniBand because it only exchanges activations at stage boundaries.

    Weak answer: "I'd use vLLM and scale horizontally." That names the right tool but demonstrates no architectural depth — it is indistinguishable from an answer given by someone who has read one blog post about vLLM.

    Strong answer: explains why vLLM's approach solves the specific memory-fragmentation problem that makes naive VRAM management unacceptable at production scale, and can walk through the continuous batching loop — what happens at each decode iteration, how eviction and admission interleave — without prompting.

    Staff-level probe: "Your TTFT P95 is 2.1 seconds against a 1-second SLO during peak hours. GPU utilization is 92%, KV VRAM utilization is 89%, queue depth is 150. What's happening, and how do you fix it?" This tests whether the candidate reads the three numbers together rather than treating them as independent: 92% GPU utilization plus 89% KV VRAM utilization plus a 150-deep queue describes a system genuinely at capacity, not misconfigured — there is no free lever left in the current fleet. Immediate mitigation is shedding async_bulk traffic to protect the streaming_user SLO; medium-term is activating the warm pool; the investigation track asks whether batch composition has skewed toward unusually long-context requests consuming disproportionate KV VRAM and compute, whether quantization settings are still optimal for current traffic mix, whether speculative decoding is helping or now adding net overhead at this saturation level, and whether the routing classifier needs to shift more traffic toward Tier 1.

    Staff-level probe: "You want to add support for 1M-token context window requests. What breaks in the current architecture, and what changes?" Three things break, in order of severity. First, KV cache memory: a single 1M-token request at 70B fp16 costs ~2.6GB of KV cache alone — enough to collapse batch size toward 1 for that request class, since it consumes what would otherwise serve dozens of normal-length requests. Second, attention computation: standard attention materializes an O(T²) attention matrix — at 1M tokens that's a 1M×1M matrix, ~4TB at fp32 — requiring FlashAttention-3-class kernels or ring attention that never materialize the full matrix. Third, sequence parallelism: at 1M tokens, a single sequence's KV tensors may not fit on one GPU's VRAM budget even after every other optimization, requiring the sequence itself to be sharded across GPUs (SP) — meaning long-context requests need an entirely separate serving pool with SP enabled, routed apart from standard-length traffic rather than folded into the existing tiers.
