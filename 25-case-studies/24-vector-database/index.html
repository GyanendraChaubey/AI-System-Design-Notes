    Vector Database — System Design Case Study¶

    Every other chapter in Case Studies is either an AI-powered product — ChatGPT, Claude, an agent that plans and calls tools — or a serving and pipeline system built to feed one, like LLM Inference System or RAG System. This chapter is the only one in the book that is purely a database: a storage and query engine with no model in its hot path, no prompt, no generation step. RAG System is this chapter's primary consumer — every time that chapter says "dense ANN retrieval" or "vector index," it means the system described here, and it deliberately does not re-derive index internals, sharding, or write-path mechanics; it treats this chapter's system as an infrastructure dependency the same way LLM Inference System is a dependency of every generation step in this book. AI Recommendation System and AI Search Engine are two more consumers with different access patterns — item-embedding retrieval at extreme QPS and query-time dense retrieval, respectively — that this chapter's design has to serve simultaneously. A candidate asked to "design a vector database" in an interview is being tested on systems engineering knowledge that has nothing to do with LLMs: index data structures, distributed query execution, write-path consistency, storage tiering, and the fundamental theorem of approximate nearest-neighbor search.

    That theorem is the central fact that shapes every decision in this chapter: vector similarity search is not a solved problem the way relational lookup is. An exact nearest-neighbor search over 1 billion 768-dimensional float32 vectors costs O(N × D) per query — for N = 1,000,000,000 and D = 768, a single query performs roughly 768 billion multiply-accumulate operations. At 10 GFLOPS per CPU core, that is about 77 seconds — for one query. No B-tree equivalent exists, because a B-tree's speedup comes from spatial locality (values near each other in sort order live near each other on disk), and Euclidean or cosine distance in 768 dimensions has no such locality: in high-dimensional space, almost every pair of points is nearly equidistant from a third, so no recursive partition of the space reliably narrows the search the way a range partition does for scalar keys. Every production vector database therefore substitutes an approximate nearest-neighbor (ANN) algorithm and manages the resulting recall-versus-latency tradeoff explicitly, rather than sidestepping it. This chapter covers the three dominant ANN algorithms at mechanism depth, how they compose into a distributed system that serves billions of vectors at millisecond latency, and the write-path and storage-tiering decisions that determine whether that system is affordable. Indexing Algorithms is the reference chapter for the full algorithm catalog (including DiskANN) and exhaustive parameter-tuning tables; this chapter assembles those algorithms into one coherent, capacity-planned system and reasons about the tradeoffs at the level a system-design interview actually probes.

    Requirements¶

    Functional

    • Insert, update, and delete vectors with associated structured metadata; support multiple distance metrics (cosine, L2 Euclidean, dot product) selectable per collection.
    • Serve approximate nearest-neighbor queries with an optional metadata filter expression (boolean combinations of equality, range, and set-membership predicates).
    • Expose a synchronous query API for low-latency top-K lookups and an asynchronous bulk-ingestion API for high-throughput loading.
    • Support horizontal scale-out to 1B+ vectors by adding shard nodes, without downtime and without requiring a full-corpus re-index.

    Non-functional

    • Query latency: P50 < 10ms, P99 < 50ms at 1,000 QPS sustained.
    • Recall@10 > 95% for unfiltered queries; the system must expose recall as a tunable, measured quantity, not an incidental byproduct of default settings.
    • Insert throughput > 10,000 vectors/second sustained, without degrading concurrent query latency beyond the P99 budget.
    • Availability: 99.9% (three nines) per shard group, achieved through replication rather than any single node being individually reliable.

    Explicitly out of scope: training or fine-tuning the embedding model that produces the vectors this system stores — that is Embedding Models's concern, and this chapter treats incoming vectors as opaque float arrays with a declared dimensionality and metric. The RAG pipeline that sits above the retrieval layer — chunking, query transformation, reranking, context assembly, generation — is RAG System's concern; this chapter's API returns (id, distance, metadata) tuples and has no opinion on what the caller does with them. Graph traversal, relational joins across collections, and full-text/BM25 search are separate systems this database may sit alongside (as in RAG System's hybrid retrieval) but does not itself implement.

    Capacity Planning¶

    Sized for a 1B-vector collection at 768 dimensions — a representative large-scale embedding size (Embedding Models covers the 384–3072-dimension range in production use) — using the tiered-storage architecture developed in Concept 5 below:

    Tier Fraction of corpus Vector count Index / quantization Footprint
    Hot 10% 100M HNSW or flat, int8 scalar quantization (SQ8) ~75GB RAM
    Warm 50% 500M Quantized HNSW, mmap'd, IVF-PQ (M=96) ~47GB NVMe SSD
    Cold 40% 400M IVF-PQ (M=96) ~38GB on object storage

    A vector's tier is a function of recency and query frequency, not a permanent assignment — see Concept 5 for the promotion/demotion mechanism. The hot tier is the only one sized against a hard RAM budget: at 20 shards, each hot-tier shard holds 5M vectors at ~240MB — small enough that a single shard node has enormous headroom for OS page cache, in-flight query state, and the growing write segment described in Concept 4 below.

    Supporting infrastructure: a coordinator pool of 3 stateless nodes (horizontally scalable independent of shard count), a config store (etcd or ZooKeeper) of 3 nodes holding the shard routing table, and a metadata index (PostgreSQL) holding scalar fields used by filter predicates, sized at roughly 200 bytes/vector × 1B ≈ 200GB — frequently the most underestimated line item in capacity planning, because it is small per-vector but multiplies by the full corpus, not by whatever fraction happens to be hot.

    Scale Estimation¶

    At the target of 1,000 QPS sustained with P99 < 50ms, sharding the hot tier across 20 shards puts 50 QPS on each shard. An HNSW index at 5M vectors/shard with ef_search = 64 answers a query in roughly 2ms on a single thread — Concept 1 below develops the ef_search tuning curve; at 50 QPS/shard, that workload is comfortably handled by 4 CPU cores per shard node with room to spare. With SIMD-optimized distance computation (AVX-512), a modern core sustains 500–2,000 QPS on D = 768 HNSW search, so raw compute is not the binding constraint at this scale — the fan-out and merge overhead described in Concept 2, and the tail latency of the single slowest shard, dominate the P99 budget instead.

    On the write side, 10,000 vectors/second sustained across 20 shards is 500 vectors/second/shard into each shard's in-memory growing segment (Concept 4) — well within HNSW's per-insert cost of a few hundred microseconds at this shard size, leaving ingestion CPU-bound only during periodic segment flush and compaction, not during steady-state writes.

    The write path and read path are deliberately decoupled: writes land in a durable queue and are absorbed into per-shard growing segments asynchronously, while reads fan out to whichever mix of growing and sealed segments each shard currently holds. This is the same decoupling RAG System's ingestion pipeline uses for its own reasons (bounded freshness SLO without blocking query serving) — here it exists because ANN indexes are fundamentally bad at absorbing high-throughput random writes, which Concept 4 below explains in mechanism detail.

    Detailed Design¶

    Concept 1 — ANN index structures: HNSW, IVF-PQ, and the recall-latency surface¶

    The three dominant ANN algorithm families make categorically different tradeoffs, and the choice between them is the single highest-leverage decision in the system. Indexing Algorithms covers the full mechanism depth, including DiskANN and the recall-tuning benchmark tables; this section covers the mechanism at the depth needed to reason about the tradeoff, not to re-derive it.

    HNSW (Hierarchical Navigable Small World). HNSW builds a multi-layer proximity graph. The top layer contains a sparse subset of nodes connected by long-range edges; each successive layer down contains more nodes with shorter-range edges; the bottom layer, layer 0, contains all N vectors. A new vector's layer assignment is drawn from a geometric distribution — the probability of appearing in layer L is e^(-L / mL) — so most vectors live only in layer 0, a few reach layer 1, and progressively fewer reach higher layers. At insertion, the new node is connected to its M nearest neighbors at each layer it belongs to, found via a greedy search from the fixed entry point.

    Query execution enters at the single entry-point node in the top layer and performs a greedy walk: at each step, move to whichever neighbor most reduces distance to the query. When no neighbor is closer, descend one layer and repeat. At layer 0, the search widens to explore ef_search candidates via a priority queue — the beam width — before returning the top-K. Three parameters govern the resulting recall/latency/memory point:

    Parameter Effect on recall Effect on latency Effect on memory
    M — edges per node Higher M → higher recall Higher M → higher build latency, small increase in query latency Higher M → more memory, M × 4 bytes × N for edges
    ef_construction Higher → better-connected graph → higher recall No query-time effect No effect
    ef_search Higher → higher recall Higher → higher latency, roughly linearly No effect

    Memory is dominated by the raw vectors plus bidirectional edge storage: D × 4 bytes per vector for float32, plus roughly 2 × M × 4 bytes for edges (bidirectional, stored as node IDs). At D = 768, M = 16: 3,072 + 128 ≈ 3.2KB per vector, so 100M vectors need ~320GB of RAM. HNSW is fundamentally a RAM-resident index — a disk-backed HNSW pays 50–200× higher query latency from random I/O during graph traversal, because each hop touches a different, unpredictable region of the graph. HNSW is the right choice for memory-resident collections up to roughly 100–200M vectors per node where recall ≥ 95% is required and inserts happen continuously — it is the only one of the three families with native O(log N) online insert.

    IVF-PQ (Inverted File + Product Quantization). Two orthogonal ideas combine here. IVF clusters the corpus into K centroids via k-means (K typically 1,024–65,536) and stores each vector in its nearest centroid's inverted list. A query examines only the nprobe nearest centroids and scans the vectors in those lists — at K = 4,096, nprobe = 32, that is 32 / 4,096 ≈ 0.78% of the corpus. The failure mode is direct: if a query's true nearest neighbors are spread across more than nprobe clusters — common with skewed or multi-modal data — they are silently missed and recall degrades, with no error signal.

    PQ compresses each vector for cheap approximate distance computation: split the D-dimensional vector into M subvectors of D/M dimensions, run k-means with 256 centroids independently per subvector position, and store each subvector as a single byte — the index of its nearest centroid. A D × 4-byte float32 vector compresses to M bytes: 32× compression at M = D/8. At query time, precompute a (D/M) × 256 lookup table of distances from the query to every centroid at every subvector position; the distance to any compressed vector is then M table lookups and additions instead of D multiplications — an order of magnitude cheaper per candidate, and the reason IVF-PQ scans are so fast even without narrowing to nprobe clusters.

    PQ compression is lossy in a way nprobe tuning cannot fix: at the common choice M = D/8, expect 5–15% recall degradation versus full-precision IVF, because the compressed vector is itself an approximation independent of which clusters were searched. Recall is recoverable by increasing M (larger codes, less compression) or by using asymmetric quantization — keeping the query in float32 and compressing only the stored vectors, which this lookup-table scheme already does. At D = 768, M = 96, K = 4,096, 1B vectors need roughly 100GB — versus 3TB for float32 HNSW at the same scale — which is why FAISS and most billion-scale production systems default to IVF-PQ. Its memory-access pattern (scan an inverted list, table-lookup a distance) also maps cleanly onto GPU execution: FAISS-GPU sustains 10,000+ QPS on IVF-PQ indexes that fit in VRAM, a throughput HNSW's random graph traversal cannot approach on GPU hardware — see GPU Architecture for ML for why random-access, branchy traversal is a poor fit for SIMT execution.

    ScaNN. Google's production ANN system optimizes for anisotropic — direction-sensitive — quantization error: rather than minimizing average reconstruction error the way standard PQ does, ScaNN's learned quantization minimizes the error specifically in the component of each vector that determines its rank among the top-K candidates. Layered with an optional IVF-style tree partition, ScaNN consistently achieves higher recall at equal QPS than HNSW or IVF-PQ on ann-benchmarks.com, especially at the 384–1,536-dimension range where the anisotropic advantage is largest. The cost is integration complexity — ScaNN is a library to operate, not a packaged database, making it the right choice for teams willing to build a custom serving layer around it rather than adopt an off-the-shelf vector database.

    Concept 2 — Distributed sharding and query fan-out¶

    At billion-vector scale, no single machine holds the full index; the distributed architecture is what separates a vector database from an in-process library like FAISS. The corpus is partitioned across S shards, each holding N/S vectors and an independent ANN index, with two competing partitioning schemes.

    Random or hash sharding distributes vectors uniformly across all shards by ID hash. Every query fans out to all S shards — simple, predictable per-shard load, but O(S) fan-out on every query regardless of filter. Metadata-partitioned sharding colocates vectors sharing a metadata value — tenant, category — on the same shard or shards. A filtered query scoped to one partition touches only that shard, O(1) fan-out, at the cost of hot-partition risk: a single tenant generating a disproportionate share of traffic concentrates load on whichever shard holds them. The mitigation is spreading a large tenant across multiple shards rather than treating shard assignment as a single hash bucket per tenant — the same "whale tenant" problem Enterprise RAG Platform solves with dedicated infrastructure at the tenant-isolation layer above this one.

    Fan-out, over-fetch, and merge. A query arrives at a stateless coordinator, which fans it out to all relevant shards in parallel. Each shard returns its local top-K_shard candidates, where K_shard must exceed the final K — with 10 shards and a final K = 10, the globally 10th-best vector might rank 8th on its own shard; if each shard returns only 5 candidates, that vector never reaches the coordinator. The rule of thumb is K_shard = max(3 × K_final, 50): retrieving 50 candidates per shard, merging across all shards, and selecting the global top-10 from the resulting 500 candidates gives near-exact global top-K. Fan-out latency is bounded by the slowest shard's P99, not the sum — with S = 20 shards at 5ms P99 each, the coordinator's P99 is ~5ms plus a submillisecond network round-trip for co-located shards and a negligible O(S × K_shard × log(S × K_shard)) merge.

    Replication. Each shard has R replicas for fault tolerance and read throughput; reads load-balance round-robin across replicas, while writes go to a primary and propagate to R - 1 followers either synchronously (strong consistency, higher write latency) or asynchronously (eventual consistency, lower write latency). For a read-heavy search index — this system's primary access pattern — eventual consistency is the right default: a vector appearing in results 1–5 seconds after insert is not user-visible in a RAG or search context. A workload where a just-deleted or just-purchased item must never reappear (e-commerce inventory search is the canonical case) needs synchronous replication instead, at the cost of write latency.

    Coordinator design. The coordinator pool is stateless and horizontally scalable independent of shard count: any coordinator instance can serve any query, reading the shard routing table from the config store (ZooKeeper or etcd) rather than holding routing state itself. Scaling read throughput is adding coordinator replicas behind a load balancer with no data migration — the state that would require migration lives entirely in the shard pool and the config store.

    Concept 3 — Metadata filtering: the recall degradation problem¶

    This is the concept most candidates miss entirely, and it determines whether the database is usable in production — nearly every real query carries a metadata filter, and a system that silently returns wrong results under a filter is worse than one that is simply slow. The setup: a 1B-vector collection with metadata like {tenant_id, category, created_at, language}, and a query "top-10 similar to q WHERE tenant_id = 'acme' AND language = 'en' AND created_at > '2025-01-01'." If 99% of vectors fail that filter, the effective search space is 10M vectors — but the ANN index was built over all 1B, and the index structure has no inherent awareness of which nodes will later be excluded.

    Post-filter runs ANN search over the full index ignoring the filter, retrieves K × oversample candidates, then applies the filter and returns the survivors. To expect K results after filtering at selectivity p (the fraction of the collection passing the filter), retrieve K / p candidates before filtering: at K = 10, p = 0.001, that is 10,000 candidates — an ef_search so high on HNSW that the traversal visits most of the graph, and latency explodes toward the exact-search cost this whole system exists to avoid. Post-filter is correct only when the filter is weak, p > 10%; it is also what naive implementations do by default, because it requires zero changes to the ANN index.

    Pre-filter applies the metadata predicate first via a secondary index on the metadata store, collects the surviving vector IDs, and runs an exact nearest-neighbor scan over only that ID set — O(|valid set| × D). At p = 0.001, |valid set| = 1M, and 1M × 768 ≈ 768M operations per query is roughly 77ms at 10 GFLOPS/core: acceptable for some use cases. At p = 0.1, |valid set| = 100M, and the same math gives roughly 7.7 seconds — completely unacceptable. Pre-filter works only when the filter is very selective, p < 0.1%; above that it bypasses the ANN index entirely and the investment in HNSW or IVF-PQ buys nothing.

    Filtered-graph ANN is the general solution: store metadata per node in the index and, during graph traversal, skip nodes that fail the filter from the result set while still allowing them to serve as navigation waypoints on the way to nodes that pass. The failure mode is a selective filter trapping the greedy walk in a graph region where all nearby nodes are excluded, because the graph's edges were optimized for the full distribution, not the filtered subset — the walk cannot "see" a valid candidate that requires routing through a locally dense but entirely filtered-out neighborhood. The fix is either raising ef_search to increase the odds of encountering a valid node, or maintaining per-partition subindexes: a separate, smaller HNSW built over only the vectors matching each common metadata value. A filtered query against a common partition — one tenant, one language — searches that partition's subindex directly, with exact recall relative to the partition and no filtering approximation at all. At 1,000 tenants averaging 1M vectors each, 1,000 subindexes at ~3.2GB each is 3.2TB — not memory-resident — so subindexes are memory-mapped and page in from NVMe on demand: hot tenants stay resident in OS page cache, cold tenants pay 2–5ms of NVMe read latency (50–100ms on spinning disk) on first access.

    Strategy Works well when Fails when Mechanism cost
    Post-filter Filter selectivity p > 10% p small — most oversampled candidates get discarded K/p candidates fetched via normal ANN, then filtered
    Pre-filter p < 0.1% p moderate-to-large — exact scan over the valid set becomes the bottleneck O(\|valid set\| × D) exact scan, bypasses the ANN index
    Filtered-graph ANN p between roughly 0.1% and 10%, or any p with per-partition subindexes Extremely selective filters without a dedicated subindex — greedy walk can get trapped Graph-aware skip during traversal; subindex avoids the trap entirely

    No single strategy is correct across all selectivities, which is why production systems — Weaviate, Qdrant, Pinecone — estimate filter selectivity per query (via cached counts or a lightweight statistics table) and route adaptively between the three strategies rather than committing to one.

    Concept 4 — Write path: inserts, deletes, and the mutable index problem¶

    Large ANN indexes are not designed for high write throughput, and the write path is the weakest link in most vector database architectures. An HNSW insert is O(log N) but the constant is large — finding the new node's neighbors requires a greedy search through the existing graph — and it competes with concurrent queries for the same graph structure via node-level readers-writer locks; a high write rate measurably degrades query latency even though HNSW is the one algorithm of the three that natively supports online insert. IVF-PQ insert is cheaper per vector — assign to the nearest of K centroids, append to that list — but centroids drift out of balance as the true data distribution shifts, and an overloaded inverted list slows every query that touches it; recovering requires a full offline re-cluster, not an incremental fix. Deletes are worse for both: HNSW physically removing a node can disconnect the graph, so deletes are lazy tombstones — excluded from results but left in place for navigation — and tombstones accumulate, adding traversal overhead until a periodic, offline compaction rebuilds the graph without them.

    The LSM-inspired solution, used by Milvus and Weaviate, borrows the log-structured-merge pattern from write-optimized storage engines and applies it to ANN indexes. A growing segment is a small, in-memory, mutable index — often a flat exact-search structure below a size threshold, an in-memory HNSW above it — that absorbs all inserts and deletes for that shard. It stays bounded (a common threshold is around 200K vectors) for fast writes and acceptable recall even at small scale, since a small enough segment gives near-exact results without needing a heavily approximated index. When it reaches the threshold, it is sealed: quantized, compacted, and written to disk as an immutable, read-optimized IVF-PQ or quantized HNSW segment, while a fresh empty growing segment takes over new writes. Sealed segments never mutate — high query throughput, zero write contention — and accumulate over time until a background compaction job merges several small sealed segments into one larger, better-built index, keeping the segment count per shard bounded (the target is roughly O(log N) segments for an N-vector shard).

    Query execution against this layout searches the growing segment (fast, in-memory, small) plus every sealed segment (in parallel, disk-resident) and merges the results — so more sealed segments means more parallel sub-searches per query, and query latency creeps upward as segment count grows until compaction catches up. Deletes are recorded as a delete log in the growing segment; a query against a sealed segment consults that log to filter out deleted vectors at query time, and compaction is what physically removes them, exactly mirroring the tombstone-then-compact pattern of an LSM tree.

    Concept 5 — Quantization, storage tiering, and billion-scale economics¶

    Billion-vector collections are financially untenable at full float32, and the quantization choice determines the entire storage architecture that follows from it.

    Technique Compression Memory Recall loss Best for
    float32, baseline 1× D × 4 bytes/vector 0% Small indexes, maximum quality
    float16 2× D × 2 bytes/vector < 0.5% Moderate savings, negligible loss
    int8, SQ8 4× D × 1 byte/vector < 1% Default production choice
    Product Quantization 8–32× M bytes/vector 3–15% Billion-scale, GPU serving
    Binary 32× D/8 bytes/vector 10–25% Ultra-low-memory, with reranking

    At 1B vectors, 768 dimensions, monthly RAM cost tracks compression almost linearly: float32 needs 3TB (~\(60,000/month at typical cloud RAM pricing), int8 needs 750GB (~\)15,000/month), and PQ at M = 96 needs 96GB (~$2,000/month) — binary quantization lands in the same ballpark as PQ once paired with the reranking step below. Int8 is close to a free lunch — under 1% recall loss for a 4× memory cut — and is the right default for essentially every production collection; PQ and binary are the levers to pull only once a collection genuinely exceeds the RAM budget the business is willing to fund.

    Two-phase retrieval with binary quantization recovers most of binary's lost recall cheaply. Binary ANN is fast but imprecise — Hamming distance is a single bitwise XOR-and-popcount, sub-millisecond even over large candidate sets — so run it as a first pass to get roughly 1,000 candidates in under a millisecond, then rerank those 1,000 using int8 or float32 exact distances in roughly 10ms. Net effect: 32× memory reduction, a faster first pass than running int8 directly, and under 2% recall loss versus full-precision ANN — because the expensive, precise computation only ever runs on a thousand candidates, not the whole collection.

    Matryoshka Representation Learning (MRL) truncation is a second, complementary lever specific to MRL-trained embedding models (OpenAI text-embedding-3-large, nomic-embed-text-v1.5 — see Embedding Models), which encode progressively more information in the first dimensions of the vector by training design, not by accident. Truncating 1,536 dimensions to 256 cuts storage 6× with graceful, roughly 5% recall degradation; the truncated vector serves as a fast first-pass ANN stage, and the full vector — stored separately or recomputed — serves as the reranking stage, the same two-phase shape as binary quantization but achieved through dimensionality rather than bit-width. For collections built on an MRL model, this is frequently better economics than PQ, because it needs no lossy k-means codebook at all.

    Storage tiers compose these techniques into a system that serves 10B+ vectors affordably, because at that scale most of the corpus is cold — rarely queried — and only the small hot fraction needs top-tier latency:

    Tier Index Storage Latency Use case
    Hot HNSW float32 or SQ8 RAM 1–5ms Recent, high-query-frequency vectors, roughly last 90 days
    Warm Quantized HNSW, mmap'd NVMe SSD 5–20ms Moderate age, moderate frequency
    Cold IVF-PQ Object storage, S3/GCS 100–500ms Archive, batch/analytics queries only

    A background tiering process promotes and demotes vectors based on last_queried_at and age; query execution checks hot first, falls through to warm on a miss, and only touches cold tier for queries explicitly marked batch-mode. Concretely, at a 10B-vector collection: a 100M-vector hot tier at SQ8 is ~75GB RAM, a 500M-vector warm tier at PQ is ~47GB SSD, and the remaining 9.4B cold vectors at PQ on object storage are ~900GB — total at-rest cost on the order of $100/month for cold storage plus roughly $5,000/month for hot/warm compute, against roughly $6M/month to hold all 10B vectors in RAM at float32. Tiering is not an optimization layered on top of the design; for any collection past the low billions, it is the design that makes serving the collection possible at all.

    POST /vectors and POST /query/batch are asynchronous because they are throughput-oriented — bulk ingestion and batched GPU query processing both amortize better when queued and processed in large groups rather than handled one request at a time. DELETE is synchronous because callers need to know the tombstone was recorded, even though the underlying physical removal happens later at compaction. POST /query is the one synchronous, low-latency path, and its filter DSL is a small boolean expression tree — and/or combinations of field, operator, and value — deliberately no richer than that, because the filter selectivity estimator described in the Model Layer below needs to reason about the expression's selectivity, and an unbounded predicate language makes that estimation intractable.

    The load-bearing decision in this sequence is the selectivity check before fan-out: the coordinator queries a cached selectivity estimate (a bloom filter or per-value counter maintained in the metadata index) rather than guessing, and that estimate is what decides between pre-filter, post-filter, and filtered-graph ANN from Concept 3 above on a per-query basis.

    Retrieval Layer¶

    This chapter is the retrieval layer that RAG System, AI Search Engine, and AI Recommendation System sit on top of — Concepts 1 through 3 above constitute it in full: the ANN index structure determines the recall-latency point, sharding determines how that point holds up past single-node scale, and filtering determines whether the result is actually correct once a caller's access pattern (tenant scoping, category restriction, recency bounds) is applied. What this chapter does not do is decide when to call itself, how many candidates to request, or what to do with the results afterward — RAG's hybrid fusion with BM25, a recommendation system's blending with collaborative-filtering scores, and a search engine's onward reranking are all decisions made by the caller against this system's plain (id, distance, metadata) contract, not by this system.

    Agent Layer¶

    Not applicable — this system has no agentic loop. It is a storage primitive called by applications, stateless between requests in the sense that mattered for ChatGPT or Deep Research Agent: a query carries no memory of a prior query, and the system makes no autonomous decision about what to retrieve next. Systems that do have agent loops — Deep Research Agent, Multi-Agent Research System — use this database as one tool among several, deciding independently, at the calling layer, when and how many times to invoke it per reasoning step; this chapter's system has no visibility into that fan-out, symmetric to how LLM Inference System is a dependency an agentic caller invokes repeatedly without the inference system itself being agentic.

    Model Layer¶

    There are three model-adjacent components, none of which are a neural network sitting in the query hot path the way a generator sits in RAG System's pipeline:

    1. The ANN index itself — HNSW, IVF-PQ, or ScaNN — is the closest thing to a "model" this system has: a structure fit to the data distribution at build time that determines every downstream recall and latency number.
    2. The selectivity estimator — a lightweight statistics table or small learned model that predicts what fraction of the collection a given filter expression will pass, used to choose between pre-filter, post-filter, and filtered-graph ANN in Concept 3. It is updated by a background stats-collection job and is the component most directly responsible for the adaptive filtering strategy — a stale estimator silently degrades either latency (choosing pre-filter when the filter is weak) or recall (choosing post-filter when the filter is selective).
    3. PQ codebooks — the k-means centroids trained per subvector position — are trained offline on a representative sample and stored alongside each sealed segment. When a new batch of vectors has statistically different properties than the training sample (a new document category, a new language), the codebooks can go stale relative to the incoming distribution; tracking quantization error per segment is the leading indicator, and retraining codebooks is an offline operation similar in shape to re-embedding a corpus after an embedding-model upgrade.

    Observability Layer¶

    • Query latency P50/P95/P99, broken out by tier — hot, warm, cold — because a cold-tier query showing up in what should be the hot-tier latency path (P99 > 200ms where hot-tier queries are expected) is itself the alert, not just a slow individual request.
    • Recall@K against a golden set — 10,000 held-out (query, ground-truth top-10) pairs, computed on every index parameter change or quantization change, never inferred from latency alone.
    • Shard latency imbalance — if the slowest shard's P99 exceeds 2× the median shard's P99, the data distribution is skewed and rebalancing is needed, not just more replicas on the slow shard.
    • Growing segment depth — vectors accumulated in the growing segment since the last flush; a persistently high count means the flush rate cannot keep up with the write rate.
    • Segment count per shard — too many small sealed segments means high per-query fan-out within a single shard, the signal that compaction is falling behind.
    • Filter strategy distribution — the fraction of queries using pre-filter versus post-filter versus filtered-graph ANN; a sudden shift toward post-filter on queries known to be highly selective indicates the selectivity estimator has gone stale.
    • Delete tombstone count per segment — growing tombstone counts mean compaction is not keeping pace with the delete rate, the same signal Indexing Algorithms flags for HNSW specifically.
    • Cold-tier query rate — a sudden spike may indicate a caller bug querying archived data from what should be a hot-path request, not a legitimate batch workload.

    Security Layer¶

    • Namespace and tenant isolation. In a multi-tenant deployment, every query and insert must be scoped to a tenant_id enforced at the storage layer, not only at the API gateway — a compromised coordinator must not be able to query another tenant's vectors merely by omitting a filter. Each shard independently validates the tenant claim against the authenticated caller before executing the query, the same defense-in-depth principle Enterprise RAG Platform applies to ACL enforcement one layer up.
    • Embedding inversion. A caller with sustained query access can approximate the original text behind a stored embedding via model-inversion techniques. Mitigate with per-key rate limiting and by never returning raw embedding values in query results — only (id, distance, metadata), never the vector itself.
    • Insert-path poisoning. An actor with insert access can plant adversarial vectors engineered to appear similar to a broad range of legitimate queries, degrading retrieval quality or steering results. Mitigate with anomaly detection on inserted embeddings — flagging vectors unnaturally close to a disproportionate number of existing vectors.
    • ANN parameter abuse. A caller passing extreme runtime parameters — ef_search = 100000 — can force a near-brute-force search that saturates shard CPU and degrades every other tenant's latency. Enforce hard caps at the API layer: a maximum ef_search, a maximum top_k, rejected before the request ever reaches a shard.

    Failure Handling¶

    Failure Degradation strategy
    A shard replica is unavailable Route reads to the remaining replicas; alert if replica count for that shard drops below 2, since a second failure would then take the shard fully offline
    A shard's primary is unavailable Promote a replica; writes queue briefly during promotion rather than being rejected outright
    Config store quorum is degraded Coordinators keep serving from their last-known routing table; refuse shard-topology changes until quorum is restored, since routing table writes without quorum risk a split-brain shard assignment
    Growing segment lost before flush, node crash Replay from the write-ahead queue — Kafka retains unflushed writes, so the growing segment is reconstructable, not a durability boundary itself
    Compaction falls behind write rate Segment count and tombstone ratio climb past alert thresholds before query latency visibly degrades; treat the alert as the incident, not the eventual latency spike
    Selectivity estimator is stale or wrong Bounded blast radius by design — a wrong strategy choice degrades latency or recall for that query, it does not return incorrect results outside the requested filter
    One tenant's insert or query burst degrades shared shards Per-tenant rate limits and quotas at the API layer; a noisy tenant should exhaust its own quota, not the shared shard pool's capacity
    Cold-tier object storage is slow or unavailable Batch-mode queries queue and retry; interactive queries never touch cold tier, so this failure has no interactive-path blast radius by construction

    Tradeoff Analysis¶

    flowchart TD
    Q1{"Collection size\nvs RAM budget?"} -->|"Fits in RAM"| HNSWCHOICE["HNSW:\n95-99% recall, 1-5ms\nRAM proportional to N"]
    Q1 -->|"Exceeds RAM budget"| IVFCHOICE["IVF-PQ:\n80-92% recall, 2-10ms\n10-30x less memory"]

    Q2{"Shard count?"} -->|"More shards"| MORESHARD["Lower per-shard latency\nHigher coordinator fan-out overhead"]
    Q2 -->|"Fewer shards"| FEWERSHARD["Lower fan-out overhead\nHigher per-shard latency and memory"]

    Q3{"Growing segment\nflush threshold?"} -->|"Larger"| LARGERSEG["Fewer sealed segments\nHigher flush-pause latency"]
    Q3 -->|"Smaller"| SMALLERSEG["Lower flush-pause latency\nMore segments, more per-query fan-out"]
    1. HNSW versus IVF-PQ. HNSW gives 95–99% recall at 1–5ms per query but needs RAM proportional to the full collection size; IVF-PQ gives 80–92% recall at 2–10ms with 10–30× less memory. The decision is a straightforward function of collection size relative to the RAM budget the business will fund, not a matter of one algorithm being generally superior — Concept 1 above develops the crossover point in detail.
    2. Shard count. More shards lower per-shard latency — fewer vectors, faster local search — but raise coordinator fan-out and merge overhead; the sweet spot for HNSW shards is 10–50M vectors each, past which per-shard memory and build time start to dominate and below which fan-out overhead is paid without a meaningful latency benefit.
    3. Growing-segment flush threshold. A larger threshold means fewer sealed segments and better steady-state query efficiency, but a longer, more disruptive flush pause and higher sustained memory pressure — tuned against the write rate and how much flush-induced latency variance the SLO tolerates.
    4. Quantization level. Int8 is close to a free optimization — under 1% recall loss for 4× memory reduction — and should be the default for essentially every collection; PQ's 5–15% recall loss in exchange for 10–30× memory reduction is a cost-driven choice, applied only once the collection genuinely exceeds the RAM budget, not by default.
    5. Synchronous versus asynchronous insert. Synchronous insert confirms to the caller that a vector is immediately queryable but blocks the write path on index update; asynchronous insert — queue, then background ingestion — decouples write throughput from query latency at the cost of a 1–10 second freshness window between insert and queryability, the same tradeoff RAG System's incremental-indexing design makes for its own freshness SLO.

    Interview Discussion¶

    "Design a vector database" looks, on the surface, like an AI-knowledge question, but it is actually a pure systems engineering question, and the strongest signal an interviewer is watching for is whether the candidate treats it that way. The first filter is whether the candidate understands why exact nearest-neighbor search is computationally intractable at scale — that no B-tree equivalent exists for high-dimensional distance, and why not — rather than jumping straight to naming HNSW as a memorized fact. The second filter is whether they can describe an ANN algorithm at mechanism depth: not "use HNSW" but "HNSW builds a multi-layer proximity graph; search descends from the sparsely-connected top layer to the densely-connected bottom layer, widening to ef_search candidates at layer 0." The third filter is metadata filtering — a candidate who describes hybrid retrieval fluently but cannot explain why post-filtering degrades under a selective filter has not actually built production vector search, only read about it.

    Weak answer: "Store the vectors in Pinecone, search with cosine similarity." A correct product choice, carrying zero systems depth. Strong answer: describes HNSW's graph traversal at the mechanism level, names the recall-latency-memory three-way tradeoff explicitly, explains why metadata filtering needs a different strategy depending on selectivity rather than one universal approach, and raises the distributed fan-out-and-merge problem unprompted.

    Staff-level probe: "P99 query latency is 8ms at 500 QPS but jumps to 200ms at 1,200 QPS. GPU utilization is 30%, CPU utilization is 95%. What's happening and how do you fix it?" The system is CPU-bound, not GPU-bound — the bottleneck is HNSW graph traversal, which is inherently CPU-bound, random-access, and a poor fit for GPU parallelism, so more QPS simply saturates CPU cores faster than it saturates the GPU. Fix options, in order of what to check first: reduce ef_search to trade recall for CPU cost; add CPU-heavy shard replicas and load-balance across them; or switch the hot path to IVF-PQ, which both uses less CPU per query and can offload work to the underutilized GPU. Before picking a fix, isolate whether the P99 jump originates on the shard side (per-shard graph traversal) or the coordinator side (result merging) — a merge-side bottleneck at high QPS needs a different fix than a shard-side one, and conflating them wastes the fix.

    Staff-level probe: "Queries for tenant_id = 'mega-corp' are 40× slower than other tenants, despite mega-corp holding only 5% of total vectors." Two likely causes, and the diagnostic separates them. First, mega-corp's per-tenant subindex may be fragmented from many small flushes without compaction keeping up — check sealed segment count for that tenant, and trigger compaction if it is high. Second, mega-corp's data may have an unusually narrow metadata distribution — most of their vectors concentrated in one or two categories — which causes filtered-graph ANN to struggle finding valid navigation paths for narrowly-scoped queries within that tenant's subgraph; check filter selectivity within the tenant specifically, and if it is unusually high, pre-filter mode may outperform filtered-graph ANN for that tenant's query shape despite pre-filter's general downsides at scale. See How AI System Design Interviews Work for how this diagnostic-reasoning expectation — isolate the mechanism before proposing the fix — generalizes across every case study in this book, not just this one.
