    AI Search Engine — System Design Case Study¶

    Perplexity is a product built on an assumption: somewhere, a corpus exists, retrieval over it works, and a query can be answered by fetching and reading a handful of pages — that chapter's Requirements explicitly puts "building and operating a general-purpose web crawler and search index" out of scope and leans on third-party search APIs instead. This chapter is about the assumption itself. Where does a corpus that can answer a same-day-news query in under three seconds come from? Who is crawling the web to build it, on what schedule, and how does an index avoid being stale from the moment the last document finishes embedding? Classic web search (blue links, no synthesis) and pure RAG (a synthesized answer over a static, periodically-rebuilt corpus, the pattern examined in Enterprise RAG Platform over a fixed, permissioned internal document set) each solve half of what an AI-native search engine needs, and each fails badly deployed alone: a keyword index with no LLM in front of it returns ten links and makes the user do the reading; an LLM layered over a corpus that was indexed last Tuesday confidently answers a "what happened this morning" query with last Tuesday's facts. This chapter builds the system that owns both halves — a live, continuously-updating index and a synthesis pipeline layered on top of it — at a scale where the retrieval infrastructure alone runs into the tens of thousands of CPU cores and the corpus is measured in hundreds of billions of passages.

    Requirements¶

    Functional - Four pipeline stages run for every query: crawl and indexing (continuous, upstream of any single query — the corpus exists before the query arrives, not built in response to it), query understanding (intent classification, freshness-need detection, query expansion, and decomposition for the bounded multi-hop case), hybrid retrieval fan-out (parallel dense, keyword, and freshness-prioritized search followed by cross-encoder re-ranking), and LLM synthesis (a single grounded answer generated from the re-ranked passages, with inline numbered citations). - Three response artifacts per query: a direct synthesized answer with inline [N] citations, a source panel listing the ranked passages/URLs the answer draws from (title, URL, crawl timestamp), and follow-up query suggestions generated from the original query and the retrieved evidence. - Time-sensitive and time-insensitive queries are served by the same pipeline but routed differently: query understanding detects freshness need (lexical cues like "latest," "today," a year, "current," plus a learned classifier) and biases retrieval toward the freshness-prioritized news index when it fires. - Bounded multi-hop query resolution for queries whose answer requires chaining retrieval steps (resolving an intermediate entity before the final lookup) — capped at three hops; anything requiring deeper, iterative research routes to Deep Research Agent rather than being absorbed into this system's single-pass latency budget.

    Non-functional - Latency: P50 < 2.5s, P95 < 5s end-to-end for a complete answer (first-token time is tracked separately as a UX metric, not a substitute for completion latency). - Freshness SLOs are tiered, not uniform: Tier 0 (breaking news) indexed within 15 minutes of publication; Tier 1 (high-freshness) re-crawled every 4 hours; Tier 2 (standard web) re-crawled weekly to monthly. A single platform-wide freshness number would hide the fact that these are effectively different products with different tolerances. - Answer grounding rate > 90% — the fraction of factual claims in a generated answer that a post-generation entailment check confirms are actually supported by the passage cited for them. - Retrieval Recall@20 > 80% — the fraction of queries for which a passage containing the correct answer appears somewhere in the top-20 passages handed to synthesis. This number is a hard ceiling on achievable answer quality: no amount of synthesis capability recovers a passage retrieval never surfaced. - Scale envelope used throughout this chapter (illustrative, order-of-magnitude assumptions chosen to keep the arithmetic concrete, not a reported figure from any specific company): 500M queries/day, 50B indexed documents, 5 passages/document at ~256 tokens ≈ 250B indexed passages, ~17,400 QPS at peak.

    Explicitly out of scope: image and video search; personalized or history-informed ranking (this pipeline ranks and synthesizes from the query alone, not a user profile); ad-supported or sponsored result ranking; and deep, many-hop research tasks, which this system deliberately hands off to Deep Research Agent — the same boundary Perplexity draws between its default mode and Pro Search, examined here from the infrastructure side in Agent Layer below.

    Capacity Planning¶

    Using the method from GPU Sizing & Capacity Planning, with illustrative, order-of-magnitude assumptions:

    Step Assumption Result
    Queries/day Platform-wide query volume 500M queries/day
    Average QPS 500M / 86,400s ~5,800 QPS average
    Peak-to-average ratio Search traffic peaks ~3x average across waking hours, time zones, and news cycles ~17,400 QPS peak
    Indexed documents Web-scale crawl target 50B documents
    Passages per document Each document split into retrieval-sized chunks at ~256 tokens each ~5 passages/doc
    Total indexed passages 50B × 5 250B passages

    That table looks like any other capacity-planning exercise until the two numbers that actually size the infrastructure are worked through explicitly — and both are more counterintuitive than they first appear.

    Sizing the dense vector index. This is the single most computationally intensive component in the system, and the shard count below is not a design preference — it's what the arithmetic requires:

    1. Raw embedding size at float32. 250B passages × 1,536 dimensions × 4 bytes/dim = 1.5PB. This cannot live on one machine, or one rack, at any realistic memory density — it has to be sharded from day one as a precondition for the system existing at all, not as a later optimization.
    2. int8-quantized embedding size. Quantizing each dimension to a single byte (with a per-shard scale/offset for dequantization) cuts this to roughly 375TB. Still far larger than any single machine's RAM, but now shardable into a tractable number of pieces.
    3. Shard count. At a practical working limit of ~100M vectors/shard (chosen so a shard's HNSW graph plus quantized vectors fit comfortably in one machine's RAM alongside query-serving overhead), 250B / 100M = 2,500 shards.
    4. Per-shard query load. Every dense-retrieval query broadcasts to all 2,500 shards simultaneously — there is no way to know in advance which shard holds the relevant passage, so scatter-gather across the full shard set is mandatory, not a choice. At 17,400 QPS peak, every one of the 2,500 shards receives 17,400 queries/sec.
    5. Per-shard compute. HNSW search over 100M int8-quantized vectors costs roughly 1ms/query on a modern CPU core, and one core sustains roughly 1,000 QPS at that cost. Serving 17,400 QPS/shard needs roughly 17,400 / 1,000 ≈ 18 CPU cores per shard.
    6. Total ANN fleet. 2,500 shards × 18 cores = 45,000 CPU cores, dedicated entirely to dense retrieval — before BM25, before re-ranking, before synthesis.

    Forty-five thousand CPU cores just to answer "which passages are semantically similar to this query" is what 250B passages at 17,400 QPS actually costs. It's why Vector Database sharding strategy is a first-order architecture decision here, not an implementation detail delegated to a vendor.

    Sizing LLM synthesis. At 17,400 QPS and roughly 4,400 tokens processed per query (20 re-ranked passages at ~200 tokens each, plus the query, plus generated output), aggregate synthesis throughput is 17,400 × 4,400 ≈ 76.6M tokens/second. A single H100 serving Claude 3.5 Sonnet-class throughput sustains on the order of 2,000 tokens/second, so self-hosting synthesis at peak needs 76.6M / 2,000 ≈ 38,300 H100s — a GPU fleet larger than most companies' entire compute footprint, dedicated to one pipeline stage. That's why synthesis at this scale doesn't get self-hosted by default; it routes to a managed inference API, and the question of when self-hosting starts to make sense becomes an economic one, revisited in Cost Model below rather than settled here as a capacity question.

    The contrast between these two numbers — 45,000 CPU cores for retrieval versus a synthesis stage that would need 38,300 GPUs to self-host — previews the chapter's central cost finding: retrieval is the computationally dense part of this system, but synthesis is the expensive part, by a wide margin, because GPU-hour cost dwarfs CPU-hour cost per unit of work. Cost Model quantifies exactly how wide that margin is.

    Scale Estimation¶

    • Dense vector index storage: 375TB int8-quantized (from Capacity Planning), plus HNSW graph overhead (typically 1.3-1.8x raw vector size) → a realistic working figure of 500-650TB across the 2,500 shards before replication; at 2x replication for availability, 1-1.3PB.
    • BM25/lexical index (Elasticsearch): inverted-index storage for 250B passages runs at roughly 25-40% of raw text size once compressed (term dictionaries, postings lists, positional data). At ~256 tokens/passage (~1.3KB raw text), that's ~325TB of raw text, so 80-130TB of lexical index storage across an estimated 250-node Elasticsearch cluster.
    • Freshness-prioritized news index: Tier 0/Tier 1 content only, well under 1% of the full corpus by design — on the order of 1-2B passages, small enough to serve entirely from a compact, fast-refreshing Elasticsearch cluster at sub-10ms query latency, kept physically separate from the general lexical index so a burst of breaking-news re-indexing never contends with general-web query traffic.
    • Crawl frontier (URL queue): 50B documents tracked with next-crawl-time, tier, content hash, and politeness-window metadata — at ~150 bytes/entry, ~7.5TB, held in a priority-queue-backed store rather than a flat table, so Tier 0 preemption and Tier 1/2 scheduling stay cheap operations rather than full-table scans.
    • Citation audit store: every generated answer persists its (claim span, cited passage ID, entailment-check result) tuples for quality monitoring and dispute resolution. At ~5 citations/answer and a few hundred bytes/citation, roughly 1-1.5KB/answer × 500M answers/day ≈ 500-750GB/day — small relative to the index, but load-bearing for the grounding-rate metric that is this chapter's primary quality signal.
    • Content-hash change-detection store: one hash per crawled URL (not per passage), refreshed on every crawl. At 50B URLs and a 32-byte hash plus timestamp, roughly 2TB — cheap to store, and the single highest-leverage piece of state in the crawl pipeline, since a cache hit here skips chunking, embedding, and index writes entirely for the 70-80% of re-crawled pages that turn out not to have changed.

    High Level Design¶

        RESP --> U
    end

    subgraph CrawlPath["Crawl and Index Path - Background"]
        FRONTIER["URL Frontier: Tier 0 / 1 / 2 Priority Queue"] --> CRAWLER["Crawler Fleet"]
        CRAWLER --> EXTRACT["Content Extractor"]
        EXTRACT --> CHANGE{"Content Changed?"}
        CHANGE -->|No| TOUCH["Update Last-Crawl Timestamp Only"]
        CHANGE -->|Yes| CHUNK["Chunker"]

    PUBLISH["Publisher Push: RSS / Webhooks"] -.->|"Tier 0 preempt"| FRONTIER
    IDXUPDATE -.-> RET

    Two paths, running independently and at different tempos: the query path answers a single request in under three seconds; the crawl and index path runs continuously in the background, and its output — the live index — is the input the query path's retrieval stage reads from. Neither path blocks on the other: a query never waits on an in-flight crawl, and the crawl pipeline never slows down to accommodate query load.

    The query-path latency budget, worked stage by stage:

    Stage Latency Notes
    Query Understanding ~50ms Intent + freshness classification + query expansion (T5-small, CPU)
    Parallel Retrieval ~150ms Dense ANN (150ms), BM25 (30ms), News (8ms) run concurrently — stage latency is the slowest branch, not the sum
    Re-Ranking ~220ms Cross-encoder over up to 220 candidates, ~1ms/inference
    Synthesis, first token ~500ms Streaming begins before generation completes
    First token, cumulative ~950ms
    Synthesis, stream to completion to ~2.4s Remaining tokens stream at generation throughput

    That lands comfortably inside the P50 < 2.5s target, with headroom before the P95 < 5s ceiling that absorbs cross-encoder queueing delay and slower single-shard ANN tail latency under load.

    Index consistency protocol. Dense and BM25 update asynchronously — a changed passage's embedding and its lexical index entry are written by different workers on different schedules, not inside one transaction. Every passage write carries a version tag (a UUIDv7, so the tag itself is time-ordered) alongside both the embedding and the lexical entry. The two-phase write order is fixed: the dense index is written first, the BM25 index second. That ordering means a version-tag mismatch between the two can only ever mean one thing — the dense side has already picked up a newer write than the BM25 side has caught up to. The candidate-merge step (Merge, above) exploits this directly: when a passage comes back from both BM25 and Dense with different version tags, the merge resolves to the dense version — its embedding and the passage-text snapshot captured at embed time — because the ordering guarantee rules out the more dangerous alternative: a stale embedding paired with already-updated BM25 text, which would let re-ranking and synthesis reason about text the embedding doesn't actually represent. Within any update window shorter than the two-phase write's typical propagation delay (single-digit seconds in production), this keeps every passage handed to re-ranking internally consistent — the embedding and the text describing it were computed from the same underlying content, even if that content is momentarily one version behind the very latest crawl.

    API Design¶

    POST /v1/search
{
  "query": "What did the Fed say about rate cuts this morning",
  "session_id": "sess_9c31...",         // optional, ties into follow-up context
  "max_passages": 20                     // caller-tunable, server may cap
}

Response: a streamed event sequence —
  event: status         data: {"stage": "retrieving", "freshness_required": true}
  event: source          data: {"id": 1, "url": "https://...", "title": "...", "crawled_at": "2026-07-15T13:02:00Z", "tier": 0}
  event: source          data: {"id": 2, "url": "https://...", "title": "...", "crawled_at": "..."}
  ...
  event: token           data: {"text": "The Federal Reserve"}
  event: token           data: {"text": " signaled it would hold rates steady [1][3]"}
  ...
  event: citation_flag   data: {"sentence_span": [42, 88], "citation": 4, "entailment": "failed"}
  event: done            data: {
    "sources": [{"id": 1, "url": "...", "rank": 1, "tier": 0}, ...],
    "follow_ups": ["What is the Fed's next meeting date", "..."],
    "usage": {"retrieval_ms": 178, "rerank_ms": 220, "synthesis_ms": 1450, "grounding_score": 0.94}
  }

    source events are emitted as soon as retrieval and re-ranking finish — before synthesis begins — the same decoupling Perplexity's API uses, so the client can render the source panel while the answer is still streaming rather than presenting a blank state for the full ~2.4s. citation_flag events surface a failed entailment check live, on the specific sentence, rather than only in a batch audit the user never sees. usage.grounding_score exposes the answer's own grounding rate per response, not just as an aggregate metric buried in Observability Layer — a caller building on top of this API can make its own decision about whether to surface a lower-confidence answer differently.

    Data Flow¶

    sequenceDiagram
    participant U as User
    participant GW as Gateway
    participant QU as Query Understanding

    participant RR as Re-Ranker
    participant GEN as Synthesis

    GW->>QU: Route to query understanding, plus 50ms for intent freshness and expansion
    QU->>RET: Issue BM25 Dense and News queries in parallel
    RET-->>QU: BM25 top-100 in 30ms, Dense top-100 in 150ms, News top-20 in 8ms

    QU->>RR: Up to 220 deduplicated candidates
    RR->>RR: Cross-encoder scores each pair, plus 220ms for 220 candidates

    GEN-->>U: Remaining answer streams with inline citation markers
    GEN->>GEN: Async citation verifier runs regex and entailment checks
    GEN->>GEN: Async persist citation audit record

    A default query realistically completes in the 2-2.5 second range, consistent with the latency budget in High Level Design above, dominated by the synthesis stage's streaming duration rather than by retrieval — the inverse of Perplexity's latency profile, where fetch latency (waiting on third-party pages) is the dominant term. Owning the index instead of fetching pages live trades that fetch-latency uncertainty for a fixed, well-characterized retrieval cost.

    participant C as Crawler

        CH->>E: Passage-sized chunks

    Note over F: A Tier 0 URL arriving via publisher push preempts the frontier immediately

    The branch that matters for cost is the alt block: in production, roughly 20-30% of fetched pages have actually changed since their last crawl, so the 70-80% that take the "Hash unchanged" path skip chunking, embedding, and both index writes entirely — only a timestamp updates. This is what makes continuous re-crawling computationally viable across a 50B-document corpus; without it, every re-crawl cycle would re-embed the full re-crawl volume regardless of whether anything actually changed.

    Retrieval Layer¶

    This is the architectural core of the system — more load-bearing than the choice of synthesis model, and the place where the corpus stops being "a given" and becomes the thing this chapter is actually about.

    Freshness-Tiered Crawl Scheduling¶

    A static RAG corpus is a file you load once and periodically rebuild. This corpus is not a file — it's a continuously-updating live system, and different content ages at completely different rates, which is the reason a single "re-crawl everything nightly" schedule cannot work: it either wastes enormous capacity re-crawling pages that haven't changed, or misses breaking news by hours. The mechanics of fetching, parsing, and extraction themselves are covered as a standalone topic in Web Crawler for AI Knowledge Ingestion; this section covers the scheduling and freshness-tiering logic layered on top of that pipeline.

    The URL frontier is a priority queue, not a flat schedule, with three tiers:

    Tier Target freshness Trigger mechanism Representative content
    Tier 0 — Breaking news Indexed within 15 minutes of publication Publisher-pushed: RSS feeds, news aggregator APIs, sitemap change webhooks — never polled on a fixed schedule Wire-service articles, live financial events, major announcements
    Tier 1 — High-freshness Re-crawled every 4 hours Scheduled via a next_crawl_time timestamp on each URL's frontier entry Product pages, documentation, Wikipedia, financial data pages
    Tier 2 — Standard web Re-crawled weekly to monthly Scheduled, lowest priority in the frontier Evergreen reference content, blog posts, company pages — the long tail

    Tier is the frontier's primary sort key, and a Tier 0 URL doesn't wait in line — it preempts whatever the crawl fleet is currently processing and jumps to the front the instant it arrives. Because Tier 0 URLs arrive asynchronously (a publisher's webhook fires, an RSS feed updates) rather than on a schedule, the frontier has to support insertion-with-immediate-priority, not just dequeue-by-priority. When a Tier 0 URL's actual indexing time risks exceeding the 15-minute SLO — a freshness alarm — the scheduler automatically activates a burst pool: a reserve of crawl workers, normally idle or doing low-priority Tier 2 work, redirected to breaking-news processing until the backlog clears. This is the mechanism that absorbs a major breaking event (an earnings surprise, a natural disaster, an election result) without either missing the freshness SLO or permanently over-provisioning crawl capacity for a load spike that is rare by definition.

    Freshness scheduling determines when a URL gets re-fetched; change detection determines whether re-fetching it does anything useful. After every fetch, the content extractor produces the page's main text with boilerplate — navigation, ads, cookie banners — stripped out, and the system computes a content hash over that extracted text, not the raw HTML. This distinction matters: a page's HTML changes on nearly every crawl (a rotated ad slot, an A/B-tested nav bar, a timestamp in a footer) even when the substantive content hasn't moved at all. Hashing raw HTML would trigger a full re-index on almost every re-crawl and defeat the purpose of change detection entirely; hashing extracted text means the hash only changes when the content a reader — or a retrieval system — actually cares about changes. The computed hash is compared against the hash stored from the page's previous crawl: if they match, the pipeline stops immediately, updating only the last-crawl timestamp; if they differ, the page proceeds through the full chunk-embed-index pipeline from the Data Flow diagram above. As noted there, the typical observed change rate is 20-30% of fetched pages, so change detection cuts indexing load by 70-80% without touching freshness quality — the pages that haven't changed are simply confirmed unchanged, cheaply, rather than skipped by guesswork.

    Two constraints are enforced at the scheduler, not left to individual crawl workers' discretion, because a hard architectural guarantee is the only thing that scales safely across a fleet of workers that don't otherwise coordinate:

    • robots.txt compliance is not best-effort. Before any URL on a domain is fetched, the scheduler consults that domain's cached robots.txt (itself re-fetched periodically, since it can change) and filters disallowed paths out of the frontier entirely — a disallowed URL never becomes a crawl-worker task, rather than being fetched and discarded after the fact. This is revisited as a security and ethics constraint in Security Layer below.
    • Crawl politeness is a hard rate limit, not a suggestion. No more than 1 request/second to any single domain, enforced centrally at the scheduler by tracking last-request-time per domain across the entire worker fleet — not per-worker, since a per-worker limit would let N independent workers each send 1 req/sec to the same domain and produce N req/sec in aggregate. A shared, centrally-enforced domain-level token bucket is what keeps the crawler from behaving, in aggregate, like a denial-of-service source against any single site, including during a Tier 0 burst, when the temptation to hammer a breaking-news source for freshness is strongest and the politeness constraint matters most.

    Hybrid Retrieval: Why Neither BM25 nor Dense Alone Is Sufficient¶

    Query understanding having decided what the user is asking, retrieval fan-out has to decide how to search 250B passages for the ones that answer it. Three retrieval surfaces run in parallel, each covering a failure mode the others don't:

    BM25 (keyword index, Elasticsearch). Returns the top-100 passages by term-frequency relevance — classic lexical search. Its strength is exact matching: an error code, an API method name, a product model number, a legal statute number — terms that either appear verbatim in both the query and the document or they don't, with no "close enough" for a part number. Its weakness is vocabulary mismatch: a query using "DB" doesn't match a document that only ever says "database," unless the gap is closed before the query hits the index. That gap is closed by query expansion — a small, fine-tuned T5 model adds synonyms and abbreviation expansions to the query before it reaches BM25, running in under 5ms on CPU, deliberately not an LLM call, because at 17,400 QPS an LLM call on every query for a task this narrow would be an enormous and unnecessary cost and latency tax (see Model Layer below).

    Dense ANN (FAISS HNSW, 2,500 shards). Returns the top-100 passages by embedding similarity — semantic search. Its strength is exactly BM25's weakness: it captures intent even when vocabulary differs entirely, so a query about "infrastructure migration" matches a document about "moving to new cloud architecture" with no shared keywords at all. Its weakness is the mirror image — it is comparatively slow (150ms vs. BM25's 30ms, per the scale math in Capacity Planning) and can underperform on exactly the queries BM25 handles well: an embedding space compresses an exact API method name into the same general neighborhood as conceptually related but non-identical terms, which is a liability for exact-match technical queries, not a feature. The sharding architecture behind this surface — 2,500 shards, 45,000 CPU cores at peak — is derived in full in Capacity Planning above and treated as a general pattern in Vector Database.

    Freshness-prioritized news index (Elasticsearch, Tier 0/Tier 1 content only). Queried only when query understanding sets freshness_required = true, triggered by lexical cues ("latest," a year, "current," "news") or a learned classifier. This index is small by design — under 1% of the full corpus — and correspondingly fast, under 10ms. It uses time-decay scoring: score_final = bm25_score × exp(-λ × hours_since_crawl), so a slightly less lexically relevant but much more recent document can outrank an older, more textually on-topic one. This is what makes freshness a retrieval-time property rather than something bolted on afterward — without it, a general-relevance index has no principled way to prefer "published nine minutes ago" over "published nine months ago and slightly more keyword-dense."

    All three run in parallel — the query fans out to BM25, Dense, and (when triggered) News simultaneously, since none depends on the others' output and running them serially would needlessly stack their latencies instead of taking the max. A candidate aggregator merges BM25's top-100, Dense's top-100, and News's top-20 into up to 220 candidates after deduplication (a passage returned by more than one surface is merged, not double-counted — this is also where the version-tag consistency check from Detailed Design applies). These 220 candidates pass to re-ranking.

    Cross-encoder re-ranker (BERT-large). A bi-encoder — the kind of model that produces the embeddings used for Dense ANN — encodes the query and each passage independently and compares the resulting vectors; a cross-encoder instead takes the (query, passage) pair together as joint input and lets the model attend across both simultaneously, reasoning about the actual relationship between them rather than relying on two independently-computed points happening to land close in vector space. That joint reasoning is more accurate but far more expensive per pair — exactly why it isn't the first-stage retriever over 250B passages; it runs only over the 220 candidates first-stage retrieval has already narrowed the field to. Each of the 220 (query, passage) pairs gets its own inference, at roughly 1ms each, for 220ms total, producing a re-ranked top-20 that goes to synthesis. This is the stage where the gap between "retrieval found something plausible" and "this passage deserves to be read by the synthesis model" gets closed.

    Why the hybrid matters. The reason to run three retrieval surfaces instead of picking the conceptually simplest one — Dense alone, the most "AI-native" choice — comes down to one fact: final answer quality is bounded by retrieval recall, not synthesis quality. If the passage that actually contains the answer never makes it into the top-20 handed to the LLM, no amount of prompt engineering or model capability recovers it; the model can only synthesize from what it's given. BM25 alone misses queries that depend on paraphrase or intent rather than exact terms; Dense alone misses queries that depend on an exact code, name, or number a general-purpose embedding space doesn't preserve precisely enough to distinguish from near neighbors. In head-to-head evaluation across diverse query types, hybrid retrieval consistently achieves 5-15% higher Recall@20 than either surface run alone — against the > 80% Recall@20 target in Requirements, that's the difference between meeting the bar and missing it on an entire class of queries. This is the same argument made generically in Hybrid Search and Reranking and RAG Architecture; the difference here is scale — running BM25 + Dense + a freshness-aware third index in parallel over 250B passages at 17,400 QPS is an infrastructure commitment an order of magnitude larger than the same pattern applied to a single-tenant RAG corpus.

    Vertical Indexes¶

    Beyond the three general-purpose surfaces above, a small number of domain-specific indexes exist for query types where a general-purpose embedding model measurably underperforms a domain-tuned one. The clearest example: a CodeBERT-class embedding model, trained on source code and run over a dedicated code index, outperforms the general dense index on code-search queries — general web embeddings are trained on natural language and don't represent code structure (variable scope, function signatures, control flow) as precisely as a code-specific model does. The routing decision — whether a query goes to the general dense index, the code index, or both — comes from query understanding's intent classification, the same mechanism that sets freshness_required. Vertical indexes are additive to the hybrid architecture above, not a replacement for it: a code query still benefits from BM25 catching an exact function name a code-embedding model might blur.

    Citation Grounding as an Architectural Mechanism¶

    This is what separates AI-native search from a chatbot that happens to have read some web pages: every factual claim in the answer has to be traceable to a specific retrieved passage, and "traceable" has to mean something a system can check, not just something a prompt asks for. Treating this as "we prompt the model to cite its sources" is a hope, not an architecture — a prompt is a request the model can silently fail to honor, and a pipeline serving 500M queries/day needs a mechanism that catches that failure, not one that merely reduces its likelihood.

    Synthesis prompt structure. The 20 re-ranked passages are handed to the model numbered, and the prompt makes the numbering load-bearing:

    Answer the following query using ONLY the numbered passages below.
Every factual claim must cite the passage number using [N] inline.
If the passages do not contain enough information, say so explicitly.
Do not state facts not present in the passages.

Query: {user_query}

[1] {passage_1_text} (Source: {url_1}, crawled: {ts_1})
[2] {passage_2_text} ...
...
[20] {passage_20_text}

    The numbered format isn't a stylistic choice — it's what makes citation verification mechanically possible after generation. A citation marker [7] in the output references a specific, addressable unit of retrieved evidence, not a vague gesture at "the sources," and that addressability is the entire foundation the verification step below is built on.

    Post-generation citation verifier. Two checks run on every generated answer before it reaches the user:

    • Check A — citation number validity. Does every [N] marker correspond to a real passage number, 1 through 20? This catches hallucinated citation numbers — a model inventing [21] when only 20 passages were provided, which happens more often on longer answers where the model's internal count of what it's already cited can drift. A regex pass, essentially free, run on every response.
    • Check B — entailment. Does the passage cited for a claim actually support the claim made in the sentence that cites it? A small NLI-class model (DeBERTa-scale) runs an entailment check on each (cited passage, claim sentence) pair. This catches a subtler and more damaging failure than an invalid citation number: a valid citation number attached to a sentence the passage doesn't actually support, which reads to a user as confidently sourced and is, in fact, wrong. A failed entailment check doesn't suppress the whole answer — it flags that specific sentence with a visible warning, leaving the rest of the answer (and its valid citations) intact, since suppressing a multi-sentence answer over one ungrounded clause destroys more value than it protects.

    When the passages genuinely don't have the answer. The synthesis prompt explicitly instructs the model to say so ("The available sources do not contain sufficient information to answer this") rather than filling the gap with parametric knowledge dressed up with a citation number that doesn't really support it. This uncertainty-expression behavior isn't just a UX nicety — its rate, broken out by query category, is a monitored production signal. A spike in how often the system says "insufficient information" for a specific category is not a quality success to be satisfied with; it's a retrieval-failure signal. It typically means one of two things: the crawl corpus has a genuine coverage gap for that category (nobody's crawling the sites that would answer it), or there's a systematic BM25/Dense recall gap specific to that query shape, per Hybrid Retrieval above. Either way, a rising uncertainty rate for a query category is the trigger to go investigate retrieval — not a metric the system gets credit for satisfying.

    Agent Layer¶

    It would be easy to describe this system as an agent, and it would be wrong to do so — for the same reason it would be wrong to call classic web search "agentic" just because it involves a ranking model. The base pipeline — query, retrieve, synthesize — is a single pass: query understanding runs once, retrieval fan-out runs once, re-ranking runs once, synthesis runs once. There is no planner deciding what to do next, no loop, no reflection step deciding whether to retrieve again. That's a deliberate scope boundary, not an omission: the moment a query needs iterative, adaptive retrieval with a sufficiency check and a replanning loop, this system hands it to Deep Research Agent, which is built for exactly that pattern.

    Two extensions sit at the edge of the single-pass design, and both are better described as bounded tool calls than as agent behavior:

    • Multi-hop query resolution. A query like "who is the CEO of the company that acquired the startup founded by X" can't be answered by one retrieval pass, because the second half depends on resolving the first half. The system supports up to 3 hops: resolve the first sub-entity, use it to construct the next retrieval query, repeat, capped at three iterations. Each hop adds roughly 500ms — a retrieval fan-out plus a lightweight resolution step. A query that would need a fourth hop doesn't get one inline; it routes to the Deep Research Agent, because at that depth the query needs actual planning and sufficiency-checking, not a fixed 3-step chain.
    • Query reformulation on retrieval failure. If the cross-encoder's re-ranked scores come back uniformly low — a signal that none of the 220 candidates is a good match for the query as stated — the system gets exactly one retry: an LLM reformulates the query (fixing likely typos, disambiguating an under-specified term, rephrasing toward more retrievable language), and retrieval fan-out runs again with the reformulated query. There is no second retry and no loop; a query that still scores poorly after one reformulation proceeds to synthesis with whatever it has, backed by the uncertainty-expression behavior from Citation Grounding above, rather than retrying indefinitely against a query that may simply not be well-formed.

    Both are tool calls triggered by a fixed condition, not a model deciding turn by turn what to do next — which is the actual distinction between "this system uses an LLM at more than one point" and "this system is an agent."

    Model Layer¶

    Four distinct models sit in this pipeline, each chosen for a narrow job rather than one large model doing everything, and each with a different update cadence driven by a different constraint:

    1. Query expansion — T5-small. Runs on every one of 17,400 queries/sec, entirely on CPU, in under 5ms. This cannot be an LLM call at this volume: even a fast, cheap LLM call adds cost and latency on 100% of traffic for a task — adding synonyms and abbreviation expansions — that a small fine-tuned model handles adequately. The same "don't use a large model for a task that runs on every request" principle Perplexity applies to query decomposition, sharpened here by two orders of magnitude more query volume.
    2. Document/query embedding — bi-encoder. The same model version embeds documents at index time and queries at query time; it has to be the identical version, not just the same architecture, because embeddings from different model versions aren't comparable in the same vector space. A version mismatch silently invalidates every stored embedding — the geometry the ANN index is built on no longer means what the query embedding assumes, and the failure mode isn't a crash, it's silently degraded relevance that's hard to detect without a recall regression showing up in eval. Because re-embedding all 250B passages takes on the order of weeks of embedding-service throughput, bi-encoder updates are quarterly, deliberately infrequent, and treated as a full re-indexing project rather than a routine model swap.
    3. Re-ranking — cross-encoder. The most frequently updated model in the pipeline, on a monthly cadence, because updating it requires no re-indexing — the cross-encoder only ever runs at query time over already-retrieved candidates, so a new version deploys the same way any stateless inference service does, with none of the weeks-long re-embedding cost that gates bi-encoder updates.
    4. Synthesis — the LLM. At this query volume (recall the 38,300-H100 figure from Capacity Planning), synthesis runs on a managed API, not a self-hosted deployment, for the base case. Improving production quality is primarily a prompt-engineering exercise — refining the numbered-passage structure, the citation instructions, the uncertainty-expression instructions — rather than a fine-tuning exercise, since fine-tuning a frontier-class model the platform doesn't own isn't generally an option, and the marginal quality gain from prompt refinement on a well-retrieved context is usually larger than what fine-tuning would buy anyway — the same "good retrieval lowers the floor of model capability needed" principle noted in Perplexity's Model Layer.

    The throughline across all four: update cadence is set by re-indexing cost, not by how much a team wants to ship improvements. The cross-encoder ships monthly because it's cheap to redeploy; the bi-encoder ships quarterly because redeploying it means re-embedding 250 billion passages.

    Two of these — answer grounding rate and Recall@20 — matter most, because together they answer the question every other metric is a proxy for: is the corpus giving retrieval the right passages, and is synthesis being honest about what those passages say. Every other metric on this list exists to help explain a movement in one of those two.

    Security Layer¶

    AI-native search inherits the standard RAG threat model — retrieved content is untrusted input, and prompt injection via planted text is possible (see AI Security Architecture) — but three concerns are specific to owning the crawl and serving synthesized answers over the open web, rather than retrieving from a fixed, owned corpus:

    Crawl ethics. robots.txt compliance is non-negotiable and auditable — every disallow decision the scheduler makes is logged, so a publisher dispute or a compliance review can reconstruct exactly why a given URL was or wasn't crawled. IP rotation to evade a domain's rate limits or blocking is not permitted: the crawl politeness constraint from Retrieval Layer (1 req/sec/domain, centrally enforced) exists precisely so the crawler behaves identifiably and predictably from a site operator's perspective, and rotating IPs to get around a site's own rate-limiting is indistinguishable in effect from the behavior of a hostile scraper.

    Index poisoning. A search engine that synthesizes answers is a more valuable adversarial target than one that returns links: getting a claim into a synthesized answer is more impactful than getting a link onto page one, because the user reads the claim as the system's own statement rather than as one of ten results they'll evaluate themselves. Adversarial SEO specifically targeting AI search means content engineered to rank into the top-20 candidates and read as confidently citable once it's there. Defenses: domain authority scoring that discounts content from new domains with no meaningful inbound-link history (tuned carefully against the Tier 0 freshness requirement, since a freshly registered domain with engineered content and no backlinks is a stronger poisoning signal than a genuine breaking-news source that also has no backlinks yet); claim diversity enforcement in the synthesis prompt, biasing the model away from building an answer's core claim on a single passage when multiple independent passages are available; and coordinated-content detection, flagging clusters of near-duplicate content published across many domains in a short window — a pattern characteristic of manufactured-consensus attacks rather than organic reporting.

    Copyright. The synthesis model is instructed not to reproduce retrieved text verbatim — a search engine that reads a page and repeats it near word-for-word isn't adding the synthesis value the product exists to provide, and creates real copyright exposure. This is enforced mechanically, not just by instruction: if an answer sentence exceeds 60% character overlap with the text of its cited passage, that triggers a regeneration request with a stricter verbatim-similarity constraint in the prompt, rather than shipping the near-copy to the user.

    Cost Model¶

    Component Per-query cost
    BM25 retrieval (Elasticsearch cluster, amortized) ~$0.000006
    Dense ANN retrieval (2,500 shard servers, amortized) ~$0.000012
    Cross-encoder re-ranking ~$0.0000002
    LLM synthesis (Claude 3.5 Sonnet-class, ~4,400 tokens) ~$0.018
    Total ~$0.018

    The total rounds to the synthesis line item alone because retrieval, at roughly \(0.000018/query combined, is genuinely negligible against it — **LLM synthesis costs roughly 900× what the entire retrieval stack costs, per query**. At 500M queries/day, that's **\)9M/day in synthesis cost alone at managed-API pricing. The entire retrieval infrastructure derived in Capacity Planning above — 2,500 ANN shards, roughly 250 Elasticsearch nodes, the re-ranker fleet — costs less than 1% of the synthesis bill**, despite being the part of the system with 45,000 CPU cores dedicated to it. Retrieval is computationally dense; synthesis is where the money is.

    Three architectural consequences follow directly from that asymmetry, and each is a worked instance of the general method in Cost Engineering:

    1. The primary cost lever is the synthesis model choice, not the retrieval infrastructure. Switching from a Sonnet-class model to a Haiku-class model cuts synthesis cost by roughly 90%, for a real but bounded quality cost — 15-20% degradation on the grounding and coherence metrics from Observability Layer. Switching from managed to self-hosted retrieval, by contrast, saves under 1% of total query cost — a large engineering effort against a cost line that was never the problem. A team that spends a quarter optimizing the ANN shard count has optimized the wrong 1%.
    2. Query-type routing is the cost strategy that actually moves the number. Not every query needs the more capable model: a narrow, single-source-answerable factual query (a definition, a date, a simple lookup) synthesizes just as well on the cheaper model as the more expensive one, while a comparative or analytical query ("compare X's approach to Y's") benefits from the stronger model's reasoning over multiple, sometimes conflicting, passages. The query-type classifier that already runs in query understanding — the same signal that sets freshness_required — makes this routing close to free to compute; the only added cost is the model-serving infrastructure to support two tiers, covered generally in Multi-Model Serving and Routing.
    3. Self-hosting synthesis is the only path to commodity-level economics, but it only pencils out above a real scale threshold. Zoom into a single illustrative point on that curve, deliberately at a smaller scale than the 500M-queries/day flagship figure used elsewhere in this chapter: a platform running 500M queries/month (not per day). Managed-API cost at that volume: \(0.018/query × 500M/month × 12 months ≈ **\)108M/year. An owned fleet sized to cover that load — roughly 1,500 H100s at $3/hr each, running continuously — costs 1,500 × \(3 × 8,760 hours/year ≈ **\)39.4M/year. Self-hosting saves roughly $68M/year at that scale. Below that volume, the fixed cost and operational burden of running an H100 fleet (procurement, utilization risk, the serving-stack engineering GPU Sizing and Capacity Planning walks through) outweighs the savings; in practice the crossover sits around ~200M queries/month, below which managed-API pricing is the more economical — and certainly the operationally simpler — choice.

    Failure Handling¶

    Failure Degradation strategy
    Crawl fleet falls behind on Tier 0 (breaking-news freshness alarm) Auto-activate the burst pool, redirecting idle/Tier-2 crawl capacity to the Tier 0 backlog until the SLO recovers, rather than silently missing the 15-minute target
    A single ANN shard (of 2,500) is slow or down Proceed with the remaining shards' results rather than blocking the whole query on one shard — a small, principled Recall@20 hit on that query beats a stalled response; the missing shard's documents are simply absent from that query's top-100
    BM25 (Elasticsearch) cluster degraded or unavailable Fall back to Dense-only retrieval; exact-match technical queries suffer, but the system stays answerable rather than failing closed
    Dense ANN fleet degraded or unavailable Fall back to BM25-only retrieval (plus the news index if freshness-triggered); semantic/paraphrase queries suffer, general answerability is preserved
    Cross-encoder re-ranker overloaded or down Skip re-ranking, pass first-stage retrieval merge order directly to synthesis — degraded ranking quality beats no answer
    Citation verifier (entailment check) unavailable Fall back to Check A (citation-number validity) alone, and flag every response in that window as unverified-entailment in the audit log, rather than blocking all answers on a non-critical-path service
    Synthesis (managed LLM API) provider outage or rate-limit exhaustion Fail over to a secondary model/provider if configured; if none available, serve the source panel (ranked passages, no synthesized answer) with an explicit "synthesis unavailable" state rather than fabricating an answer
    Crawl fetch times out or a domain is unresponsive Per-fetch timeout in the low single digits of seconds; that URL's re-crawl is simply deferred to its next scheduled slot rather than blocking the crawler fleet
    A domain consistently fails to fetch (bot-blocking, aggressive rate limiting) Deprioritize that domain for a cooldown window rather than retrying it on every scheduled cycle, freeing crawl capacity for domains that are actually reachable

    Tradeoff Analysis¶

    flowchart TD
    Q1{"Query freshness need?"} -->|"Time-sensitive"| FRESH["Bias toward News index,\ntime-decay scoring,\naccept narrower source pool"]
    Q1 -->|"Not time-sensitive"| Q2{"Query shape?"}
    Q2 -->|"Exact-match technical term"| BM25BIAS["Weight BM25 candidates higher,\nrely on query expansion"]
    Q2 -->|"Conceptual or paraphrastic"| DENSEBIAS["Weight Dense ANN candidates higher"]
    Q2 -->|"Ambiguous or broad"| HYBRID["Full hybrid fan-out,\nno single-surface bias"]
    HYBRID --> Q3{"Query complexity?"}
    Q3 -->|"Single-source factual"| CHEAP["Route synthesis to\ncheaper model tier"]
    Q3 -->|"Comparative or analytical"| EXPENSIVE["Route synthesis to\nmore capable model tier"]

    1. Hybrid retrieval (BM25 + Dense + News) vs. Dense-only. Dense-only is the conceptually simpler, more "AI-native" choice — one index, one model family, no keyword-matching machinery to maintain. It loses on exact-match technical queries in a way that shows up directly in Recall@20, and the 5-15% recall improvement hybrid retrieval buys (Retrieval Layer, above) is worth the real operational cost of running and keeping in sync two structurally different index types, precisely because Recall@20 is a hard ceiling on everything downstream.

    2. Real-time index updates vs. periodic snapshot rebuilds. A snapshot-based index — rebuild the whole corpus on a fixed cadence — is operationally simpler and avoids the version-tag consistency machinery in Detailed Design entirely. It is also disqualifying for this product: freshness is the primary differentiator between this system and a static RAG corpus, the framing this chapter opens with, and a same-day-news query answered from last night's snapshot is exactly the failure mode this architecture exists to avoid. Real-time, tiered updating is non-negotiable, not a nice-to-have layered on top of a simpler baseline.

    3. Query-type-routed model tiering vs. a single synthesis model. A single model tier for every query is simpler to operate, but given the 900× synthesis-cost dominance in Cost Model, it leaves the largest cost lever in the system unpulled. Routing factual, single-source-answerable queries to the cheaper tier while reserving the stronger tier for comparative and analytical queries recovers roughly 70% of synthesis cost on the queries that don't need the expensive model, without touching quality on the queries that do — the query-type classifier already exists in query understanding, so the routing decision is close to free.

    4. Pre-computed embeddings vs. on-demand re-embedding at query time. On-demand embedding — computing a fresh embedding for every passage against the current model version at query time, rather than storing 375TB of pre-computed int8 vectors — would sidestep the model-version-mismatch problem in Model Layer entirely. At 250B passages, it is simply infeasible: embedding a passage costs orders of magnitude more than looking one up, and doing it 17,400 times a second against the full corpus isn't a smaller version of the pre-computed-index problem, it's a different and far larger one. Pre-computed embeddings are the only viable design at this scale, and the 375TB storage cost from Capacity Planning is the accepted price of that choice.

    5. Crawl politeness vs. freshness SLO during a breaking-news event. The tempting shortcut during a major breaking event is to relax the 1 req/sec/domain politeness limit on whichever source is currently newsworthy, to hit the 15-minute Tier 0 SLO with more certainty. Production behavior holds the politeness constraint even then, closing the freshness gap instead through publisher-push mechanisms — RSS, webhooks, news-aggregator APIs — that don't require polling a domain harder in the first place, plus the burst-pool mechanism from Retrieval Layer, which adds crawl capacity rather than crawl rate against a single domain. Politeness is a constraint the system holds even under freshness pressure, not a dial that gets turned down when it's inconvenient.

    Interview Discussion¶

    This case study and Perplexity get confused for the same question, and distinguishing them is the first thing a strong candidate does. Perplexity tests the consumer product — how a query becomes a fan-out of search-API calls, fetches, and a synthesized answer, largely treating "there is a searchable corpus" as a given (explicitly out of scope in that chapter's Requirements). This chapter tests the infrastructure underneath that given: how a corpus of 250B passages gets built and stays current, how retrieval actually works at 17,400 QPS rather than through a third-party search API, and how the economics of running that infrastructure shape the architecture. Four things specifically distinguish the two, and a candidate should be able to name all four without prompting — this is also the kind of structural comparison the general framework in How AI System Design Interviews Work rewards over a feature-by-feature retelling:

    1. The freshness-tiered crawl scheduler, and why it is not "crawl the web on a cron job." A fixed-interval crawl either wastes enormous capacity re-crawling pages that haven't changed (no change detection) or misses breaking news by hours (no tiering, no publisher-push preemption). The three-tier priority queue plus content-hash change detection is what makes continuous freshness and efficient crawl capacity coexist.
    2. The 2,500-shard ANN architecture, and why it's a consequence of the scale math, not a design preference. 250B passages at int8 quantization is 375TB — no single machine holds that, and at 100M vectors/shard the shard count and the 45,000-CPU-core fleet size follow directly. A candidate who proposes "we'll use a vector database" without doing this arithmetic hasn't actually sized the system.
    3. Why citation grounding needs post-generation verification, not just a prompt. A prompt instructing the model to cite sources is a request the model can silently fail to honor; the regex validity check plus the NLI entailment check are what turn "the model was asked to cite accurately" into "the system caught it when the model didn't."
    4. The 900× cost asymmetry between synthesis and retrieval, and the architectural decisions that follow — query-type model routing, and the fact that retrieval-infrastructure optimization is close to irrelevant to total cost at this scale, however computationally impressive 45,000 CPU cores sounds.

    A weak answer describes AI search as "use Google's index, summarize the results with GPT-4" — collapsing the entire crawl, index, and hybrid-retrieval problem into someone else's API call, the same simplification Perplexity's Retrieval Layer explicitly allows as a legitimate build-vs-buy choice for a product, but exactly the choice this case study is testing whether a candidate can architect past. A strong answer leads with the freshness-tiered crawl (not a static or periodically-rebuilt corpus) and the hybrid retrieval architecture (not dense vectors alone) as the two structural differentiators from both classic search and pure RAG, then treats citation verification and cost asymmetry as the natural follow-on depth once those two are established.

    Staff-level follow-up probes to expect:

    • "Your answer grounding rate dropped from 92% to 78% after last week's synthesis model update — walk me through the investigation." Grounding rate is downstream of two independent things — the passages retrieval hands to synthesis, and how faithfully synthesis represents them — and the investigation has to separate which one moved. Recall@20 didn't change (nothing in retrieval, re-ranking, or the corpus changed in the same window), which isolates the regression to synthesis. The next question is whether the new model version changed how it follows the numbered-citation prompt structure — a model update can silently shift instruction-following behavior even when raw capability improves — and the fix path is prompt re-tuning against the new model version, re-validating the numbered-passage format and the citation and uncertainty-expression instructions against Check A/Check B pass rates, before considering a rollback. A candidate who jumps straight to "roll back the model" without first isolating retrieval from synthesis is skipping the diagnostic step that actually explains the regression.
    • "A competitor claims they deliver answers within 60 seconds of query submission at 17K QPS. Your P50 is 2.4 seconds. What does it actually take to get to 60 seconds, and what do you trade off?" The question is testing whether the candidate notices it's inverted — 60 seconds is dramatically slower than this system's 2.4-second P50, not faster, and the honest answer starts by naming that. A system that can afford 60 seconds per query isn't solving the same latency-budget problem this architecture is built around: it could run a full multi-hop research loop (closer to Deep Research Agent's minutes-scale budget) on every query, use a far more thorough re-ranking pass, or route every query to the most capable synthesis model regardless of query type — none viable inside a sub-3-second budget. The trade being made is depth and completeness for latency, a legitimate choice for a research tool and a disqualifying one for a search product, where users have consistently demonstrated they won't wait 60 seconds for an answer to a query they could have typed into a traditional search box in under a second. "60 seconds at 17K QPS" isn't a harder version of this system's problem — it's a different product with a different latency contract.
