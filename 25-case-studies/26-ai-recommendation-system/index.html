    AI Recommendation System — System Design Case Study¶

    Every other chapter in Case Studies either builds around an LLM as the primary component — ChatGPT, Claude, Cursor — or uses an LLM as the sole inference engine end to end — AI SDR, AI Recruiter. This chapter is the only one in the book built around a system that predates the transformer by a decade and would still work, at meaningfully lower quality, if every LLM in it vanished tomorrow. A production recommendation system is a precision-recall cascade: a two-tower embedding model narrows 100M items to 1,000 candidates in single-digit milliseconds, a deep neural ranker narrows 1,000 to 50 using feature-cross interactions no embedding-similarity search can capture, and — only at the very top of the funnel, on the last 50 candidates, at a cost per item three orders of magnitude higher than the first stage — an LLM adds natural-language intent understanding, cold-start reasoning, and personalized explanation generation that neither of the first two stages can produce. Retrieval happens in Vector Database, which this chapter treats as an infrastructure dependency exactly the way RAG System does: the two-tower model's item embeddings live in that system's ANN index, and this chapter does not re-derive HNSW, IVF-PQ, or distributed sharding — it assumes Chapter 24's system and asks what has to sit above it to turn "nearest embeddings" into "the ten items this specific user should see right now." AI Search Engine is the closest architectural cousin and the sharpest contrast: search retrieves against an explicit, stated query string; recommendation retrieves against an implicit one — a user profile the system has to construct from behavior, with no query to work from at all.

    The central discipline of this chapter is being honest about where each technology earns its place in the stack. Two-tower retrieval exists because nothing else scores 100M items in a 10ms budget. The neural ranker exists because feature-cross interactions between user and item — signal the decoupled two-tower model structurally cannot see at inference time — recover the precision retrieval traded away for scale. The LLM shows up exactly three times, each at a point where its unique capability has no substitute in the classic ML toolkit: semantic understanding of stated preferences at cold-start, natural-language explanation generation, and open-ended intent parsing when a user states one explicitly. It does not show up as a fourth ranking stage that scores all 1,000 candidates, and it does not replace the two-tower model — running an LLM over 1,000 candidates at 3,500 QPS is not a latency optimization away from viable, it is off the table by three orders of magnitude, a constraint this chapter treats as load-bearing rather than incidental.

    Requirements¶

    Functional

    • Serve personalized recommendation feeds with sub-200ms latency for the default (no explicit intent) path.
    • Support explicit intent queries — free-text input alongside a recommendation request — with sub-700ms latency, inclusive of LLM reranking.
    • Produce cold-start recommendations for new users from stated preferences, with no interaction history required.
    • Generate personalized, specific explanations for viewed recommendations ("because you finished three hard-SF novels this month," not "because you liked similar items").
    • Refresh recommendation feeds within 30 seconds of a new interaction signal (a click, a completion, a skip) reaching the feature store.

    Non-functional

    • Retrieval recall@1000 > 85% — the top-1000 candidates returned by ANN retrieval must contain at least 85% of the items a fully-computed, ground-truth ranking would place in its own top-50.
    • Neural ranker P95 latency < 40ms for a 1,000-candidate batch.
    • Feed freshness < 30 seconds from user interaction to that interaction influencing the next served feed.
    • Diversity index (Concept 5) held within 20% of a user's historical range — the guardrail against filter-bubble drift.
    • Cold-start CTR (new users, no interaction history) within 70% of established-user CTR.

    Explicitly out of scope: content creation, curation, or moderation of the item catalog itself — this chapter assumes a catalog that already exists and is policy-compliant. Fraud and abuse detection is a separate ML system with different objectives and a different cost of a false negative. Ad recommendation and auction-based ranking are out of scope — ad systems optimize an auction-cleared price alongside relevance, a fundamentally different objective function than the engagement-and-satisfaction objectives this chapter's ranker optimizes; see Multi-Model Serving & Routing for the general routing infrastructure both systems would share if deployed side by side.

    Capacity Planning¶

    Sized for a consumer media platform with a 10M-item catalog and 100M daily active users, each refreshing their feed an average of 3 times per day:

    Component Assumption Result
    Recommendation requests 100M DAU × 3 refreshes/day 300M requests/day ≈ 3,500 QPS sustained
    Item catalog Consumer media platform 10M items
    ANN retrieval cluster 20-shard hot-tier cluster, Vector Database architecture Throughput headroom far exceeds 3,500 QPS — shard count here is set by catalog memory footprint, not query load
    Neural ranker GPU fleet ~100 ranking requests/sec sustained per GPU (1,000-candidate batches, pipelined to keep the GPU saturated across the ~20ms/batch cost developed in Concept 3) 3,500 QPS ÷ 100 QPS/GPU ≈ 35 GPU instances
    Feature store (Redis) ~2.5M ops/sec raw capacity per node, held at a 20% steady-state utilization target for hot-key and burst headroom → ~500K effective ops/sec/node 3,500 QPS × 1,002 lookups/request (1 user + 1,000 items + 1 context) ≈ 3.5M ops/sec → 7 nodes
    Training event volume 100M DAU × 20 interaction events/day/user 2B events/day ≈ 23,000 events/sec — 3 Kafka brokers hold this comfortably at well under half their combined throughput

    The retrieval line is worth dwelling on because it is the one place this chapter's capacity story diverges from Vector Database's own: that chapter sizes its 20-shard reference architecture against 1,000 QPS sustained, and this system needs 3,500 — but per-core HNSW throughput of 500–2,000 QPS (Chapter 24's own scale-estimation figure) means query load was never the constraint on shard count for either system. What actually sizes the shard count here is holding a 10M-item hot tier resident in RAM with headroom for the query-tower's embedding refresh cycle (Concept 1) — a capacity constraint, not a throughput one, which is precisely the distinction Chapter 24's own tiered-storage design is built to make explicit.

    Scale Estimation¶

    Serving latency budget, default path (no explicit intent — the common case):

    Stage Latency
    Query tower forward pass (parallel with user feature lookup) ~5ms
    User static feature lookup, Redis ~1ms (parallel with above)
    ANN retrieval, 1,000 candidates ~10ms
    Feature hydration, batch multi-get over 1,000 candidates ~3–5ms
    Neural ranker forward pass, DCN, GPU, batched ~20ms
    Score combination + sort ~1.5ms
    MMR diversity filter ~1ms
    Business rules (dedup consumed items, freshness check) ~1ms
    Total ~40ms, comfortably inside the 200ms P95 budget

    With explicit intent (LLM reranking over the top-50, Concept 4c): add one LLM call of roughly 5,000 input tokens (50 candidate descriptions at ~100 tokens each) at ~500ms — total ~540ms, inside the 700ms P95 budget. This path is gated behind the presence of explicit intent text in the request; it never runs on the default feed-refresh path, so its cost and latency do not tax the 97%+ of requests that carry no explicit query.

    Training data throughput: 100M DAU generating ~20 interaction events/day/user is 2B events/day ≈ 23,000 events/second sustained into Kafka — well inside three brokers' combined capacity, with the same durability role Kafka plays in Vector Database's write path: the queue is the replay source if a downstream consumer falls behind, not a durability boundary itself.

    Item embedding refresh: at 10,000 embeddings/second per A100 (batched GPU inference, the same order-of-magnitude figure Vector Database uses for FAISS-GPU throughput), 6 A100s embed the full 10M-item catalog's raw vectors in under 3 minutes of GPU compute. The full refresh cycle — reading changed item content, feature extraction, embedding, and writing the new vectors into the ANN index's bulk-ingestion path — realistically runs 15–20 minutes end to end once I/O and index-write overhead are included, comfortably inside an hourly delta-update cadence for changed items and a nightly cadence for a full re-embed.

    Explanation generation cost is the line item most sensitive to a design decision made in Concept 4b, and it is worth working through both ends of that decision here because the gap between them is the entire argument for lazy generation. At a blended Haiku-class cost of roughly $0.001 per explanation call (~300 input tokens of attribution context, ~150 output tokens of generated text): eagerly generating explanations for all top-10 feed items on every one of 100M DAU's 3 daily refreshes is 100M × 3 × 10 × \(0.001 ≈ **\)3,000,000/day — clearly untenable. Generating explanations only for items a user actually views (measured at roughly 2–3 items per user per day across all sessions) is 100M × 2.5 × \(0.001 ≈ **\)250,000/day, a 12× reduction. Reserving full LLM generation for a power-user cohort and top-3 slots, with a template system covering the long tail (Concept 4b), pushes this further, to the low tens of thousands per day. Cost Model below carries this comparison forward against the rest of the system's cost lines.

    Five components, each independently scalable: an offline training pipeline that turns interaction logs into the two-tower model and a freshly-embedded item catalog; a real-time feature pipeline that keeps session-level signals current to the second; a serving pipeline that is the request-time cascade this chapter is built around; an async explanation pipeline that never sits on the serving critical path; and an experimentation layer that stamps every request with its A/B bucket before it enters the serving pipeline, so every downstream metric is attributable to a specific model, weight, or threshold configuration.

    Detailed Design¶

    The five concepts below map directly onto the cascade the introduction describes. Each stage trades recall for precision at a cost roughly two orders of magnitude higher per item than the stage before it — the reason a system that touches 100M items per request can still respond in 40ms is that only the first stage ever sees all 100M, and every subsequent stage operates on an already-narrowed, already-higher-quality candidate set.

    flowchart LR
    Catalog["Item Catalog\n100M items"] --> ANNStage["ANN Retrieval\nembedding cosine similarity\n~0.0001ms per item"]
    ANNStage --> C1["1,000 candidates"]
    C1 --> RankStage["Neural Ranker\ndeep feature cross interactions\n~0.02ms per item"]
    RankStage --> C2["50 candidates"]
    C2 --> LLMStage["LLM Reranker\nnatural language intent understanding\n~10ms per item, optional"]
    LLMStage --> C3["10 candidates"]
    C3 --> RuleStage["Business Rules\ndiversity, freshness, policy\n~0.01ms per item"]
    RuleStage --> C4["8 to 10 candidates"]
    C4 --> Feed["Recommendation Feed"]

    Two things about this cascade are easy to miss on first read. First, the LLM stage is the only optional one — it fires only when explicit intent is present, so the vast majority of requests skip it entirely and the cascade collapses to three stages. Second, the cost-per-item column is not decorative: it is the reason the stages are ordered the way they are. Running the ~10ms-per-item LLM stage first, over 100M items, would cost 1,000,000 seconds per request. Running it last, over 50 items, costs 500ms — the entire design is this ordering, applied consistently.

    Concept 1 — Two-tower model: the architecture that makes 100M-item retrieval possible¶

    Why a cross-encoder fails at this scale. A cross-encoder — the architecture a text reranker like a BERT cross-encoder uses — computes affinity between a (user, item) pair by processing both jointly through a single network with cross-attention. It is the most accurate architecture available, because the model sees the full user-item interaction before scoring. It is also the wrong architecture for retrieval: scoring a 100M-item catalog this way requires 100M forward passes per request. At 5ms per pass, that is 500,000 seconds — not a latency problem to be optimized away, a computational impossibility at this catalog size. RAG System's cross-encoder reranker runs the same architecture successfully, but only ever over the ~50 candidates a prior fusion stage has already narrowed to — the identical constraint this chapter's cascade is built around.

    The two-tower solution. Decouple the user and the item into two independent encoder networks that never see each other at inference time:

    • Query tower: takes user features — user_id embedding lookup, recent interaction history, session signals, demographics — and outputs a query embedding q ∈ R^D.
    • Item tower: takes item features — item_id embedding, content features, metadata, popularity signals — and outputs an item embedding v ∈ R^D.
    • Affinity: score(user, item) = cosine(q, v).

    The item tower runs entirely offline: every item in the catalog is embedded once and written into the ANN index described in Vector Database. The query tower runs online, one forward pass per request, in roughly 5ms. ANN search over the resulting embedding space finds the top-K items by cosine similarity in roughly 10ms — Chapter 24's HNSW mechanism, applied here without modification. Total retrieval: roughly 15ms for 100M items, a five-orders-of-magnitude improvement over the cross-encoder's 500,000 seconds.

    The tradeoff is real, not free: because the towers never see each other during inference, the model cannot capture user-item feature crosses at retrieval time — an item the user would love but that doesn't happen to sit near their embedding is simply missed, a recall loss the neural ranker (Concept 3) partially recovers by scoring the 1,000 survivors with exactly the cross-features retrieval had to give up.

    Training the two-tower model. Training data is (user, positive_item, negative_items) triples mined from interaction logs, where a positive is a strong-signal interaction — completion, purchase, save — not a mere impression.

    • In-batch negatives: the other positive items already present in the same training batch double as negatives for every other example — efficient, since it needs no separate negative-sampling pass, but prone to false negatives when an item that would genuinely interest a user happens to sit in the batch as someone else's positive.
    • Hard negatives: items the current model retrieves with high similarity but the user did not interact with — near-misses in embedding space. Training on these specifically sharpens the decision boundary the in-batch negatives leave soft, and hard-negative mining measurably improves recall@K by 10–25% over random negatives alone on standard benchmarks.

    Loss is an in-batch softmax (an InfoNCE variant). For a positive pair (u, i⁺) against B−1 negatives drawn from the same batch:

    \[\mathcal{L} = -\log \frac{\exp(q \cdot v^+ / \tau)}{\sum_{j=1}^{B} \exp(q \cdot v_j / \tau)}\]

    Temperature τ controls how peaked the resulting distribution is — a lower τ (typically 0.05–0.1) punishes near-misses harder, producing a sharper embedding space at the cost of a less forgiving training signal.

    Item tower update cycle. Item embeddings need refreshing whenever the item tower model itself is retrained (typically weekly) or when an individual item's content changes materially — price, description, availability. A full re-embed of a 10M-item catalog is, per Scale Estimation above, under 3 minutes of raw GPU compute and 15–20 minutes end to end including the index write. During that transition window, the old embeddings remain live and continue serving queries; the new embeddings build in a separate index and swap in atomically once the rebuild completes — the same atomic-swap discipline RAG System uses for its own incremental-indexing freshness SLO, applied here to a full-catalog rebuild rather than an incremental delta. Delta updates for individual changed or newly-added items run hourly, needing no full rebuild.

    Concept 2 — Feature store: the training-serving consistency problem¶

    The feature store is the component most likely to determine whether a recommendation system works in production versus only in offline evaluation — more often the actual cause of a quality regression than the ranking model architecture itself.

    Training-serving skew, defined. The ranking model (Concept 3) is trained on features computed in batch from historical data. At serving time, those same features are computed from real-time data. If the two computation paths diverge — a timezone handled differently in timestamp aggregation, a different rolling-window definition, a schema migration applied to one path and not the other — the model sees a feature distribution at serving time that differs from what it was trained on. The result is a ranking-accuracy gap between offline evaluation and production that is invisible until it is measured explicitly, because nothing in either pipeline throws an error; the numbers are simply, silently wrong in one of the two paths.

    The unified feature store. One feature-computation pipeline, two read paths: the transformation and aggregation logic is written once, and the same code runs offline against historical event logs (producing training features) and online against the real-time event stream (producing serving features). Both write into the same logical feature namespace, differing only in staleness — an offline training job reads from the offline store, a serving request reads from the online store, and the schema is identical by construction rather than by discipline.

    Feature class Examples Latency target Storage
    User static account age, country, subscription tier < 2ms Redis (hot cache)
    User real-time last 10 clicked item IDs, session start time, current device < 2ms Redis, TTL = session timeout
    Item static category, content embedding, metadata tags < 2ms Redis, populated from nightly batch
    Item real-time rolling 1-hour CTR, inventory count < 5ms Redis, updated by stream processor
    Cross features user-item co-occurrence, trailing 30 days < 5ms Redis or Cassandra
    Context device type, hour of day, geolocation 0ms Derived from the HTTP request itself

    Real-time session feature pipeline. User events — click, view start, view end, dwell time — stream to Kafka as they happen. A Flink job consumes the stream and computes rolling session features per user: last N clicked item IDs (evicting the oldest past N), the category distribution of recent views, an estimated current intent derived from that distribution, and current dwell time on the active item. Flink writes each of these to Redis keyed by user_id, TTL'd to the session timeout (30–60 minutes). A serving request reads the latest session state in under 2ms — the real-time half of what Concept 5's feedback loop needs to close within its 30-second freshness SLO.

    Feature hydration at ranking time. After retrieval returns 1,000 candidates: read the requesting user's features from Redis (one key lookup, ~1ms); batch-read item features for all 1,000 candidates via a pipelined multi-get (~3ms regardless of batch size up to roughly 5,000 items); derive context features from the request itself (0ms). Total hydration: ~5ms for the full 1,000-candidate set. This is on the serving-latency critical path — Scale Estimation's ~40ms budget prefetches user features in parallel with retrieval rather than sequentially after it, exactly the overlap the High Level Design diagram's parallel Req → QTower / Req → UserFeat edges show.

    Concept 3 — Neural ranking model: multi-task scoring at production latency¶

    The ranker takes 1,000 feature-hydrated candidates and produces a score per candidate — the stage where the cross-feature interactions the two-tower model structurally cannot see get recovered.

    Architecture. Input is the concatenation of user, item, and cross features per (user, item) pair — typically 500–2,000 features, a mix of dense embeddings and sparse categorical one-hot encodings. Wide & Deep (Google, 2016, still widely deployed) pairs a manually-engineered wide linear component for memorizing exact feature combinations with a deep MLP that learns interactions automatically. DCN (Deep & Cross Network) replaces the hand-engineered wide component with a cross network that explicitly models bounded-degree feature interactions, more parameter-efficient than Wide & Deep at capturing the same interaction signal and the current industrial default for non-transformer rankers. Transformer-based rankers apply self-attention across the candidate set rather than across tokens — the model sees all 1,000 candidates simultaneously and can compare them directly ("candidates 1–4 are all sci-fi; candidate 5, a thriller, should get a diversity bonus"), a list-aware ranking signal item-level scoring cannot produce, at meaningfully higher inference cost. DCN is this chapter's default; transformer rankers are the next step once list-level ranking quality justifies the added compute.

    Multi-task learning. A ranker trained purely on click-through rate learns to surface clickbait — sensational thumbnails and misleading titles that generate clicks without satisfaction. Production rankers optimize several objectives simultaneously: engagement (click probability, play/view rate), quality (completion rate, dwell time, 24-hour return visit), and satisfaction (share, save, like versus skip, hide, report). The architecture is shared bottom layers that capture general user-item affinity, feeding separate task-specific heads that each predict one objective — the shared bottom lets engagement signal inform quality prediction and vice versa, a transfer-learning effect single-task models forgo entirely.

    The final ranking score is a weighted combination of head outputs:

    \[\text{score}(u, i) = w_{\text{ctr}} \cdot p_{\text{click}} + w_{\text{quality}} \cdot p_{\text{completion}} + w_{\text{satisfaction}} \cdot p_{\text{like}} - w_{\text{negative}} \cdot p_{\text{skip}}\]

    The weights are business parameters, tunable without retraining — change the weights, rerun scoring against the already-computed head outputs, and get a different ranking. This separation between what the model predicts and how the business weighs those predictions matters because it lets different product surfaces run different weights against the same trained model: a news feed and a search-results surface can prioritize engagement and completion differently without either needing its own ranker.

    Position bias correction. Items shown at position 1 are clicked roughly 10× more often than items at position 10, independent of quality — training on raw click data without correction teaches the model "position 1 is good" rather than "the user genuinely preferred this." The fix is inverse propensity scoring: weight each training sample by 1 / P(position), downweighting high-propensity positions (1) and upweighting low-propensity ones (8). P(position) itself is estimated by periodically randomizing recommendation order for a small slice of traffic (1–5%) and measuring the click-rate ratio across positions in that randomized traffic — an experiment, not a formula, because the true propensity curve is a property of this specific product surface's UI, not a universal constant.

    Serving latency budget (developed in full in Scale Estimation): feature hydration ~5ms (run in parallel with retrieval), DCN forward pass over 1,000 candidates on GPU ~20ms, score combination ~1ms, sort ~0.5ms — ~25ms total, the single largest component of the ~40ms default-path budget. GPU batching is what makes this figure viable at all: all 1,000 candidates for one request go through one batched forward pass, not 1,000 sequential ones — sequential inference at 20ms each would cost 20 seconds per request, three orders of magnitude past the budget.

    Concept 4 — LLM integration: three specific capabilities, not a fourth ranking stage¶

    An LLM adds value at exactly three points in this pipeline, each chosen because the classic ML toolkit has no substitute for it — and nowhere else, because scoring 1,000 candidates per request with an LLM at 3,500 QPS is off the table by three orders of magnitude, not a target for future optimization. Multi-Model Serving & Routing covers the general routing infrastructure that decides, per request, whether the LLM reranker below fires at all — the same tiered-routing discipline that chapter applies to cost-sensitive chat traffic applies here to a request-level yes/no gate rather than a model-size choice.

    4a — Cold-start via semantic intent embedding. A new user with zero interaction history has no click signal to feed the query tower, so it defaults to the population-mean embedding and recommendations collapse to pure popularity — a degraded early experience that measurably increases churn before a user has had a chance to see the product work. At sign-up, an LLM can turn an explicit preference statement ("I enjoy hard SF and cyberpunk, and I recently loved Project Hail Mary") into an intent embedding two ways: encode the statement directly with the same embedding model the item tower uses, so it lands in the same space; or have the LLM generate a set of representative item descriptions matching the stated preference, embed those, and use their centroid. This intent embedding substitutes for the query tower's output on the first N recommendations, then blends out as real interaction history accumulates:

    \[q_{\text{effective}} = \alpha \cdot q_{\text{intent}} + (1-\alpha) \cdot q_{\text{tower}}\]

    α decays from 1.0 (no history) to 0.0 (sufficient history, typically 50+ interactions). Cost is one LLM call at sign-up, roughly 50ms — not on the serving hot path, paid once per user rather than once per request.

    4b — Personalized explanation generation. "Because you liked X" is a rule, not an explanation; an LLM can generate a specific, accurate one from the ranker's own feature attributions. For each of the top-10 recommendations: extract feature attributions for that (user, item) pair (SHAP values against the DCN ranker, or attention weights directly if using a transformer ranker); map the top attributions to human-readable signals ("6 recent sci-fi completions" → "your interest in science fiction"; high embedding similarity to a recently-finished item → "similar to books you finished recently"); prompt an LLM with the user's recent completions and the top two attributed features, instructed to generate one specific sentence and explicitly told not to fall back to "because you liked books like this."

    Cost at 100M DAU is the reason this cannot run eagerly — Scale Estimation works the arithmetic: eager generation for all top-10 items on every refresh is roughly $3M/day; generating only for items a user actually views (measured at 2–3 per session) cuts this to roughly $250K/day; reserving full LLM generation for power users and the top-3 slots specifically, with a distilled template system — the LLM generates the template vocabulary once, offline, and the template runs at near-zero marginal cost for the long tail — pushes the aggregate well below $50K/day. The lazy-generation mechanism itself: the feed response returns item IDs and scores immediately; explanations generate asynchronously, triggered only when the client signals a user actually scrolled to or tapped an item, via the GET /explanations/{user_id}/{item_id} endpoint below.

    4c — Explicit intent reranking. When a request carries free-text intent ("something light to read on a flight") alongside the implicit profile, an LLM can rerank the neural ranker's top-50 by understanding that stated intent against each candidate's description — a natural-language-understanding task neither the two-tower model nor the DCN ranker is built for. This applies to search-and-recommendation hybrid surfaces and conversational refinement requests; it does not apply to a passive feed, where there is no stated intent for an LLM to interpret against. Prompt structure is numbered item descriptions (kept to 50–100 tokens each to bound cost) in, a ranked list of item IDs out — for 50 candidates at 100 tokens each, roughly 5,000 input tokens, well under $0.002/call at Haiku-class pricing. Latency of ~500ms for a call this size is acceptable specifically because the user issuing an explicit query already expects search-like latency, not feed-refresh latency — the same expectation-setting Perplexity relies on to justify its multi-second default-mode budget.

    Concept 5 — Feedback loops, diversity, and filter bubble avoidance¶

    The system's own output becomes tomorrow's training data — a closed loop that, left unmanaged, amplifies whatever bias existed in the first recommendation it ever made.

    How a filter bubble forms. A user watches three sci-fi films; recommendations shift to 60% sci-fi; the user, shown mostly sci-fi, watches two more; recommendations shift to 80%; after four weeks, recommendations are 95% sci-fi. The model has correctly learned "this user clicks on sci-fi" while the confound — "this user has only been shown sci-fi" — goes unmeasured. The engagement signal the model is optimizing was itself produced by the model's own prior output, and nothing in a naive training loop distinguishes a genuine preference from a preference the recommender manufactured by narrowing the options.

    Measuring it. Diversity index: the number of distinct genre or category clusters present in a user's feed over the trailing 7 days. If a user who previously engaged across 6 categories now receives recommendations spanning only 2, that is a filter-bubble alert, not a quality improvement — tracked per user cohort, with an alert when the cohort's P25 diversity index drops more than 40% week over week.

    Explore-exploit scheduling. Reserve ε = 10–15% of recommendation slots for exploration — items drawn from categories the user has not recently engaged with. Exploration-slot signal is used only to estimate preference in the new category, never to reinforce the existing profile, a deliberate firewall against the loop that formed the bubble in the first place. Too much exploration (ε = 30%) visibly degrades immediate engagement; too little (ε = 5%) lets the bubble close faster than exploration can counteract it. Start new users at ε = 15% (more exploration is needed while the preference map is still being built) and decay to ε = 10% once the profile is established. Thompson sampling over each category's estimated click-rate posterior is the better mechanism than uniform-random exploration: categories with high uncertainty get sampled more (genuine exploration), categories with a well-established high rate get sampled reliably (exploitation), and categories with a well-established low rate are rarely wasted on.

    Diversity constraint at final reranking. After the neural ranker scores all 1,000 candidates, apply Maximal Marginal Relevance to the final selection:

    \[\text{MMR}(i) = \lambda \cdot \text{score}(u, i) - (1-\lambda) \cdot \max_{j \in \text{Selected}} \text{sim}(i, j)\]

    where sim is item-embedding cosine similarity (high similarity implies the same genre or topic cluster). λ = 0.9 is relevance-focused; λ = 0.6 is diversity-focused, and which end of that range a given surface should sit on is itself a business decision — a news feed tolerates lower diversity because the reader is deliberately deep in one topic, while a discovery surface needs the opposite. λ is a per-surface tunable, the same MMR mechanism RAG System applies to context-window redundancy, repurposed here for feed-level redundancy instead.

    Implicit signal quality hierarchy. Not every interaction carries the same evidentiary weight, and treating them as equal corrupts the training signal:

    Signal Informativeness Examples
    Strong positive Very high Watched > 90%, purchased, saved, shared
    Weak positive Medium Clicked, watched 30–90%, read partially
    Ambiguous Low Impression without click — may mean no interest, or may mean the item was never actually seen
    Negative High Skipped, hid, reported, abandoned in the first 10%

    A non-click is not a negative label on its own — the item may never have been rendered in view, or the click may have been inconvenient in that moment. Only a confirmed skip (the item was in the primary viewport and the user actively scrolled past without engaging) is a negative label; treating every non-click as negative teaches the ranker to avoid anything a user simply hasn't reached yet.

    A/B testing specifics. Recommendation experiments are harder than a typical feature A/B test because the recommendation itself shapes future behavior — a better model in week 1 produces a better interaction history that makes week 3's recommendations better too, so a short-window measurement understates a real improvement and overstates a novelty effect equally. Practices that follow from that: randomize at the user level with a stable assignment across the whole experiment; run a minimum of 14 days to let behavioral adaptation show up; maintain a permanent 5% holdout excluded from all model changes, compared against production monthly as a long-term compounding-effect baseline; track diversity index, negative-feedback rate, and return-visit rate as guard metrics alongside the primary engagement metric, since a treatment that lifts CTR 3% while dropping return-visit rate 2% is not a net win; and separate week-1 from week-3 effect size specifically — if the week-3 lift is under half of week 1's, most of the measured gain was novelty, not quality.

    GET /explanations exists as a separate endpoint precisely because of the lazy-generation decision in Concept 4b: the client calls it only after confirming a user actually viewed the item, not for all 10 items returned by /feed. POST /events returns immediately and writes to Kafka asynchronously — it is on no one's latency budget, and blocking it on the real-time feature pipeline (Concept 2) would tie a fire-and-forget write to Flink's processing latency for no benefit to the caller.

    end

    ANN-->>QT: 1000 candidates, 10ms
    ANN->>FS: batch item feature hydration, 3ms
    FS-->>NR: hydrated features for 1000 candidates

        NR->>LR: top 50 candidates, intent text
        LR-->>MM: reranked top 10, 500ms

    U->>U: async, viewed items trigger explanation generation, 500ms

    The branch point worth noticing is the alt block: the LLM reranker sits entirely inside a conditional that the overwhelming majority of requests never enter, which is what lets the default path hold to ~40ms while the explicit-intent path still exists as a first-class, correctly-budgeted branch of the same pipeline rather than a bolted-on separate system.

    Retrieval Layer¶

    Retrieval in this chapter is the query tower's online forward pass plus an ANN search against the item tower's offline-computed embeddings — the mechanism is Vector Database's in full, and this chapter adds nothing to how that search executes: the recall-latency tradeoff of HNSW versus IVF-PQ, the fan-out-and-merge pattern across shards, and the filtered-graph ANN strategy for scoping a query to, say, one content category or one region are all Chapter 24's mechanisms, unmodified. What this chapter owns instead is everything on either side of that search: producing the query embedding (Concept 1's query tower, trained jointly with the item tower on interaction triples rather than on any general-purpose corpus), and everything the ANN search's raw (id, distance) output goes through before it reaches a user (Concepts 2 through 5). RAG System is the same shape of dependency in a different direction — it asks the vector database for the chunks that best support a generation step; this chapter asks it for the items that best match a user profile, and the two systems' entirely different consumption patterns (RAG's small top-K feeding a prompt; this chapter's top-1,000 feeding a ranker) are exactly the kind of access-pattern diversity Chapter 24's own introduction names as the reason it has to serve both simultaneously.

    AI Search Engine sharpens the contrast from the other side: that system's query is explicit and stated by the user in the moment, so its retrieval problem is "find what matches this text." This chapter's query is implicit — there is no text, only a behavioral profile the query tower has to construct from history — and the entire cold-start problem in Concept 4a exists precisely because a user with no history gives the query tower nothing to construct that profile from.

    Agent Layer¶

    Not applicable in the sense the term is used for Deep Research Agent or Pro Search in Perplexity: there is no planning loop, no sufficiency check, and no multi-step tool use anywhere in this pipeline. The serving cascade is a fixed sequence — retrieve, hydrate, rank, optionally rerank, diversify, filter — executed once per request with no branch that revisits an earlier stage based on what a later stage found. The one LLM call that resembles a "decision" (whether to invoke the reranker in Concept 4c) is a static gate on request content, not an autonomous choice the system makes about how much work to do; it is architecturally identical to the tiered-routing gate in Multi-Model Serving & Routing, not to an agent's sufficiency check. The explanation pipeline (Concept 4b) runs asynchronously but is likewise a single LLM call per triggered item, not a loop.

    Model Layer¶

    Five models, versioned and upgraded independently:

    1. Query and item towers (Concept 1) — the two-tower retrieval model, trained jointly on interaction triples with in-batch and hard-negative sampling. The item tower's output feeds directly into Vector Database's ANN index; the query tower serves online.
    2. Neural ranker (Concept 3) — a DCN with shared-bottom multi-task heads, served on a dedicated GPU fleet sized in Capacity Planning. This is the highest-QPS model-serving component in the system and the one Multi-Model Serving & Routing's load-aware routing and batching disciplines apply to most directly, even though it is not itself an LLM.
    3. Cold-start intent LLM (Concept 4a) — a single call per new user at sign-up, off the serving hot path; any capable general-purpose model is sufficient since output quality, not latency, is the constraint.
    4. Explanation-generation LLM (Concept 4b) — Haiku-class, chosen specifically for cost given the volume worked out in Scale Estimation; served through the same infrastructure LLM Inference System describes generically, with the async, cache-backed invocation pattern this chapter adds on top.
    5. Explicit-intent reranking LLM (Concept 4c) — also Haiku-class by default, gated behind the presence of explicit intent text; Multi-Model Serving & Routing is the general pattern this gate is an instance of, applied here as a binary present/absent trigger rather than a complexity-scored cascade.

    No LLM in this list scores all 1,000 retrieval candidates, ranks the full candidate pool, or sits on the default feed-refresh path — the load-bearing absence this chapter keeps returning to.

    Observability Layer¶

    • Retrieval recall@50 — do the neural ranker's eventual top-50 selections actually appear in the 1,000 ANN candidates? A drop below 85% means the two-tower model is undershooting and needs retraining or a wider ef_search, the same signal Vector Database tracks for its own recall SLO.
    • Neural ranker P95 latency, per batch size — a regression here is a model-complexity or serving-fleet signal, tracked separately from retrieval latency so the two never get blended into one misleading "backend latency" number.
    • Feature hydration P95 — Redis latency above 5ms indicates either an overloaded feature store or a hot-key concentrating load on one shard.
    • Feed CTR and completion rate / dwell time, tracked per experiment group — the primary engagement and quality metrics from Concept 5's A/B testing discipline.
    • Diversity index, P25 across the user base — the filter-bubble early-warning signal; a sustained drop is the trigger for Concept 5's explore-exploit and MMR interventions, not something to notice only after retention has already declined.
    • Cold-start CTR ratio — new-user CTR relative to established-user CTR; the requirement in this chapter's Requirements section sets a 0.7× floor, and this metric is how a regression against that floor is caught.
    • Explanation cache hit rate — a low hit rate means the LLM is being invoked more often than the lazy-generation design intends, the first signal of a cost overrun before the daily spend number itself moves.
    • LLM reranker invocation rate — the fraction of requests carrying explicit intent; a sudden spike is either a genuine product-usage shift or a client-side bug sending intent text on every request, and the two require very different responses.

    Security Layer¶

    • Right-to-deletion. Interaction history reveals preferences, and sometimes health or political interests by implication; on account deletion, purge interaction history from the feature store, training pipeline, and item co-occurrence tables within 30 days. Deleting embeddings from the ANN index itself is expensive (Chapter 24's vector-deletion mechanism is lazy-tombstone-then-compact); maintain a deleted-user filter at query time in the interim rather than blocking deletion on a full index rebuild.
    • Model inversion. The query tower's embedding is a dense, queryable representation of a user's preferences and could itself be probed to infer sensitive interests. Never expose raw query embeddings in an API response — /feed returns item IDs and scores only, never the vector that produced them.
    • Cross-user contamination. A shared Redis feature store with a misconfigured key structure could serve one user's features to another's request. Enforce strict user_id namespacing in the key schema and verify it at the feature server layer, not only at the API gateway — the same defense-in-depth principle RAG System applies to its own tenant-scoped retrieval filters.
    • Recommendation manipulation. An adversary controlling item metadata could craft content engineered to surface in recommendations it has no organic claim to. Run new or changed item content through a policy classifier before it enters the corpus the item tower embeds — a gate at ingestion, not a filter applied after the fact to whatever the ranker already surfaced.

    Failure Handling¶

    Failure Degradation strategy
    ANN retrieval unavailable Fall back to a cached popularity-ranked candidate set rather than failing the request — degraded personalization beats no feed, the same principle RAG System applies to its own retrieval-outage fallback
    Neural ranker timeout or GPU fleet overloaded Serve candidates in raw ANN similarity order, skipping ranking — a quality regression, not a correctness failure
    Feature store (Redis) latency spike or partial unavailability Serve with population-level default features for the affected users or items rather than blocking the request; flag the response as degraded for observability, don't silently absorb it
    LLM reranker (4c) times out or is unavailable Skip reranking, serve the neural ranker's top-10 directly — explicit intent goes unaddressed for that request, but the feed still returns within the default-path latency budget
    Explanation generation (4b) fails Serve the recommendation without an explanation; the explanation endpoint is additive and non-blocking by design, so its failure never delays or breaks the underlying feed
    Cold-start intent LLM call (4a) fails at sign-up Fall back to popularity-based recommendations for that user until enough interaction history accumulates for the query tower to operate normally — the pre-LLM baseline this system had before Concept 4a existed
    Item tower rebuild fails mid-run Old embeddings remain live throughout, per Concept 1's atomic-swap design; the failed rebuild simply doesn't swap in, and retrieval continues serving the last known-good embedding set
    MMR diversity filter fails Skip the diversity constraint, serve the neural ranker's raw top-10 — a filter-bubble risk that accumulates over days, not an immediate correctness failure, so it degrades gracefully rather than blocking
    Training pipeline falls behind (model staleness) Continue serving the last successfully-trained model; alert on model age past a threshold (for example, 10 days without a successful retrain) as a first-class incident

    Tradeoff Analysis¶

    flowchart TD
    Q1{"Catalog size\nvs cross-encoder cost?"} -->|"Under 100K items"| CE["Cross-encoder feasible\nhigher recall, O of N cost"]
    Q1 -->|"100M plus items"| TT["Two-tower required\n5 to 10 percent recall tradeoff"]

    Q2{"Candidate set size K\nat retrieval?"} -->|"Larger K"| MoreRecall["Higher ranker recall\nmore feature hydration cost"]
    Q2 -->|"Smaller K"| Cheaper["Lower cost\nrisk missing best items"]

    Q3{"Multi-task weights?"} -->|"Engagement-weighted"| ClickHeavy["Higher short-term CTR\nclickbait drift risk"]
    Q3 -->|"Quality-weighted"| Retention["Higher 30-day retention\nlower short-term CTR"]

    Q4{"Diversity lambda\nin MMR?"} -->|"High lambda, 0.9"| RelevanceFocus["Maximizes session CTR\nnarrower filter bubble risk"]
    Q4 -->|"Low lambda, 0.6"| DiversityFocus["Reduces filter bubble\nimproves 30-day retention"]
    1. Two-tower versus cross-encoder retrieval. A cross-encoder gives higher recall by seeing the full user-item interaction, but requires O(N) forward passes — viable only for catalogs under roughly 100K items. Two-tower retrieval scales to 100M-item catalogs at the cost of 5–10% recall degradation, recovered only partially by the ranker downstream. This is not a close call at this chapter's catalog size; it is Concept 1's entire argument.
    2. Retrieval candidate set size, K. A larger K gives the ranker more to choose from and improves eventual recall, but costs more in feature hydration and ranker compute — both linear in K. A smaller K is cheaper but risks the globally best item never reaching the ranker at all. The precision-recall knee for most catalogs sits around K = 500–2,000; this chapter's K = 1,000 default sits inside that range.
    3. Multi-task weight tuning. Raising the engagement weight improves short-term CTR and risks the clickbait drift the multi-task framing exists to prevent; raising the quality weight improves retention at some short-term CTR cost. The holdout group from Concept 5 is the only reliable instrument for resolving this — a 30-day retention comparison across weight configurations, not a same-day CTR readout, because same-day metrics cannot see the retention effect at all.
    4. Explanation generation scope. Eager generation for every user and every item is $3M/day-class spend; lazy, view-triggered generation is roughly 12× cheaper at $250K/day; a power-user-plus-template hybrid pushes below $50K/day at minimal measured quality loss, since users who never view an item never notice its absence anyway. This is Cost Model's single highest-leverage lever, restated here as a design tradeoff rather than a cost line.
    5. Diversity constraint strength, λ in MMR. High λ (relevance-focused, ~0.9) maximizes same-session CTR; low λ (diversity-focused, ~0.6) reduces filter-bubble formation and improves 30-day retention at some immediate-session cost. Like the multi-task weights above, this needs a long-duration A/B experiment (4+ weeks minimum) to resolve, because the retention effect the low-λ setting is meant to produce is by definition invisible in a short window.

    Interview Discussion¶

    "Design a recommendation system" tests whether a candidate understands the funnel architecture as a computational necessity, not a stylistic choice. The first filter is whether the candidate can explain why retrieval uses embedding similarity rather than a neural ranker, and why ranking then uses a neural ranker rather than a simple lookup — a candidate who jumps straight to "train a recommendation model" without naming the compute constraint that forces a multi-stage cascade (the cross-encoder-at-100M-items arithmetic from Concept 1) has missed the question's central insight.

    The second filter is training-serving skew. A strong candidate states, unprompted, that the feature store must produce byte-identical features offline and online, and can explain concretely what breaks when it doesn't — a silent accuracy gap between offline eval and production that no error log will surface. A weaker candidate describes training and serving as two systems that both happen to compute features, without ever naming the consistency requirement between them.

    The third filter is feedback loops. "Add diversity" is not an answer; a strong answer names the filter-bubble formation mechanism specifically (the recommender's own prior output confounding the next round's engagement signal), proposes explore-exploit scheduling with a named mechanism (Thompson sampling over category posteriors, not uniform random), names the diversity index as the detection metric, and states the MMR reranking constraint that enforces it at serving time — then names the tradeoff against immediate engagement rather than presenting diversity as a free improvement.

    Staff-level probe: "Session CTR has been flat or improving for six months, but 30-day retention is declining. What's happening, and how do you diagnose it?" This divergence is the signature of the filter-bubble-plus-clickbait trap: the ranker has learned to surface content that generates a click without producing satisfaction, and users are exhausting their narrow interest band before the system surfaces anything new to sustain their engagement. Diagnosis in order: check whether the diversity index is narrowing over the same window; check whether completion rate and dwell time are declining alongside retention (if CTR is flat but completion is falling, the model is optimizing the wrong signal); and check the holdout group's retention specifically — if the holdout is also declining, the cause is external (seasonal, competitive) and no amount of model tuning will fix it; if the holdout is flat while the treatment population declines, the model updates over that period are the cause. The fix, once isolated to the model: reduce the engagement weight and raise the quality weight in the multi-task score, and increase the explore-exploit ε.

    Staff-level probe: "New-user cold-start CTR is 30% of established-user CTR. What are the levers, and what do they cost?" Three, in order of investment required. First, LLM semantic intent embedding (Concept 4a) — gains 10–20 percentage points but requires collecting an explicit preference statement at sign-up, adding sign-up friction that has its own conversion cost. Second, popularity-based fallback retrieval for new users — cheap to implement, high raw CTR, but every new user with similar demographics sees nearly the same feed, which is not really personalization and caps how much this lever alone can close the gap. Third, cold-start augmentation during two-tower training — randomly zeroing out portions of user history during training so the query tower is forced to perform well on sparse features, a training-methodology change rather than a serving-time patch, but the one that improves the model's underlying cold-start generalization rather than working around its absence. The right answer names all three and orders them by the lever a staff engineer would actually pull first: lever 1 for immediate impact if the UX cost is acceptable, lever 3 as the durable investment, lever 2 as the cheap stopgap that should not be mistaken for a real fix.

    See How AI System Design Interviews Work for how this diagnostic-reasoning expectation — isolate the mechanism before proposing the fix — generalizes across every case study in this book, not just this one.
