    AI Notification System — System Design Case Study¶

    Every other chapter in Case Studies designs a pull system: a user opens an app, types a question, or requests a feed, and the system responds. ChatGPT waits for a prompt. AI Search Engine waits for a query. Even AI Recommendation System, which feels proactive because the feed appears the instant the app opens, is still triggered by the user's own action of opening the app. This chapter is the only pure push system in the book: the system decides, unprompted, based on its own models, to interrupt a user who has not asked for anything in that moment. That inversion changes every design constraint that follows.

    In a pull system, a mediocre response costs the system very little — the user simply tries again, rephrases, or scrolls past. In a push system, a poorly timed, irrelevant, or too-frequent notification costs the system something it cannot get back: the user disables the channel, or worse, uninstalls the app. Every notification sent is a debit against a finite, slowly-replenishing trust budget the user has extended to the product. A system that sends at whatever rate its upstream event producers generate — an order ships, so send; a friend posts, so send; a price drops, so send — will exhaust that budget, at which point the channel itself, not any individual notification, has failed. This chapter is built around the thesis that fatigue management is not a feature bolted onto a notification system — it is the constraint that makes the system a system rather than an unthrottled event-to-message pipe. Send-time optimization and per-user preference learning exist to spend that same trust budget more efficiently, but fatigue management is what stops the budget from going negative in the first place.

    The second distinction worth naming up front: this is the only chapter in the book that routinely talks to three independent external channel providers — APNs and FCM for push, SendGrid or SES for email, Twilio for SMS — each with its own delivery semantics, its own regulatory regime, and its own failure modes. AI SDR already built the compliance architecture this chapter reuses for outbound email: a synchronous, blocking opt-out check ahead of every send, CAN-SPAM fields enforced at the template layer, GDPR legitimate-interest documentation. Chapter 19 operates at B2B scale — thousands of prospects, one channel, a human sales rep in the loop for anything ambiguous. This chapter operates at consumer scale — millions of users a day, four channels, no human in the loop for any individual send — so the same compliance pattern has to run as a hard, low-latency gate inside a real-time pipeline rather than a batch job a compliance officer reviews weekly. Where Chapter 19's deliverability mechanics (domain warming, bounce-rate monitoring, SPF/DKIM/DMARC) apply unmodified to this chapter's email channel, they are not re-derived here — this chapter's detailed design starts at the point that is genuinely new: deciding whether, when, and through which channel to reach a user who did not ask to be reached.

    Requirements¶

    Functional

    • Receive notification trigger events from upstream services — order management, content platform, marketing automation — each carrying an event type, a target user, a priority tier, and a payload.
    • Route each triggered notification to the correct channel based on priority, learned per-user channel preference, and real-time channel availability (token validity, provider health).
    • Schedule delivery at the per-user optimal send time for non-urgent notifications, while delivering urgent notifications immediately regardless of the send-time model's output.
    • Generate or select personalized content for every send, bounded by hard per-channel length limits (a push title has 50 characters; there is no soft version of that constraint).
    • Track delivery status and engagement for every send, from queued through sent to engaged, expired, bounced, or opted_out.
    • Enforce fatigue caps and opt-out lists before every send, as a blocking gate no priority tier below Critical can bypass.
    • Provide a campaign management API for batch, audience-scoped sends that reuse the same per-user scheduling and fatigue infrastructure as individually triggered notifications.

    Non-functional

    Requirement Target Why this number
    Critical notification delivery latency < 5 seconds end-to-end A compromised-account alert or a failed payment is time-sensitive by definition; the 5-second budget is sized to leave no meaningful window between the triggering event and the user's awareness of it
    Standard notification delivery within 1 hour of the scheduled optimal send time The send-time model picks a target hour, not a target instant; a 1-hour SLO absorbs queue depth and worker scheduling jitter without meaningfully missing the engagement window the model optimized for
    Deduplication zero duplicate sends for the same notification_id Upstream event producers deliver at-least-once (Kafka replays, retried webhooks); a duplicate send is not a minor annoyance here, it is the exact behavior that erodes the trust budget this chapter is built around
    Opt-out processing latency < 60 seconds Same discipline as AI SDR's opt-out SLO, tightened for consumer scale and multi-channel exposure — TCPA and GDPR both treat a slow opt-out as a live compliance liability, not a UX nicety
    Throughput 10M notifications/day across all channels Sized to a 100M-registered-user consumer platform at moderate per-user notification volume (Capacity Planning)
    Delivery tracking completeness > 99% of sends have a status record The fatigue score, send-time model, and channel preference score are all trained on delivery and engagement events; missing status records don't just hurt observability, they silently corrupt every downstream model

    Explicitly out of scope: the client applications and SDKs that render notifications and report engagement back (assumed to exist and to call this system's APIs correctly); the upstream services that emit trigger events — order management, content platform, marketing automation — whose own correctness (did the order actually ship?) is a separate system's concern; content moderation of notification copy for prohibited categories, which is a trust-and-safety system with a different objective function than deliverability or engagement; sponsored or advertiser-funded push, which optimizes an auction-cleared price alongside relevance and would compete with, not cooperate with, this chapter's fatigue-budget model if mixed into the same queue undifferentiated.

    Capacity Planning¶

    Sized for a consumer platform with 100M registered users sending 10M notifications/day — a moderate ~0.1 notifications/user/day blended across a base where most users receive zero to a few notifications daily and a smaller active cohort receives several.

    Step Assumption Result
    Total daily notification volume Per throughput NFR 10M/day ≈ 115/second average
    Peak factor Business-hours concentration across time zones, campaign bursts ~5x average
    Peak throughput 115/second × 5 ~500/second peak
    Channel split 60% push, 30% email, 10% SMS 6M push / 3M email / 1M SMS per day
    Push provider capacity FCM/APNs sustain well beyond 500/second via HTTP/2 connection pooling 10-worker fleet with pooled connections handles the full peak with headroom
    Email provider capacity SendGrid at 3M/day = ~35/second Within a single dedicated warmed IP's capacity — no domain-pool scaling problem the way AI SDR's cold-outreach volume requires, because this is consented, transactional-adjacent mail, not cold outbound
    SMS provider capacity Twilio at 1M/day = ~11.5/second A single long-code pool covers transactional SMS; marketing SMS at this volume moves to a 10DLC or short-code registration for throughput and carrier-filtering reasons
    Idempotency store (Redis) 10M notification_ids/day × 7-day TTL × ~100 bytes/key ~70M keys ≈ 7GB — fits a single replicated Redis instance

    The number that should not anchor this system's sizing is raw send throughput — 500/second peak is trivial by the standards of any inference-serving system in this book. The actual engineering effort goes into the gates that sit in front of every one of those 500 sends: a fatigue check, an opt-out check, and a channel-availability check, each of which has to complete in single-digit milliseconds without becoming the bottleneck a naive read of the throughput number would miss entirely.

    Scale Estimation¶

    Scheduled delivery queue depth. At 10M notifications/day with roughly an 18-hour delivery spread (the send-time model's natural effect, developed in Concept 2): ~10M ÷ 24 × 18 ≈ 555K notifications resident in the delivery queue at any given moment. A Redis sorted set at 555K entries × ~200 bytes/entry ≈ 110MB — trivial.

    Send-time model update volume. 10M sends/day, each producing roughly one histogram-bin update per send (was this notification engaged within 60 minutes of this hour/day-of-week bin) plus a handful of read-side engagement events: ≈ 10-15M histogram writes/day ≈ 115-175 writes/second, well inside a single Redis or Cassandra cluster's capacity.

    LLM content generation cost. Roughly 5% of sends (500K/day) use online, per-user LLM generation (Concept 4) rather than offline templates; at ~300 tokens average per call and Haiku-class pricing (~\(0.0025/1K input tokens): 500K × 300 tokens = 150M tokens/day ≈ **~\)375/day**. The other 95% of sends (9.5M/day) go through template slot-filling with no LLM call in the hot path — sub-millisecond, effectively free at the margin.

    Critical-path latency budget (payment failed → push delivered):

    Stage Latency
    Trigger event ingest, Kafka to Trigger Processor ~50ms
    Idempotency check (Redis SETNX) ~2ms
    Opt-out list check ~5ms
    Fatigue gate (Critical bypasses the cap, but the score read still runs for logging) ~5ms
    Channel Router: priority-tier dispatch, no send-time scheduling for Critical ~5ms
    APNs/FCM HTTP/2 send ~200-800ms
    Total well under the 5-second Critical NFR, with headroom for the SMS fallback path if push delivery confirmation doesn't arrive

    Campaign delivery spread. A campaign targeting 10M users, with 40% of users' optimal window falling in the 7-9 PM local slot: sending all 10M at a single fixed UTC time would produce a 5M-send spike inside a 2-hour window against the channel providers' rate limits. With per-user optimal-time scheduling, the same 10M sends spread across roughly 18 waking hours per time zone — on the order of 500K/hour rather than 5M/hour, an order of magnitude reduction in peak load with no change to total volume or to the providers' aggregate daily quota.

    Four stages, each independently scalable. Ingestion: a Trigger Processor reads from the notification.triggers Kafka topic, computes the deterministic notification_id, and runs it through deduplication, the opt-out check, and the fatigue gate — three sequential blocking checks that together decide whether this notification is allowed to exist at all. Scheduling: notifications that pass the gates and aren't urgent enter a time-indexed delivery queue keyed on the send-time model's output. Dispatch: delivery workers pull due notifications, resolve the channel via the Channel Router's priority and preference logic, fetch or generate content, and send to the appropriate provider. Tracking: provider callbacks and client-side engagement events flow back into a Notification Events store, which feeds the fatigue score and send-time histogram that gate and schedule tomorrow's notifications — the dotted feedback edges in the diagram above are what make this a closed loop rather than a one-way pipe, the same feedback-loop shape AI Recommendation System manages for engagement signal, applied here to send rate rather than send content.

    The three gates in the ingestion stage are drawn as sequential, blocking steps deliberately, in the same spirit as AI SDR's spam-check-then-opt-out-check sequence: deduplication protects against a mechanical failure (Kafka's at-least-once delivery), the opt-out check protects against a legal violation, and the fatigue gate protects against the slower-burning failure this chapter is centrally about — a technically legal, technically correct notification that still degrades the channel because it arrived as the fourth one that hour.

    Detailed Design¶

    Concept 1 — Fatigue management: the self-regulating constraint¶

    A notification system without fatigue management sends at whatever rate its trigger events generate. That rate has no natural ceiling — an active e-commerce user might plausibly generate "order shipped," "item delivered," "review reminder," "price drop on a saved item," and "abandoned cart" events all in the same day, each individually legitimate and each individually justified by its own upstream service. Fatigue management is the mechanism that treats these as draws against a shared, finite budget rather than five independent, unrelated decisions.

    The engagement budget model. Each (user, channel) pair has an implicit tolerance — the send rate above which engagement drops and opt-out probability rises. This tolerance is not fixed and not uniform: a power user who opened 15 of the last 20 push notifications tolerates a materially higher rate than a passive user who opened 1 of 20. Track it as a rolling engagement rate:

    engagement_rate(user, channel) = Σ(engaged events, last 30 days) / Σ(sent events, last 30 days)

    mapped to a recommended daily cap:

    Engagement rate Recommended daily cap (push)
    > 50% Up to 8/day
    20–50% Up to 4/day
    5–20% Up to 2/day
    < 5% 1/day or quiet period

    The cap is a soft constraint for Critical notifications — a compromised-account alert sends regardless of how many notifications this user has already received today — but a hard one for Standard and Low priority: once the daily cap is reached, further Standard/Low notifications are queued for the next day or dropped outright if they expire before then. This asymmetry contrasts deliberately with how AI SDR's opt-out list applies uniformly to every send regardless of priority; fatigue enforcement here is priority-aware by design, because a locked-out account is a different kind of urgency than a promotional nudge, and treating them identically would either annoy users with Critical alerts suppressed by an unrelated promotional cap, or let promotional volume hide behind a Critical-notification exemption.

    Fatigue score with decay. Daily capping alone misses a real failure mode: three notifications inside one hour, each individually under the daily cap, that still read as a burst to the user. A decaying score catches this:

    • On send: fatigue_score += send_weight(priority, channel)
    • On time passage: fatigue_score *= decay_factor ^ hours_elapsed
    • If fatigue_score > fatigue_threshold(user): suppress the next Standard notification, even with daily count still under the cap.

    The score lives in Redis with a 7-day TTL — inactivity auto-expires it rather than requiring an explicit cleanup job — and updates via INCR plus EXPIRE so concurrent notification events for the same user resolve atomically rather than racing on a read-modify-write.

    Quiet period escalation. A user who hasn't engaged with any notification in 14 consecutive days enters a quiet period: only Critical and High priority notifications send. After 7 more days with no engagement, the quiet period tightens to Critical-only. After 21 total days with no engagement, the user is flagged notification-disengaged and all non-Critical notifications are suppressed indefinitely — until the user next opens the app, which resets both the disengagement flag and the fatigue score. This escalation exists because a user who has stopped engaging has, functionally, already opted out; continuing to send to them accomplishes nothing except accelerating the formal opt-out this chapter's compliance layer (Concept 5) is built to avoid triggering unnecessarily.

    flowchart LR
    SEND["Notification Sent"] --> INCR["Increment fatigue_score\nby send_weight"]
    INCR --> STORE["Store in Redis,\nTTL 7 days"]
    STORE --> DECAY["Time Passage:\ndecay fatigue_score\nby elapsed hours"]

    The two loops in this diagram are doing different jobs: the left loop (send → decay → check) catches short-window bursts inside a single day; the right loop (14/21-day escalation) catches slow-burning disengagement that a daily cap or an hourly decay would never see, because a user receiving exactly 1 notification/day, every day, for three weeks, with zero engagement, never trips either of the other two mechanisms.

    Concept 2 — Send-time optimization: the per-user temporal engagement model¶

    When a notification arrives matters nearly as much as what it says. The same "your order shipped" notification sent at 11 PM local time reaches a user who is probably asleep; sent at 7 PM, the same content sees a 3-5x higher engagement probability in typical consumer-app data.

    Feature set. Historical app-open times, binned by (hour_of_day, day_of_week), are the strongest signal — the distribution of when a user opens the app at all is the best proxy for when they're receptive to anything. Historical notification-engagement times are a more direct but sparser signal. Device activity (screen-on events, foreground SDK signals, where available) indicates the device is in active use right now. Time zone is a hard constraint, not a model feature — a notification never sends before 8 AM or after 9 PM local time regardless of what the model predicts, the same non-negotiable floor Concept 5's TCPA compliance enforces for SMS specifically. Day-of-week matters because weekday and weekend engagement windows genuinely differ. And notification category gates whether send-time optimization applies at all: urgent categories (price alerts, security events) bypass it and send immediately; informational categories (weekly digest, feature announcements) wait for the optimal window.

    Model architecture. A lightweight per-user model estimating P(engage | send_at_hour, day_of_week) — a Bayesian histogram of engagement and send counts per (hour, dow) bin, with Laplace smoothing for sparse bins, is sufficient here and preferable to a deep model for a reason worth stating plainly: it's interpretable (a support engineer can read the histogram and see why 7 PM was chosen), it updates online with a single increment per new data point rather than requiring batch retraining, and at the per-user granularity this operates at, a neural model would be badly overparameterized relative to the handful of data points any single user contributes per week. New users with no history fall back to a population-level model — global engagement probability by hour, segmented by time zone and coarse demographics — the same cold-start discipline AI Recommendation System applies to new users with no interaction history via its intent-embedding fallback, applied here to new users with no send history instead.

    Training is implicit: every send produces one example, (sent_at_hour, day_of_week, was_engaged_within_60_min), and the relevant (hour, dow) bin count updates on arrival — the histogram is a sufficient statistic, so there's no separate offline retraining job to schedule or fall behind on.

    Scheduled delivery queue. For a non-urgent trigger: query the model for the highest-probability hour in the next 24 hours; set send_at to that hour today, or tomorrow if today's window has already passed; insert into a Redis sorted set keyed by send_at Unix timestamp, with a TTL matching the notification's own expiry. A delivery worker polls with ZRANGEBYSCORE queue 0 {now}, dequeues due entries, and hands them to the Channel Router. Every queued notification also carries an expires_at; the worker skips anything already expired (a "flash sale ends at midnight" notification has no business arriving at 9 AM the next day), and a background job sweeps expired entries out of the sorted set hourly so the queue doesn't accumulate dead weight.

    Batch campaigns get the spread for free. Because each user's optimal hour is computed independently, a campaign targeting millions of users naturally spreads its sends across the day rather than firing as a single spike — the arithmetic is worked out in Scale Estimation above, and it is a side effect of per-user scheduling, not a separate load-shedding mechanism that has to be designed on top of it.

    Concept 3 — Multi-channel routing: priority tiers, channel selection, and fallback¶

    Channel Engagement rate Cost Regulatory burden Delivery confirmation Use case
    Push (APNs/FCM) 5–15% ~$0.001/send Low — user controls opt-in at OS level Device receipt, not user engagement App-context, timely, short-form
    Email 1–3% open rate $0.001–0.01/send CAN-SPAM, GDPR Bounce + open-tracking pixel Rich content, receipts, legal comms
    SMS 45–98% read rate $0.01–0.05/send TCPA — explicit written consent, 8 AM–9 PM window Carrier delivery receipt Urgent, high-value, OTP, critical alerts
    In-app N/A, user already active $0 None Direct — user is in the app Real-time contextual, low-priority

    SMS's read rate is the highest of any channel by a wide margin — and its regulatory burden and per-send cost are also the highest, which is precisely why it is reserved for the notifications that most need to land (Cost Model and Tradeoff Analysis both return to this asymmetry).

    Priority tiers.

    Priority Trigger examples Channel strategy Latency
    Critical Account compromised, payment failed, OTP Push + SMS in parallel; SMS only if no valid push token < 5 seconds
    High Order shipped, appointment in 2 hours Push primary; email fallback if undelivered after 2 minutes < 5 minutes
    Standard New content available, friend request Best channel per learned preference; scheduled for optimal time Next optimal window
    Low Re-engagement, promotional Email or in-app only; business hours only Batch delivery

    Channel preference learning. Preference is inferred from engagement history, not just from self-reported settings. A push engagement rate above 20% against an email engagement rate under 2% marks a user push-preferred. An absent or invalid push token (OS-level disable, app uninstall) marks a user email-preferred by default, regardless of history. Active email opt-out narrows the field to in-app, or SMS for Critical only. A user opted out of every channel still receives Critical notifications through whichever channel remains opted in — Critical delivery is the one guarantee this system does not treat as negotiable by preference. Preferences are stored as a per-user channel-score vector, scoped per notification category (a user might be push-preferred for social notifications and email-preferred for receipts), and the Channel Router reads these scores for Standard/Low routing; Critical routing ignores preference entirely and always reaches for the highest-reliability channels available.

    Fallback with circuit breakers. For High priority: send via push, start a 2-minute timer, and if no delivery confirmation arrives — device offline, token invalid — fall back to email. If email also fails (bounce), log and alert for High; for Critical, escalate further to SMS. Independently, a circuit breaker watches each channel provider: if the push provider's error rate exceeds 5% over a 60-second window, the breaker opens and new sends route directly to the fallback channel until the provider recovers, rather than queuing behind a provider that is currently failing. Push token hygiene closes the loop — APNs and FCM return explicit error codes (InvalidRegistration, NotRegistered) for dead tokens, and on receipt the token is invalidated immediately in the user's channel profile; continuing to attempt delivery to a token from an uninstalled app wastes API calls and, worse, makes the send look successful in metrics that never distinguish "API accepted the request" from "a human saw a notification."

    STDBREAKER -->|"No"| STDSEND["Send via preferred channel"]

    LOW --> LOWSEND["Batch delivery,\nspread across optimal times"]

    Concept 4 — LLM content personalization: bounded generation within channel constraints¶

    An LLM adds real value transforming structured event data (order_id, item_name, delivery_date) into copy that reads as written for this person, not filled into a form — and generating A/B variants at a fraction of a copywriting session's cost. It adds no value in channel selection, routing, or send-time decisions — those are ML and systems problems, not language problems, and running an LLM over them would be the wrong tool applied for its own sake. The constraint that makes this application of an LLM different from every other one in this book: a push title has a hard 50-character limit, and a mobile email subject line has a hard 60-character limit. These are not soft guidelines the way tone or style are — they are truncated by the OS or the client regardless of what the model produces.

    Two-tier generation architecture. For high-volume notification types (>100K sends/day): generate templates offline, once, per (notification_type × user_segment) combination — "Your {{item_name}} ships {{relative_delivery_date}}." — and at send time, fill the slots from event data with no LLM call in the hot path, at sub-millisecond latency. For low-volume, high-personalization types (<1K sends/day — anniversary messages, milestone alerts, AI-curated digests): call the LLM online, at send time, with full user context, and cache the result per (user_id, notification_id) for the notification's validity window. This mirrors the eager-versus-lazy generation tradeoff AI Recommendation System resolves the same way for its own personalized explanation generation — generate broadly and cheaply by default, reserve per-call LLM generation for the volume tier where personalization actually moves the outcome.

    Prompt structure for the online path:

    System: Generate a push notification for {platform_name}.
        Hard limits: title <= 50 characters, body <= 120 characters.
        Tone: {friendly|urgent|informational} based on {segment}.
        No clickbait. No exclamation marks in title. Emoji: {allowed|prohibited}.
        Output JSON: {"title": "...", "body": "...", "cta": "..."}

User: Event type: {event_type}
      User context: {user_tier}, {days_since_join} days, last opened {days_since_last_open} days ago
      Event data: {event_payload}

    Post-generation validation is not optional. LLMs do not reliably count characters, so every output is checked programmatically after generation — len(title) <= 50, len(body) <= 120 — and a violation truncates at the last complete word with a trailing ellipsis if the cut is visible, rather than triggering a regeneration call. Truncation costs nothing in latency; a round-trip regeneration on the send-time critical path costs real milliseconds for a marginal quality gain that does not justify the latency, so the system accepts a slightly worse string over a slower one. This is the same instinct as validating LLM output against a schema before it reaches a caller, applied here as a length constraint instead of a structural one — see Structured Output & Grammars for the general pattern.

    A/B variant testing runs on every new notification type by default. Prompt the LLM for 5 copy variants with distinct emotional hooks — curiosity, urgency, benefit-focused, social proof, FOMO — launch at 20% traffic each, and after 72 hours and a minimum sample size, promote the highest-engagement variant to production. Copywriters define the hook taxonomy; the LLM generates within it; the A/B loop selects the winner without a human in that final step.

    Concept 5 — Delivery guarantees, deduplication, and regulatory compliance¶

    A system that sends duplicate notifications, drops Critical alerts, or violates an opt-out has failed at its job regardless of how well-tuned the ML underneath it is.

    Exactly-once delivery via idempotency keys. notification_id = hash(trigger_event_id + notification_type + user_id) is deterministic — the same trigger, replayed by Kafka's at-least-once delivery or a manual debug re-run, always produces the same ID. Before any send attempt: SET notification_id "in_progress" NX EX 600. A null result means another worker already owns this send; skip. An OK result means this worker owns it; proceed. On successful send, the key updates to "sent" with a 7-day TTL, which is what prevents a later Kafka replay of the same trigger event from re-sending. On a confirmed non-retryable failure, the key updates to "failed" and the system does not retry — a distinct terminal state from "sent", so a downstream replay doesn't confuse a deliberate non-retry with a race it should resolve.

    Delivery status tracking. Every send writes a notification_event record and transitions through queued → sent → (engaged | expired | bounced | opted_out):

    {
  "notification_id": "sha256:abc123",
  "user_id": "u_456",
  "channel": "push",
  "template_id": "order_shipped_v3",
  "sent_at": "2026-07-01T18:00:00Z",
  "channel_message_id": "apns:xyz789",
  "status": "sent",
  "engaged_at": null,
  "engagement_type": null
}

    The engagement event — a notification open, a link click — arrives via the app SDK or the email tracking pixel, updates this record, and increments the counters Concept 1's fatigue score and Concept 2's send-time histogram both read from. Every model in this chapter is, ultimately, downstream of this table being complete — the > 99% completeness NFR in Requirements is not a vanity metric, it's the floor below which the fatigue and send-time models start training on a biased, incomplete signal without any error surfacing to say so.

    SMS (TCPA). Explicit written consent is required before any marketing SMS, recorded with timestamp, the consent text shown, IP address, and user_id — a non-deletable legal record. An opt-out reply ("STOP") is processed within 60 seconds: add to the opt-out list, send one confirmation reply, never send marketing SMS again. This check is synchronous and blocking before every SMS send — the identical discipline AI SDR applies to its global email opt-out list, reused here for a second channel and a second statute. Time-of-day is enforced 8 AM–9 PM local, defaulting to UTC+0 (the most conservative choice) if time zone is unknown. Transactional SMS (OTP, security alerts) is exempt from the marketing restriction but not from an all-SMS opt-out; two separate lists — sms_marketing_optout and sms_all_optout — exist because a user who tells their carrier to block all SMS from this sender must never receive any SMS, transactional included.

    Email (CAN-SPAM / GDPR). Every marketing email carries a one-click unsubscribe link, honored immediately on click, well inside CAN-SPAM's 10-business-day legal floor. The append-only suppression list from AI SDR is checked synchronously before every marketing send here too. Transactional email (order confirmation, password reset) needs no opt-in under GDPR's legitimate-interest basis; marketing email does. Two lists again: email_marketing_unsubscribed and email_all_bounced — a hard-bounced address is invalid, and continuing to send even transactional email to it is pure waste plus a deliverability-reputation cost.

    Push. No statutory floor equivalent to TCPA or CAN-SPAM applies, but the same discipline holds by product convention: disabling push in-app writes synchronously to the preference store, and every worker checks that store before dispatch. A user who denies the OS-level push permission prompt is never re-prompted for at least 90 days — repeated re-prompting after an explicit denial is exactly the kind of behavior that spends trust-budget on the permission itself before a single notification has even been sent.

    Data Flow¶

    Path 1 — Critical priority, push fails, SMS fallback delivers:

    sequenceDiagram
    participant SVC as Order Service
    participant TP as Trigger Processor
    participant DEDUP as Idempotency Store
    participant SUP as Opt-Out List
    participant ROUTE as Channel Router
    participant APNS as APNs
    participant TWILIO as Twilio
    participant EVT as Notification Events

    SVC->>TP: payment_failed event
    TP->>DEDUP: SETNX notification_id
    DEDUP-->>TP: OK, this worker owns the send
    TP->>SUP: check push and SMS opt-out
    SUP-->>TP: clear
    TP->>ROUTE: priority Critical
    ROUTE->>APNS: send push
    ROUTE->>TWILIO: send SMS in parallel
    APNS-->>ROUTE: delivery failed, invalid token
    TWILIO-->>ROUTE: delivered
    ROUTE->>EVT: write status, channel used is SMS

    Path 2 — Standard priority push, scheduled at the per-user optimal hour:

    sequenceDiagram
    participant SVC as Order Service
    participant TP as Trigger Processor
    participant FAT as Fatigue Store
    participant STM as Send-Time Model
    participant DQ as Delivery Queue
    participant WORK as Delivery Worker
    participant APNS as APNs
    participant EVT as Notification Events

    SVC->>TP: order_shipped event
    TP->>FAT: check daily cap and fatigue score
    FAT-->>TP: 2.1 sends today, cap is 4, proceed
    TP->>STM: query optimal send hour
    STM-->>TP: 19:00 local time
    TP->>DQ: insert, score is send_at timestamp
    DQ-->>WORK: dequeued at 19:00
    WORK->>WORK: template injection, item name and first name
    WORK->>APNS: send push
    APNS-->>WORK: 200 OK, apns-id returned
    WORK->>EVT: write sent status
    EVT->>FAT: engagement event updates score and histogram

    Both paths share the same idempotency and opt-out gates at the front, but they diverge immediately after: the Critical path skips fatigue capping and the delivery queue entirely and dispatches in parallel across two channels at once, while the Standard path routes through both the fatigue gate and the scheduling queue and dispatches through exactly one channel. That divergence is priority tier made concrete in code, not a special case bolted onto one shared path.

    Retrieval Layer¶

    This chapter is the rare one in Section 25 with almost no semantic retrieval in it — worth naming explicitly, in contrast to RAG System or AI Recommendation System, whose retrieval layers are the architectural center of those chapters. Three lookup surfaces exist here, and none of them is a vector search:

    Surface 1 — Fatigue, opt-out, and preference state. Point lookups keyed on (user_id, channel) against Redis: fatigue score, daily send count, opt-out status, channel preference vector. These are the highest-QPS reads in the system — every single trigger event touches all three before a send decision is made — and their entire design goal is sub-5ms point-lookup latency, the opposite optimization target from a nearest-neighbor search over an embedding space.

    Surface 2 — Template library. A parameterized template is selected by a deterministic composite key, notification_type × user_segment, not by similarity search — there is exactly one correct template for a given combination, not a ranked list of plausible ones.

    Surface 3 — LLM generation context assembly. For the ~5% of sends using online generation (Concept 4), the "retrieval" is structured context assembly — event payload, user tier, recency signals — pulled by ID from known tables, not a corpus search for relevant documents. There is no retrieval-quality problem here the way there is in a RAG system, because there is nothing to search: the inputs are fully specified by the trigger event and the user record.

    Agent Layer¶

    Not applicable in the sense the term is used for Deep Research Agent or the sequence manager in AI SDR: there is no planning loop, no multi-step tool use, and no LLM making a judgment call about what to do next. The pipeline — dedupe, opt-out check, fatigue check, route, schedule, dispatch, track — is a fixed sequence of deterministic gates and lookups executed once per trigger event. The channel router's fallback logic and circuit breaker are state machines with hardcoded transition rules (2-minute timer, 5% error-rate threshold), not autonomous choices a model makes about how much effort to spend — architecturally the same non-agentic classification AI Recommendation System gives its own serving cascade. The one LLM call that resembles a decision — online versus template content generation — is a static routing gate keyed on notification-type volume, decided at configuration time, not inferred per request; it is the same shape of gate as the tiered routing Multi-Model Serving & Routing describes generically, applied here as a volume threshold rather than a query-complexity score.

    Model Layer¶

    Tier Component Latency Key property
    1 — Fatigue scorer Rule-based scoring function over Redis-resident state, not a trained model < 5ms Deterministic and auditable by design — a user or a support engineer can be shown exactly why a send was suppressed, which a learned classifier here would make opaque for no accuracy benefit
    2 — Send-time model Per-user Bayesian histogram, P(engage \| hour, dow), Laplace-smoothed; population-level fallback for cold-start < 5ms read, incremental online update No batch retraining — the histogram is a sufficient statistic updated on every new data point
    3 — Channel preference scorer Per-user, per-category score vector derived from engagement history < 5ms Updated from engagement events, not from self-reported settings alone
    4 — Content generation LLM Haiku-class; offline batch generation for high-volume types, online per-call for low-volume high-personalization types Template injection < 1ms; online call 300–500ms Served through the same infrastructure LLM Inference System describes generically; the offline/online split is this chapter's own addition on top of that generic serving layer
    5 — A/B variant selection Fixed-split experimentation over LLM-generated copy variants N/A, statistical not real-time Promotion decision runs after a 72-hour window and a minimum sample size, not per-request

    Nothing in this table is a large model running on the send-time critical path for the 95% of traffic that goes through templates — the same discipline AI Recommendation System enforces by keeping every LLM off its default feed-refresh path, applied here to keep the median notification's total latency dominated by Redis lookups and an HTTP/2 call to a channel provider, not by inference.

    Observability Layer¶

    1. Delivery rate by channel — push target > 95% of sends reaching the device; email bounce rate tracked separately, with a hard-bounce rate above 2% triggering a domain-reputation review the same way AI SDR treats its own bounce threshold; SMS tracked via carrier delivery confirmation.
    2. Per-priority delivery latency — Critical P95 < 5 seconds, High P95 < 5 minutes, Standard P95 < optimal-hour + 1 hour — tracked as three separate SLOs, never blended, because a Standard-path regression should never page the same way a Critical-path regression does.
    3. Fatigue suppression rate — the fraction of triggered notifications the fatigue gate blocks. A spike here means either an upstream service is over-firing events or the fatigue thresholds need recalibration; either way, it's the earliest signal of a problem, well before opt-out rate would show it.
    4. Opt-out rate by channel — the leading indicator of channel-trust erosion, tracked weekly; a rising trend here precedes users uninstalling the app, not the other way around.
    5. Content generation failure rate — LLM calls that failed validation (length overrun) or timed out and fell back to a default template.
    6. Deduplication hit rate — the fraction of notification_ids already present in the idempotency store on arrival; should stay under 0.1%, and a spike signals Kafka replaying at an unusual rate upstream.
    7. TCPA window violation rate — required to be exactly zero; any SMS send outside the 8 AM–9 PM local window triggers a P0 alert, not a dashboard entry reviewed later.
    8. Campaign delivery completion time — for a 10M-user campaign, time from launch to last send; target under 4 hours given the send-time spread worked out in Scale Estimation.

    Security Layer¶

    Trigger event authorization. Any service publishing to notification.triggers can, in principle, trigger a notification for any user — so topic-level authorization scopes each producer to the notification types it's allowed to fire, and a user-level check verifies the target user_id belongs to a real, active account in a state consistent with the event (no "your order shipped" notification for a deleted account). Content injection. notification_payload fields arrive from upstream services and are sanitized before template injection — HTML stripped, character set limited, field-length capped — because a compromised upstream service is otherwise a direct path to injecting arbitrary content into a push notification body. Opt-out list integrity. The opt-out list is a legal record: append-only, no deletes except an audited legal-erasure request, replicated and backed up. A bug that truncates this list ahead of a campaign send is not a data-quality incident, it's a TCPA or GDPR violation — the same severity AI SDR assigns its own opt-out list. Tracking pixel privacy. Email open tracking uses a 1x1 pixel, and EU users who have not consented to engagement tracking under GDPR must not have that pixel embedded — a consent-aware flag per user strips it from their emails specifically, rather than relying on a single global toggle that can't represent per-user consent state.

    SMS is 10% of send volume and roughly 78% of total daily cost — the single most lopsided line in this table, and the direct financial expression of the channel-characteristics table in Concept 3: the channel with the highest read rate is also, by a wide margin, the most expensive and the most regulated, which is exactly why it's reserved for Critical notifications and used sparingly as a fallback rather than as a default.     Failure Handling¶

    Failure mode Detection Response
    Push provider (APNs/FCM) error rate spikes Rolling error-rate monitor, 60-second window Circuit breaker opens at > 5%; route new sends to fallback channel until the provider recovers
    Push token invalid or expired Provider error code (InvalidRegistration, NotRegistered) Invalidate the token in the user's channel profile immediately; stop attempting push to it
    Opt-out list unreachable at send time Health check / synchronous call timeout Block the send — fail closed, same discipline as AI SDR's opt-out-unreachable handling; queue and retry rather than sending on an inconclusive check
    Fatigue score store (Redis) unavailable Health check failure Fail toward suppressing, not sending — apply a conservative default cap for the affected user rather than allowing unlimited sends while the store is down
    Idempotency store (Redis) unavailable Health check failure Block new sends and alert; a duplicate-send risk here directly undermines the trust-budget thesis this chapter is built on
    Scheduled delivery queue (Redis sorted set) unavailable Health check failure Critical/High bypass the queue by design and are unaffected; Standard/Low notifications spill to a durable Kafka topic and retry once the queue recovers
    LLM content generation fails or times out Per-call timeout / validation failure Fall back to the last known-good template; never block the send waiting on generation
    SMS time-window check disagrees across timezone sources Dual-source cross-validation (see the staff-level probe below) Suppress the send and route to manual review rather than guessing which source is correct
    Trigger event replayed by Kafka Idempotency key already sent or in_progress Skip — this is the expected, designed-for case, not an incident

    Tradeoff Analysis¶

    flowchart TD
    Q1{"Notification priority?"} -->|"Critical or High"| BYPASS["Bypass send-time\noptimization, send now"]
    Q1 -->|"Standard or Low"| OPT["Schedule at\noptimal send hour"]

    Q2{"Fatigue threshold\ncalibration?"} -->|"Too aggressive"| LOWENG["High-value sends\nsuppressed, engagement drops"]
    Q2 -->|"Too lenient"| HIGHOPT["Opt-out rate rises,\nchannel trust erodes"]

    Q3{"Content generation path?"} -->|"High volume,\nover 100K per day"| TEMPLATE["Offline template,\nonline slot injection"]
    Q3 -->|"Low volume,\nunder 1K per day"| ONLINE["Online LLM call\nat send time"]

    Q4{"Fallback channel\nfor undelivered push?"} -->|"Critical"| SMSFALL["SMS fallback,\nhighest cost and compliance"]
    Q4 -->|"High"| EMAILFALL["Email fallback,\nlower cost and compliance"]
    1. Send-time optimization vs. delivery urgency. Scheduling improves Standard-notification engagement by 20-40% but adds up to 24 hours of delay. Critical and High bypass optimization entirely — the tradeoff is resolved by priority tier, hardcoded, not left to a per-notification judgment call.
    2. Fatigue suppression aggressiveness. Too aggressive, and high-value notifications get suppressed for genuinely active users, costing engagement and revenue signal for no channel-trust benefit. Too lenient, and opt-out rates climb. The right calibration point is found by watching engagement rate and opt-out rate together — optimizing send volume alone in either direction misses the actual objective, which is long-term reachability, not short-term throughput.
    3. Online LLM generation vs. offline templating. Online generation is maximally personalized at 300-500ms and ~$0.001/send; offline templates are near-zero latency and cost but less personalized. The resolution is volume-gated, not quality-gated by default: use online generation only where an A/B test has actually proven the personalization delta, and only at a volume low enough that the added cost stays negligible.
    4. Push token refresh cadence. Refreshing on every app open generates unnecessary write volume to the token store; refreshing too rarely lets tokens go stale after a reinstall, and delivery attempts fail silently. Refresh on app open only if the stored token is over 30 days old, and validate the full token set weekly against a batch provider endpoint.
    5. SMS as a fallback channel. SMS has the highest read rate of any channel but also the highest cost and the strictest regulatory regime (TCPA). Using it as a general fallback for undelivered push doubles compliance exposure — every fallback-triggered SMS is now subject to TCPA the same as a directly-triggered one. The resolution: SMS fallback is reserved for Critical priority only; High priority falls back to email, never SMS, keeping the highest-cost, highest-liability channel reserved for the sends that actually justify it.

    Interview Discussion¶

    "Design a notification system" tests different things at different levels, and most candidates who focus solely on the delivery pipeline — Kafka to workers to APNs/FCM — miss the half of the question that makes it an AI notification system rather than a fan-out infrastructure exercise.

    The junior-level answer covers fan-out architecture, channel abstraction, and basic delivery tracking: decouple producers from workers with Kafka, run channel-specific workers for push/email/SMS, store delivery status in a database. Correct, but generic — it would work equally well for a system with no learning component at all.

    The senior-level answer adds fatigue management (does the candidate volunteer, unprompted, that a system without it destroys the channel?), send-time optimization (per-user optimal delivery scheduling, not a fixed send time for everyone), and names the dual risk explicitly — sending too much erodes trust, sending too little wastes the product's ability to reach users who'd actually want to know.

    The staff-level answer treats regulatory compliance as an architectural constraint, not a policy document: opt-out checks are synchronous and blocking before every send, never processed as an hourly batch — an async check that clears opt-outs once an hour means a user can legally receive a marketing SMS in the 59 minutes after they opted out, which is a live TCPA violation, not an edge case. And it explains exactly-once delivery via idempotency keys unprompted: Kafka's at-least-once delivery guarantee means the application layer, not the queue, is what has to guarantee a user never gets the same notification twice.

    Staff-level probe: "Your push opt-out rate has tripled in two weeks. Daily send volume hasn't changed. What's happening, and how do you diagnose it?" Three likely causes, in the order a staff engineer should check them. First, a new notification type launched without an A/B test or a fatigue review — cross-reference the notification-type launch log against the opt-out spike's start date, and check which user segments are opting out at elevated rates. Second, a bug in the fatigue gate silently raised the effective send rate for some cohort — check average notifications-per-user-per-day, segmented by tier, against the same two-week window. Third, content quality degradation from a newly-templated or newly-LLM-generated notification type producing irrelevant or misleading copy — audit the last notification received by every user who opted out in the last 14 days; if 70% of them share the same notification type as their final send before opting out, that type is the cause, not a platform-wide regression.

    Staff-level probe: "Legal flags that you sent promotional SMS to 500K users between 9:10 PM and 9:30 PM local time, due to a time zone database bug. What's the immediate response, and what changes prevent recurrence?" Immediately: preserve the send logs and time zone data used at send time as a legal record — do not modify or delete anything, notify legal and compliance, and halt further SMS sending until the scope is understood. Investigation: identify which time zone data source was in use, which version introduced the bug, and when it deployed. The architectural fix is the one that actually prevents recurrence: the TCPA time-window check moves from a single time zone source to two independent sources cross-validated against each other; if they disagree on whether the current local time falls inside the 8 AM–9 PM window for a given recipient, the send is suppressed and routed to manual review rather than resolved by picking one source and hoping. A standing monitor alerting on any SMS sent between 8:45 PM and 9:15 PM local, for any recipient, closes the loop — that 30-minute window around the constraint boundary is exactly where a timezone bug like this one would surface first.
