    Multi-Agent AI Platform — System Design Case Study¶

    Every other chapter in this section designs a specific agent application. Deep Research Agent is a single-agent research loop. AI Coding Agent resolves one GitHub issue at a time inside a sandbox. Multi-Agent Research System fans a research question out to six parallel sub-agents and synthesizes their findings into one report. Autonomous Software Engineer executes a multi-phase engineering task across hours and dozens of files. Read closely, each of those chapters solves the same handful of infrastructure problems from scratch: how does an orchestrator dispatch bounded sub-tasks and know when they're done? How does a sub-agent's output reach a synthesis step without flooding it with 180,000 tokens of raw context? What happens when one sub-agent in a six-agent fan-out fails halfway through, and its three dependents are now blocked? Who approves an agent that's about to send an email to 200 people?

    This chapter is not another agent application — it is the answer to those questions, solved once, correctly, as a platform every application in this section can run on. The relationship is the one Kubernetes has to containers, Airflow has to data pipelines, and AWS Step Functions has to workflows: this chapter designs the general-purpose runtime, and Chapters 07, 10, 16, and 17 are what get built on top of it. Solving the task DAG execution engine, the inter-agent context isolation, the shared-memory consistency guarantees, and the human-in-the-loop checkpoint system once, at the platform layer, is what lets an application team write Chapter 16's decomposition prompt and synthesis logic without also rebuilding a scheduler, a state store, and an approval workflow from scratch — and without each application team getting the safety-critical parts subtly wrong in a different way.

    Multi-Agent Research System is this platform's primary tenant throughout this chapter. Where Chapter 16 says "the orchestrator dispatches sub-agents," this chapter is the task DAG scheduler that does the dispatching (Concept 3). Where Chapter 16 says "sub-agent outputs are synthesized," this chapter is the artifact store and context-isolation contract that make that synthesis possible without the orchestrator ever holding six sub-agents' full trajectories in context at once (Concept 2). Every mechanism below is written against one test: does this actually explain what Chapter 16 needs from the platform underneath it?

    The secondary thread running through the chapter is failure. A single agent failing can simply be retried — Chapter 10's inner loop does exactly that. In a multi-agent DAG, one sub-agent's failure propagates: downstream dependents are blocked, the orchestrator may need to replan, and a human may need to be notified if the task can't recover on its own. Designing that failure-propagation and recovery logic is as load-bearing as designing the happy path, and it gets the same weight here that dispatch and scheduling get.

    Requirements¶

    Functional

    • Accept task submissions carrying a root task description, agent-type constraints, a tool permission set, and an approval-workflow configuration — the full contract an application team needs to launch a multi-agent task without hand-rolling its own orchestration.
    • Decompose a submitted task into a sub-task DAG via an orchestrator LLM call, and validate the resulting graph (no cycles, every sub-task's dependencies resolvable) before scheduling begins.
    • Schedule and dispatch sub-tasks to agent workers strictly as their dependencies are satisfied, running every independent sub-task in the current ready set concurrently (Concept 3).
    • Manage shared state — task DAG status, working memory, episodic and semantic memory — across every agent participating in a task, with per-task isolation strict enough that a bug in one task's execution cannot read or corrupt another's (Concept 4).
    • Enforce human-in-the-loop checkpoints at every configured trigger point, and block the corresponding action until a decision is recorded (Concept 5).
    • Store every task artifact with provenance — which sub-task produced it, from which inputs — so any downstream consumer, human or agent, can trace a result back to its source (Concept 2).
    • Handle sub-task failure with automatic retry, graceful degradation, and dynamic replanning when a failure sits on the task's critical path (Concept 3).
    • Provide task status, progress, and audit-trail APIs so a caller can observe a multi-minute-to-multi-hour task without polling internal state directly (API Design).

    Non-functional

    Requirement Target Why this number
    Task dispatch latency P95 < 500ms from a sub-task becoming ready to an agent worker receiving it The scheduler sits on the critical path of every sub-task in every task; a slow dispatcher adds latency to work that's already unblocked and waiting, the one delay this platform has no excuse for
    Concurrent task capacity 1,000 active tasks × up to 10 sub-tasks each = 10,000 concurrent agent workers Sized to the capacity-planning profile below; this is the number every downstream component (working memory, artifact store, worker pool) has to be provisioned against
    HiL approval notification latency < 30 seconds from checkpoint trigger to approver notified A slow notification path silently converts a fast approval process into a slow one no matter how quickly the approver actually responds once they see the request
    Artifact storage durability 99.999999999% (S3 eleven nines) Artifacts are the only record of what a sub-agent actually produced; losing one after the fact is indistinguishable from the sub-agent never having run
    Platform availability 99.9% (three nines) A platform outage doesn't just fail new task submissions — it stalls every in-flight task across every tenant application simultaneously, a much larger blast radius than a single application going down
    State recovery after restart < 5 minutes to resume all interrupted tasks from the last snapshot Bounds how much of a 1,000-task fleet sits idle after any single platform-level failure, independent of how long any individual task itself takes

    Explicitly out of scope: the agent implementations themselves — decomposition prompts, synthesis logic, tool-specific reasoning — which is application code owned by Chapters 07, 10, 16, and 17, not the platform; model training or fine-tuning; the RAG knowledge base an agent retrieves from, covered in RAG System; the LLM inference serving infrastructure underneath every orchestrator and sub-agent call, covered in LLM Inference System.

    The row worth double-checking against intuition: every infrastructure number here is small. 20MB of working memory and 155GB/day of artifact storage are rounding errors for a platform serving 10,000 concurrent agent workers — an event-driven scheduler on Redis pub/sub handles 222 events/sec without strain, and S3 was built for orders of magnitude more than 1.8MB/sec of writes. None of the compute, storage, or scheduling numbers are the platform's real constraint. That constraint shows up in the next section, and it isn't a machine.

    Scale Estimation¶

    The number that actually caps how much autonomous multi-agent work this platform can safely run isn't scheduler throughput or storage cost — it's human approval throughput, the direct consequence of the HiL checkpoint architecture in Concept 5.

    Assume tasks are submitted at 200/hour and, following typical production mixes, roughly 10% include at least one irreversible action in their planned DAG and therefore require a plan approval gate: that's 20 plan approvals/hour. Holding the wait time per approval under 5 minutes at that arrival rate requires roughly 20 concurrent approvers actively working the queue — not 20 people employed, but 20 person-slots of attention available at any given moment, which in practice means a rotating team large enough to always have that many online.

    Pre-action confirmations are the sharper constraint. A task with irreversible actions in its plan typically triggers 2-3 pre-action confirmations over its lifetime (each email.send, each database.write against a production table, each git.push to main). At 200 tasks/hour × 2 confirmations/task: 400 approvals/hour, or roughly 7 per minute. A single attentive on-call approver can work through 2-3 decisions/minute; sustaining 7/minute requires either a dedicated multi-person approval team or aggressive auto-approval thresholds that trade oversight for throughput (Concept 5's scope-expansion auto-approval logic is the direct mechanism for making that trade deliberately rather than by neglect).

    This is the platform's central operational constraint, and it recurs in Cost Model and Tradeoff Analysis below: high-volume autonomous operation requires either a well-staffed approval function or a higher tolerance for auto-approved risk — there is no infrastructure investment that makes this number go away, because the bottleneck is attention, not compute.

    High Level Design¶

    flowchart TB
    DEV["Application: Chapters 07, 10, 16, 17"] --> INGEST["Task Ingestion Service"]
    INGEST --> ORCHLLM["Orchestrator LLM:\ntask decomposition"]
    ORCHLLM --> DAGSTORE[("Working Memory:\nRedis, task DAG state")]
    INGEST --> PLANGATE{"Plan includes an\nirreversible action?"}
    PLANGATE -->|"yes"| HILGW["HiL Gateway"]

    SCHED --> WORKERS["Agent Worker Pool\nauto-scaling, stateless"]
    WORKERS --> ARTSTORE[("Artifact Store: S3")]

    WORKERS --> SEMANTIC["Semantic Memory:\nRAG routing"]
    ARTSTORE --> SCHED
    SCHED --> DAGSTORE
    HILGW --> AUDITLOG[("Audit Trail: WORM storage")]
    SCHED --> DELIVERY["Task Delivery /\nFinal Output Review"]

    Five components carry the whole platform. Task Ingestion validates a submission's tool-permission set, triggers the orchestrator LLM's decomposition call, writes the resulting DAG to working memory, and routes to the plan-approval gate when the plan warrants one. The Scheduler is the event-driven loop that watches DAG state, dispatches every sub-task whose dependencies just cleared, and reacts to completion and failure events — Concept 3 in full. The Agent Worker Pool is a fleet of stateless, container-based workers: each receives a task message, fetches its inputs from the artifact store, runs its LLM-plus-tool-calls loop, writes its output back, and reports completion — the same worker shape whether it's running Chapter 16's search-read-summarize logic or Chapter 10's code-test-fix logic. The State Management Layer is four systems working as one: Redis for working memory, S3 for artifacts and snapshots, a vector database for episodic memory, and a RAG system for semantic memory (Concept 4). The HiL Gateway intercepts every tool call in a configured high-risk category, builds an approval request, and blocks execution until a decision is recorded — the only component on this diagram that can stop an otherwise-ready sub-task from running (Concept 5).

    Detailed Design¶

    Five load-bearing concepts, each one an infrastructure problem that recurs in every specific agent application in this section and that this platform solves exactly once.

    Concept 1 — Orchestration patterns: three architectures, three failure modes¶

    The interview-relevant question isn't "name the orchestration patterns" — it's when does each pattern break, and how do you choose? Every production multi-agent system is one of three shapes, and each has a distinct failure mode that shows up only past a certain scale.

    flowchart LR
    subgraph HIER["Hierarchical Supervisor"]
        HO["Orchestrator"] --> HW1["Sub-Agent 1"]
        HO --> HW2["Sub-Agent 2"]
        HO --> HW3["Sub-Agent N"]
        HW1 --> HAS[("Artifact Store")]
        HW2 --> HAS
        HW3 --> HAS
        HAS --> HO
    end

    subgraph P2P["Peer-to-Peer Mesh"]
        PA1["Agent A"] --> PBUS[("Event Bus")]
        PA2["Agent B"] --> PBUS
        PA3["Agent C"] --> PBUS
        PBUS --> PA1
        PBUS --> PA2
        PBUS --> PA3
        PBUS --> PTRACK["Task Tracker"]
    end

    subgraph BB["Blackboard"]
        BCTRL["Controller"] --> BAG1["Agent X"]
        BCTRL --> BAG2["Agent Y"]
        BAG1 <--> BSTORE[("Blackboard Store")]
        BAG2 <--> BSTORE
        BSTORE --> BCTRL
    end

    Hierarchical supervisor (hub-and-spoke). One orchestrator agent decomposes the root task into a structured DAG, and the platform's scheduler dispatches each independent sub-task to a specialist worker. All communication flows through the orchestrator: workers write results to the artifact store, and the orchestrator — once every dependency clears — reads only the references and summaries it needs to synthesize, never a worker's raw trajectory. This is the pattern Multi-Agent Research System uses, and it's the platform's default.

    Why it works: the orchestrator holds a complete view of task state. It can detect an inconsistency between two sub-agents' outputs, request clarification, or replan, because global coherence has exactly one reasoning locus responsible for it.

    Why it breaks at scale: three specific ways. Orchestrator context saturation — a task with real recursion (sub-agents that themselves spawn sub-sub-agents) forces the orchestrator to hold nested result summaries from every level simultaneously; a 20-layer recursive task holds 20 layers of context at once, well past where "lost in the middle" degrades synthesis quality. Single point of failure — a reasoning error in the orchestrator's own synthesis call fails the entire task, because no other agent is positioned to catch it. Throughput ceiling — every coordination decision routes through one orchestrator; past roughly 10 concurrent sub-agents, its synthesis step becomes the critical path for the whole task rather than a fast final step.

    Appropriate for: well-defined decomposable tasks, fewer than ~10 concurrent sub-agents, tasks where synthesis genuinely needs to understand the full result set, and tasks where the orchestrator's own judgment is the primary quality mechanism — research synthesis and report generation are the textbook case.

    Peer-to-peer (event-driven mesh). No central orchestrator. Each agent subscribes to event types on a message bus and emits new events on completion. A lightweight, stateless task tracker — not an agent — monitors the event stream, tracks which sub-tasks are complete, and determines when the root task is done. Agents can spawn new sub-tasks by emitting task-assignment events directly, with no orchestrator approval in the loop.

    Why it works: no single point of failure, and no agent needs to know about any other agent type to participate — a new specialist can subscribe to relevant events without the existing agents changing at all. The message bus absorbs fan-out naturally, and agents stay stateless between events.

    Why it breaks: global coherence becomes impossible — no agent has a full view of what's happening, so a judgment call like "is another agent already handling this lead?" has no answer without a coordination mechanism the architecture doesn't provide. Deadlock risk — Agent A waits on Agent B's event, B waits on C's, C waits on A's; with no orchestrator to detect and break the cycle, the task tracker has to actively monitor the emitted task graph for circular dependencies and surface them as alerts, or the cycle runs forever. Debugging difficulty — reconstructing what happened requires replaying the full event stream; a failure that took 45 minutes to manifest in production takes 45 minutes of replay to understand.

    Appropriate for: loosely coupled tasks where agents make genuinely independent progress, event-driven pipelines reacting to external signals (market data, user actions), and tasks where dynamic task creation matters because agents discover new sub-tasks mid-execution.

    Blackboard architecture. A shared, structured data store — the blackboard — holds current task state: intermediate results, open questions, completed artifacts. Agents read from and write to it directly. A controller, typically a rule-based system rather than an LLM, reads the blackboard's current state, decides which agent types should act given what's present and what's missing, and dispatches them; agents read the relevant sections, do their work, and write results back for the controller to reassess.

    Why it works: the entire task state is visible in one place, at all times, to every agent. Debugging reduces to snapshotting the blackboard and replaying from any point. Agents are stateless — read, work, write back — so any one of them can be replaced or restarted without losing progress.

    Why it breaks: write contention — eight agents writing to overlapping blackboard sections simultaneously need locking or optimistic concurrency, and high-contention writes slow the whole task. Stale reads — Agent A reads the blackboard, Agent B writes an update before A finishes and writes back, and A's write silently overwrites B's, unless versioning and conflict resolution are built in deliberately. Unstructured growth — the blackboard's schema has to be defined upfront, and a task that evolves in an unexpected direction needs a schema extension, which is a hard thing to do safely at runtime.

    Appropriate for: document-construction tasks where multiple agents contribute sections to one shared output, long-running tasks where the blackboard doubles as a persistent scratchpad surviving restarts, and tasks where any agent genuinely needs to read what any other agent has produced to do its own work.

    Decision guide. The dimension that matters most is whether one agent needs to reason over the full output for coherence — if so, hierarchical is the only pattern that gives that agent the complete view it needs. If sub-tasks can make progress without any awareness of each other, peer-to-peer scales further at the cost of coherence. If agents genuinely need to read each other's in-progress work to do their own, blackboard is the only shape that provides that visibility without funneling every read through an orchestrator. In practice, most production deployments default to hierarchical and switch only once the orchestrator-context bottleneck becomes measurable — the same default Autonomous Software Engineer reaches for its own phase execution, staying sequential-through-an-orchestrator rather than reaching for peer-to-peer coordination until independence is proven, not assumed.

    Concept 2 — Inter-agent communication and the context isolation problem¶

    Context isolation is the most underappreciated platform-engineering problem in multi-agent systems, and it's worth being precise about why the obvious approach fails before describing the one that works.

    The naive approach and why it fails. The simplest inter-agent communication concatenates every sub-agent's full output text into the next sub-agent's prompt. For 6 sub-agents each producing ~2,000 tokens: the synthesis agent receives 12,000 tokens of prior output, plus its own task description, plus retrieved context — commonly 21,000 tokens total. At Sonnet-class pricing (\(3/MTok input), that's ~\)0.063 per synthesis call, roughly 3x more than necessary once most of that sub-agent output turns out to be irrelevant to synthesis. The bigger cost is quality, not dollars: synthesis attention dilutes across 21,000 tokens, and the "lost in the middle" effect means the first and last sub-agents' outputs get disproportionate weight while the middle ones are systematically underweighted — the exact failure mode Multi-Agent Research System's context isolation discussion names as the reason isolation is a quality mechanism, not just a cost optimization.

    The minimum-necessary-context principle. Each agent receives exactly what it needs for its sub-task, and the platform — not the application developer — is responsible for constructing that context. A sub-agent gets its task description, input data references, and output schema; it does not get sibling sub-agents' outputs unless the DAG's dependency structure explicitly makes one an input to another. The synthesizer gets structured summaries of every sub-agent's output, plus references to fetch the full artifact on demand — never the full text of all of them up front.

    The artifact store as the only inter-agent communication channel. Agents never pass outputs directly to each other. They write to the artifact store and pass references; the platform's message schema carries input_refs and output_refs — storage keys — never inline content.

    {
  "message_type": "task_assignment",
  "task_id": "subtask_B",
  "agent_type": "analyst",
  "input_refs": {
    "raw_data": "s3://tasks/task_abc/subtask_A_output.json",
    "context_doc": "s3://tasks/task_abc/context.md"
  },
  "output_schema": {
    "type": "object",
    "required": ["summary", "key_findings", "confidence_score"],
    "properties": { ... }
  },
  "output_destination": "s3://tasks/task_abc/subtask_B_output.json"
}

    The agent reads only what input_refs names, writes its result to output_destination, and the orchestrator or any downstream agent fetches from that destination only when it actually needs the content. No payload ever passes through the message bus itself — only pointers.

    Structured output schemas as inter-agent contracts. output_schema is a JSON Schema serving two purposes at once: it's included in the agent's system prompt as an explicit output-format requirement, and the platform validates the agent's actual output against it before marking the sub-task complete. Output that's structurally invalid — a missing required field, a wrong type — is a soft failure (Concept 3), retried before any downstream agent that depends on it is ever dispatched.

    Context construction for the orchestrator. When synthesizing N sub-agent results, the orchestrator receives the original root task description, a structured per-sub-agent summary (generated from a summary field the platform requires in every output schema, passed through directly without touching the full artifact), and references to every full artifact for on-demand fetch if the orchestrator needs to quote, verify, or reconcile. This construction cuts the orchestrator's synthesis input by 60-80% relative to receiving full outputs, while preserving the ability to go deep on any one result when synthesis genuinely needs it.

    Concept 3 — The task DAG execution engine: scheduling, parallelism, and dynamic replanning¶

    This is the execution core: the scheduling algorithm, the parallelism mechanics, and the four distinct failure types that need four distinct recovery strategies.

    Task DAG representation. Every task is a DAG stored in working memory (Redis). Nodes are sub-tasks; directed edges are dependencies. Each node carries task_id, agent_type, input_refs, output_schema, output_destination, status (pending | running | complete | failed | cancelled), depends_on[], dependent_of[], assigned_agent_worker_id, retry_count, and the three lifecycle timestamps.

    The scheduler loop. Event-driven, not polling:

    while task_dag.has_incomplete_tasks():
    ready_tasks = [t for t in task_dag.tasks
                   if t.status == 'pending'
                   and all(dep.status == 'complete' for dep in t.depends_on)]

    for task in ready_tasks:
        worker = agent_pool.acquire(task.agent_type)
        if worker:
            task.status = 'running'
            task.assigned_agent_worker_id = worker.id
            worker.dispatch(task)

    await_any_completion()  # block until at least one task completes or fails

    The scheduler wakes on completion or failure, recomputes the ready set, and dispatches — every sub-task in the current ready set fires simultaneously, which is what makes parallel execution the default behavior rather than something bolted on.

    flowchart TB
    NEW["Sub-task created:\nstatus pending"] --> READY{"All dependencies\ncomplete?"}
    READY -->|"no"| WAIT["Wait in DAG"]
    WAIT --> READY
    READY -->|"yes"| DISPATCH["Scheduler dispatches\nto agent worker"]
    DISPATCH --> RUNNING["status: running"]
    RUNNING --> RESULT{"Outcome?"}
    RESULT -->|"success, schema valid"| COMPLETE["status: complete\nartifact written"]
    RESULT -->|"hard failure"| RETRYCHECK{"retry_count\nunder max?"}
    RETRYCHECK -->|"yes"| DISPATCH
    RETRYCHECK -->|"no"| FAILED["status: failed"]
    RESULT -->|"soft failure"| ESCALATE["Escalate model tier,\nre-dispatch"]
    ESCALATE --> DISPATCH
    RESULT -->|"partial, step budget exhausted"| PARTIAL["status: partial\npartial artifact written"]
    FAILED --> PROPAGATE["BFS: mark transitively\ndependent sub-tasks cancelled"]
    PROPAGATE --> CANCELLED["status: cancelled"]
    PROPAGATE --> REPLAN{"Critical-path\nfailure?"}
    REPLAN -->|"yes"| REPLANNER["Orchestrator\nreplanning cycle"]
    REPLAN -->|"no"| COMPLETE
    COMPLETE --> DOWNSTREAM["Dependent sub-tasks\nbecome ready"]
    PARTIAL --> DOWNSTREAM

    Parallelism ceiling. Maximum useful parallelism is bounded by two things: how many tasks are actually in the current ready set (a function of DAG structure — a task waiting on unfinished work simply can't be parallelized away), and agent-pool capacity per agent_type. The platform tracks pool capacity per type and queues dispatch when a type's pool is saturated, rather than either blocking the scheduler or over-committing workers.

    Four failure types, four recovery strategies. Treating "sub-task failed" as one undifferentiated case either aborts a task over one bad thread or, worse, ships a result with a silent hole in it — the same discipline Multi-Agent Research System's own failure handling argues at the application layer, generalized here to the platform that has to enforce it for every application built on it.

    • Hard failure — the agent crashes, times out, or the LLM call returns a non-retryable error. Increment retry_count; if still under max_retries (default 2), re-dispatch to a different worker, since the original may be unhealthy. At the max, mark failed, walk the dependency graph via BFS to mark every transitively dependent sub-task cancelled, and emit a HiL checkpoint: "Sub-task X failed after 3 attempts. The following sub-tasks cannot proceed: [B, D, E]. Abandon the task, or restructure around the failure?"
    • Soft failure — output exists but fails schema validation or scores below the quality threshold. Re-dispatch to a different worker at an escalated model tier (Haiku → Sonnet → Opus). If the escalated tier also fails quality, mark soft_failed; downstream sub-tasks can still proceed against a soft-failed output if they're willing to accept a confidence_degraded flag, which the orchestrator factors into synthesis rather than silently trusting the output at face value.
    • Partial completion — the agent exhausts its step budget before finishing. The partial output is written to the artifact store flagged partial; downstream sub-tasks that can use partial input are dispatched with a partial_input flag, and a revised continuation sub-task — the original description adjusted to resume from where the partial output stopped — is created and dispatched.
    • Dynamic replanning — triggered when a hard failure lands on a critical-path sub-task (the task cannot complete without its output), or when a sub-agent discovers mid-execution that the original decomposition missed a required step. The orchestrator LLM receives the current DAG state — completed sub-tasks and their outputs, failed and blocked sub-tasks — plus the original root goal, and generates a revised sub-task list that reaches the goal using the available successful outputs plus whatever new sub-tasks it adds. The revised plan is validated (no cycles, every required output achievable) before it replaces the blocked portion of the DAG. Replanning is capped at 3 cycles per task; a task that still can't complete after 3 replans is escalated to a human with a full summary of what succeeded, what failed, and what gap remains.

    Concept 4 — Shared memory and state management with consistency guarantees¶

    Three tiers, each with a different consistency model — the interesting question for every tier isn't just what data lives there, but what happens when two agents write at the same time.

    Tier Store Contents Consistency model Retention
    Working memory Redis, task-scoped DAG state, sub-task status, worker assignments, step/token budgets, in-progress artifact refs SETNX for status transitions, DECRBY-with-check for budgets, INCR for counters; last-write-wins elsewhere task_timeout + 1 hour buffer
    Episodic memory Vector database, cross-task Past task executions: task_embedding, outcome, decomposition, execution_time, total_tokens Read-mostly; a prior, not a source of truth Indefinite
    Semantic memory RAG system, cross-task Domain knowledge agents retrieve grounded, cited facts from Read-only from the agent's perspective Managed by the ingestion pipeline

    Tier 1 — Working memory. All agents in one task execution share a Redis keyspace partitioned by task_id. Most operations are last-write-wins, which is fine for metadata nobody's correctness depends on — but three operation types need atomicity, and each gets a specific primitive rather than a generic lock. Sub-task status transitions (pending → running, running → complete) use SETNX: two workers racing to claim the same sub-task race on the same key, and only the first SETNX succeeds — the second sees the key already set and backs off, no lock manager required. Token-budget decrements use DECRBY with a check: if the decrement would push tokens_remaining negative, the platform INCRBYs it back and rejects the dispatch outright. Step counters use plain INCR, atomic by construction with no race possible. The whole keyspace snapshots to S3 every 60 seconds via a background job; on restart, the platform loads the latest snapshot, reconstructs DAG state, and re-dispatches whatever was running at snapshot time — a sub-task that actually completed during the restart window writes its artifact under an idempotency key, so re-dispatch finds the existing artifact rather than recomputing it.

    Tier 2 — Episodic memory. Indexed by task type and domain: task_embedding, outcome, the decomposition that worked, execution_time, total_tokens. At decomposition time, the orchestrator queries it — "find the 3 most similar past tasks and show me their decompositions and outcomes" — to bootstrap the current decomposition from what's worked before and steer away from what's failed before, backed by the same nearest-neighbor infrastructure covered in Vector Database. It is a prior for the decomposition LLM call, not a substitute for it: past tasks are similar, never identical. The platform writes a summary record after every completed task and a failure record with the failure point annotated after every failed one — learning from failures is exactly as valuable as learning from successes here.

    Tier 3 — Semantic memory. The knowledge base agents retrieve domain facts from, structurally RAG System embedded as a platform component. An agent issues a retrieval query — "what is the regulatory framework for X?" — and gets grounded, cited context back. Different task domains route to different indices: a legal task queries a legal corpus, a coding task queries documentation corpora, and the platform owns that routing decision so no application team has to rebuild it. Semantic memory is read-only from an agent's perspective; updates flow through the ingestion pipeline described in Web Crawler for AI Knowledge Ingestion, never through an agent's own write path.

    Cross-task isolation. With 50 concurrent tasks on the platform, one task's working memory must be strictly unreachable from another's — a bug that let task A's agent read or overwrite task B's state would be catastrophic, not a minor correctness bug. Every Redis key is namespaced {task_id}:{key_name}, every query carries task_id as a mandatory partition key, and agent workers never touch Redis directly at all — they call the platform's memory API, which enforces namespacing in one place rather than trusting every worker implementation to get it right independently.

    Concept 5 — Human-in-the-loop checkpoints and safe autonomous operation¶

    This is the governance and safety layer, and it's a first-class architectural concern here, not something bolted on after the scheduler works — building directly on the general escalation-trigger and review-queue architecture in Human-in-the-Loop Architecture, applied specifically to a fleet of concurrently executing multi-agent DAGs rather than one agent's action stream.

    The core principle: irreversibility determines gate placement. Any action whose consequence can't be undone within the task's lifetime requires a human gate before it executes. An email can't be unsent. A database record deleted without backup can't be undeleted. A commit to a production branch leaves a trace even if reverted. A resource that incurs cost can't be uncreated without paying for the time it ran. Reversible actions — drafting, computing, reading, writing to a scratchpad — need no gate at all and can be freely automated; the entire checkpoint architecture exists only for the irreversible half.

    1. Plan approval gate — mandatory before high-risk tasks. Triggered whenever the planned sub-task list includes a tool call in an irreversible category (send_message, write_to_database, call_external_api, delete_resource, commit_code). The orchestrator generates the complete plan — task DAG, agent assignments, estimated token cost, estimated duration, every external action planned — execution pauses, and an approval request goes to the task owner via the configured channel (Slack Block Kit buttons, an email approval link, a web UI). The reviewer approves, rejects with a logged reason, or modifies the DAG directly (removing sub-tasks, changing agent types, narrowing tool-permission scopes). Every decision is authenticated and logged: {approver_user_id, approver_display_name, approved_at, plan_snapshot_hash, decision, decision_reason}. The plan_snapshot_hash binds the approval to one specific plan — if the plan changes afterward via a replanning cycle, a fresh approval is required, not inherited.

    2. Pre-action confirmation — per high-risk tool call. The platform intercepts a tool call before it executes if the tool sits in a configurable high-risk category set — email.send, api.payment, database.write against a production_* table pattern, git.push to main, filesystem.delete, filesystem.write under /prod/*. The approval request shows exactly which agent is asking, the full action parameters (the actual email, the actual SQL, the actual file to delete), and the agent's own stated reasoning for the action. The reviewer approves, rejects (the agent gets the rejection back and has to find an alternative), or modifies the parameters directly — editing a recipient list before approving, for instance. If no response arrives within 15 minutes, the request escalates to a secondary approver; another 15 minutes of silence pauses the task indefinitely and notifies the task owner by email or SMS.

    3. Scope expansion alert. Triggered when a sub-agent discovers mid-execution that completing the task needs more scope than the original plan — more sub-tasks, more data sources, more tool calls, more cost. The agent emits a scope_expansion_request rather than silently proceeding: {requesting_agent, original_scope, proposed_expansion, expansion_reason, estimated_additional_cost, estimated_additional_time}. An expansion under 20% more sub-tasks and under 30% more estimated cost and using only tool types already approved in the original plan auto-approves, with the auto-approval logged for audit. Anything past either threshold, or requiring a tool type outside the original approved plan, needs human approval, presented as a direct comparison: "original plan: 6 sub-tasks, ~\(0.80, 12 minutes. Proposed: 9 sub-tasks, ~\)1.40, 18 minutes. The agent discovered [reason]. Approve the expansion, or hold it to original scope?"

    4. Final output review gate. Triggered once every sub-task reaches a terminal state and the orchestrator has produced its synthesized output. The platform presents the result to the task owner before delivery, and for long outputs — research reports, code PRs, document drafts — the review UI flags specific sections: anywhere sub-agent confidence fell below threshold, anywhere a retrieval citation couldn't be verified, and anywhere a sub-task soft-failed and its contribution should be read skeptically. The owner accepts and delivers, requests revisions (triggering a new, narrowly targeted agent pass on just the flagged sections), or rejects the task outright.

    Three properties of this flow are worth naming. First, A and C dispatch simultaneously the moment both clear the plan-approval gate — the scheduler never serializes sub-tasks that don't depend on each other, which is the entire latency argument for running this on a platform instead of a hand-rolled sequential script. Second, D waits on both B and C, not just the later of the two to finish in wall-clock time — the scheduler's ready-set computation checks the full depends_on list, not "has anything upstream happened yet." Third, the pre-action confirmation inside D's execution doesn't restart the task — only D pauses; A, B, and C's completed work stays exactly where it is in working memory and the artifact store while the approval request is in flight.

    Retrieval Layer¶

    This platform has three distinct retrieval surfaces, and none of them is a single monolithic index the way RAG System is for one application — deliberately, since bundling them would mean rebuilding retrieval infrastructure per tenant application rather than sharing it.

    Working-memory reads are point lookups against Redis keyed by task_id, not retrieval in the similarity-search sense — the scheduler and HiL gateway read DAG state and budget counters this way dozens of times per second per task.

    Episodic memory queries are genuine semantic search: at decomposition time, the orchestrator embeds the incoming task description and retrieves the nearest past-task records from the index described in Concept 4, backed by the same nearest-neighbor infrastructure covered in Vector Database.

    Semantic memory queries are how any agent worker gets a grounded domain fact. The platform's routing layer decides which of potentially several domain-specific indices answers a given query — a legal task's retrieval calls never touch the same corpus a coding task's calls do — and the actual retrieval mechanics (hybrid search, chunking, reranking) are the RAG System architecture embedded as a platform component, not reimplemented here.

    The platform's retrieval layer is deliberately thin: a router and a cache, not a search engine. Rebuilding chunking and embedding-model choices independently inside every tenant application — once for a legal corpus, once for a coding corpus — is exactly the ad hoc, per-application infrastructure duplication this platform exists to eliminate.

    Agent Layer¶

    Every agent chapter in this section — 07, 10, 16, 17 — implements its own reason-act-observe loop. This platform implements none of those loops directly. It implements the runtime substrate those loops execute inside, and the SDK contract that connects them to platform primitives — the same relationship AI Logging & Observability Platform has to the agent loops it instruments, here applied to execution rather than observability.

    Four primitives every agent worker process links against:

    • fetch_artifact(ref) / write_artifact(data) -> ref — the only way an agent reads or writes cross-task-visible data, the mechanism backing Concept 2's context isolation.
    • request_tool_call(tool_name, params) — every tool invocation, from a web search to an email send, routes through this call, which is what lets the HiL Gateway intercept a high-risk action before it executes (Concept 5). An agent that bypasses this primitive and calls a tool's API directly is exactly the failure the platform's network isolation exists to prevent (Security Layer).
    • checkpoint(state) — periodic state serialization to working memory, so a crashed worker resumes from its last checkpoint instead of restarting its sub-task from zero (Concept 4).
    • emit_span(...) — every LLM call, tool call, and retrieval an agent issues is wrapped in the trace schema AI Logging & Observability Platform defines. This platform's scheduler dispatch and DAG dependency structure map directly onto that schema: every sub-task the scheduler dispatches becomes one child AgentLoopSpan under the task's root span, and every dependency_span_ids edge Chapter 28 needs to represent "this sub-agent consumed that sub-agent's output" is exactly the edge this platform's DAG already tracks — this platform is the system that produces the nested-AgentLoopSpan trace shape Chapter 28 names as its hardest schema problem to represent correctly.

    Two loop shapes run on these primitives, matching Concept 1's two roles: the orchestrator's loop — decompose, dispatch, monitor, synthesize, the identical shape Multi-Agent Research System's orchestrator runs — and the worker's loop, a standard bounded ReAct loop no different in shape from any single sub-agent in Chapters 07, 10, or 16, differing only in which tools its role scopes it to. The platform is agnostic to what a worker's loop actually reasons about: a worker running Chapter 16's search-read-summarize logic and a worker running Chapter 10's code-test-fix logic run on the identical scheduler, artifact store, and HiL gateway, differing only in tool registry and prompt.

    Model Layer¶

    Two routing decisions belong to the platform rather than to any one application, and both configure which tier of LLM Inference System serves which call.

    Role Model tier Why
    Orchestrator: decomposition, replanning, synthesis Strongest available tier The reasoning locus Concept 1 identifies for hierarchical orchestration and the trigger for Concept 3's dynamic replanning; a cheap model's bad decomposition is expensive precisely because the entire downstream DAG inherits its mistake, the same argument Multi-Agent Research System's Model Layer makes for its own decomposition call
    Worker: routine, low-risk role Cheap/fast tier Formulaic, well-scoped work — extraction, formatting, retrieval-heavy sub-tasks — where throughput matters more than reasoning depth
    Worker: role gated by a pre-action confirmation Strongest available tier A mistake here is exactly what the HiL gateway exists to catch, and it's cheaper to prevent with a model less likely to make it than to catch after the fact every time
    Quality-gate / judge calls Cheap tier Short, structured pass/fail scoring against a sub-task's output_schema, the same cheap-tier-appropriate pattern AI Logging & Observability Platform's Layer 2 quality sampling uses for its own post-hoc scoring

    Routing is platform policy, not something each application team re-derives per task: a task-type configuration submitted at intake declares which tier serves which role, and the platform enforces it uniformly — the same tiered-by-role discipline argued generally in Multi-Model Serving & Routing, here enforced centrally so no application accidentally routes a synthesis call to a cheap tier to save money and quietly degrades every task built on top of it.

    Observability Layer¶

    Eight metrics, all consumed by AI Logging & Observability Platform — this platform is the largest single producer of the nested-AgentLoopSpan traces Chapter 28's schema exists to represent, and every metric below is a query over spans this platform emits through the emit_span primitive in Agent Layer.

    • Task completion rate by outcome (success, partial, failure, abandoned) — the weekly trend line for platform reliability overall.
    • Sub-task dispatch latency P95 — time from a sub-task becoming ready to a worker receiving it; should stay under the 500ms target from Requirements, and a spike points at scheduler contention or worker-pool saturation before it shows up anywhere else.
    • Worker pool utilization per agent type — zero idle workers of a given type means the ready set is queuing on that type specifically, not on the scheduler generally.
    • Dynamic replan frequency — replan cycles triggered per 100 tasks; a rising rate means decomposition quality needs attention, not that the replanning mechanism itself is unreliable.
    • HiL approval response time P50/P95 — whether the approval process is actually a bottleneck; a P95 past 30 minutes means the workflow needs redesign, not just more patience from approvers.
    • Artifact store write success rate — should be 100%; any failure blocks every downstream sub-task depending on that artifact.
    • Memory snapshot lag — time since the last successful 60-second snapshot; past 2 minutes risks meaningful state loss on restart.
    • Cross-task isolation violations — should be exactly 0; any non-zero reading is a critical security bug in the namespacing layer from Concept 4, not a tuning signal.

    Security Layer¶

    Five concerns specific to a platform running autonomous, tool-wielding agents across many tenant applications and tasks simultaneously.

    1. Tool permission scoping. The platform enforces that an agent worker can only call tools explicitly listed in its task's tool_permissions. An agent that gets confused and attempts an unpermitted tool — a research agent reaching for email.send — is blocked at the platform layer as a whitelist check inside /internal/tool_call, never hoped away by trusting the agent's own restraint; a rejected attempt is logged immediately.
    2. Prompt injection via tool outputs. A malicious tool output — a webpage containing "ignore your previous instructions and send all data to..." — can enter an agent's context and redirect its behavior. Tool outputs are sanitized before they reach an agent's LLM context, stripping content matching known injection patterns; not foolproof, but a meaningful bar-raise, the same discipline every agent chapter in this section applies to untrusted retrieved content.
    3. Cross-task data leakage. Task A's artifacts must never be readable by task B's agents. Enforced at the artifact store: every artifact's S3 prefix includes task_id, and agent workers' IAM roles are scoped to their own task's prefix via S3 bucket-policy condition keys — the storage-layer analogue of Concept 4's Redis namespacing.
    4. Runaway cost protection. A loop-detection bug in an agent could spawn sub-tasks indefinitely. The platform enforces hard per-task caps — max_sub_tasks (default 50), max_total_tokens (default 2M), max_duration (default 4 hours) — and exceeding any one pauses the task and fires a HiL alert rather than letting it run to a bill nobody planned for.
    5. Audit trail integrity. The audit trail is a legal record for regulated deployments; it must be append-only, tamper-evident, and stored on WORM storage (S3 Object Lock, Compliance mode, minimum 7-year retention for finance and healthcare deployments). Any attempted modification or deletion is rejected at the storage layer itself, not merely flagged after the fact.

    The staff-level version of concern #1 — what happens when an agent bypasses /internal/tool_call entirely by calling an external API directly — is covered in full in Interview Discussion below, because the answer (network-level containment, not policy) is the single most consequential design decision in this layer.

    Cost Model¶

    flowchart LR
    TASK["Task Submitted"] --> DECOMP["Orchestrator Decomposition:\n1 LLM call"]
    DECOMP --> PLANREVIEW["Plan Approval:\nhuman labor cost"]
    PLANREVIEW --> SUBAGENTS["Sub-Agent Execution:\nN parallel LLM calls"]
    SUBAGENTS --> ARTWRITES["Artifact Writes:\nS3 storage cost"]
    SUBAGENTS --> PREACTION["Pre-Action Confirmations:\nhuman labor cost"]

    Infrastructure cost is trivial, and Capacity Planning already showed why: ~\(3.57/day in artifact storage and a Redis footprint measured in tens of megabytes at 10,000 concurrent sub-tasks. LLM inference cost is real but application-owned — every tenant chapter's own Cost Model (Chapter 16's ~\)0.22/task, Chapter 10's ~$1.55/task) already accounts for it, and this platform's job is attribution, not absorption: every LLM call an agent worker makes is metered per the schema in AI Logging & Observability Platform's cost attribution, tagged back to the originating task and tenant.

    The dominant cost line is human approval labor, not tokens — the direct consequence of Scale Estimation's throughput math. At 200 tasks/hour with a 10% plan-approval rate and ~2 pre-action confirmations per irreversible task, sustaining sub-5-minute approval latency requires roughly 20 concurrent approvers for plan reviews and enough throughput to clear ~7 pre-action confirmations/minute — a dedicated multi-person review function, not a part-time on-call rotation. At a fully-loaded reviewer cost on the order of $50-80/hour, staffing that function around the clock is a five- to six-figure annual line item that dwarfs the platform's entire infrastructure bill. This is the number that should anchor every deployment's design conversation: the marginal cost of running one more autonomous multi-agent task is not the LLM call, it's the human minute spent reviewing it — which is exactly why Concept 5's auto-approval thresholds exist as a real lever and not a convenience feature. Raising the auto-approval threshold trades review cost for risk; a platform team sizing its approval headcount and a platform team tuning its auto-approval thresholds are making the same tradeoff from two different directions, and both numbers belong on the same dashboard.

    Failure Handling¶

    Failure mode Detection Response
    Hard failure — sub-task errors or times out No heartbeat, or a non-retryable LLM/tool error Retry on a different worker up to max_retries (default 2); at the max, mark failed, cancel every transitively dependent sub-task via BFS, emit a HiL checkpoint
    Soft failure — output present but invalid or low quality Schema validation fails, or judge score below threshold Re-dispatch at an escalated model tier; if still failing, mark soft_failed and let downstream proceed with a confidence_degraded flag rather than blocking outright
    Partial completion — step budget exhausted Step counter hits the ceiling mid-task Write the partial artifact flagged partial; dispatch downstream tasks with a partial_input flag; create and dispatch a continuation sub-task for the remaining work
    Critical-path hard failure A failed sub-task blocks task completion entirely Trigger dynamic replanning (Concept 3), capped at 3 cycles; escalate to a human with a full success/failure/gap summary if still blocked
    Scheduler or orchestrator process crash Health check on the scheduler worker Reload the last 60-second snapshot, reconstruct DAG state, re-dispatch whatever was running; idempotency keys on artifact writes prevent duplicate work for sub-tasks that actually finished during the outage
    HiL approval timeout No response inside the configured window Escalate to a secondary approver; a second timeout pauses the task indefinitely and notifies the task owner via email/SMS
    Runaway cost or scope max_sub_tasks, max_total_tokens, or max_duration exceeded Pause the task immediately and fire a HiL alert — no cap is ever allowed to silently extend itself
    Cross-task isolation violation Non-zero reading on the isolation-violation metric (Observability Layer) Treat as a P0 security incident: kill the affected task, freeze the namespacing layer for investigation, do not wait for a scheduled fix window

    The property tying every row together: a partial, explicitly labeled result is always preferable to a silent one, and nothing that touches the outside world executes without either a satisfied permission check or a recorded human decision — the same non-negotiable floor Concept 5's irreversibility principle sets for the entire platform.

    1. Orchestration pattern vs. task type. Hierarchical buys coherence, peer-to-peer buys scalability, blackboard buys debuggability — pick by coherence requirement first (high coherence need → hierarchical) and sub-task count second (past ~20 → peer-to-peer or blackboard). Most production deployments default to hierarchical and switch only once the orchestrator-context bottleneck from Concept 1 becomes measurable, not speculatively.

    2. Approval gate granularity. More gates mean more safety but more human latency sitting directly in the critical path; fewer gates mean faster tasks with less oversight. The resolvable middle: mandatory gates for irreversible actions, auto-approval for reversible ones below a cost/scope threshold, with the threshold itself tuned per task type against the cost-of-a-mistake-vs-cost-of-approval-latency tradeoff Cost Model quantifies above.

    3. Working memory consistency: last-write-wins vs. optimistic locking. Last-write-wins is faster but risks corruption under contention; optimistic locking is safer but adds retry overhead. The right split, per Concept 4: last-write-wins for non-critical metadata, optimistic locking (SETNX, checked DECRBY) reserved for exactly the state whose corruption would break execution — status transitions and budget counters — not applied uniformly everywhere out of caution.

    4. Dynamic replanning frequency. Replanning on every soft failure produces higher-quality outputs but slower, less predictable tasks; replanning only on critical-path hard failures is faster but risks shipping a task that quietly underperforms where a sub-task struggled. Tune per task priority: quality-critical tasks replan aggressively, speed-critical tasks replan only when a hard failure leaves no other path forward.

    5. Snapshot frequency. More frequent snapshots (every 30 seconds) lose less work on failure at higher S3-write and Redis-CPU cost; less frequent (every 5 minutes) is cheaper but risks losing up to 5 minutes of a task's progress. For tasks costing more than roughly $1/minute, 30-second snapshots are cost-justified outright; for cheap tasks, 5-minute snapshots are fine — the same cost-proportionality argument Cost Engineering makes generally for every infrastructure investment whose payoff scales with what's actually at risk.

    Interview Discussion¶

    "Design a multi-agent AI platform" is one of the hardest prompts in AI system design because it tests infrastructure thinking — task scheduling, distributed state management, failure recovery — and AI-specific thinking — context isolation, dynamic replanning, HiL governance — at the same time, a combination How AI System Design Interviews Work flags as the pattern that separates a strong answer from a merely competent one. Most candidates answer a specific application instead — "I'd build a research agent" or "I'd build a coding agent" — which answers a narrower, easier question than the one asked.

    The first discriminating question: "How do you ensure two agents don't write conflicting state to shared memory?" A candidate who can't answer this concretely — Redis SETNX for status transitions, optimistic locking on shared counters, task-scoped namespacing to prevent cross-task contamination — hasn't thought at the platform level, regardless of how well they can describe an individual agent's reasoning loop.

    The second discriminating question: "A sub-task fails in the middle of a 20-sub-task execution. What does the platform do?" A strong candidate distinguishes which downstream sub-tasks are blocked (everything transitively dependent on the failed one), which can still proceed (everything with no dependency on it), and what triggers replanning versus what simply retries. A platform that retries indefinitely with no HiL escalation and no dependency propagation isn't a production platform — it's a prototype that happens to work on the happy path.

    Staff-level probe: "Your platform is running 500 concurrent tasks. P95 sub-task dispatch latency is suddenly 45 seconds instead of under 500ms. Error rates are unchanged, artifacts are writing successfully. What's happening?" The scheduler is the bottleneck, and the diagnosis proceeds in order: check worker-pool utilization first — if every worker of a given type is saturated, the fix is adding workers, not touching the scheduler. If workers are idle but dispatch is still slow, the scheduler's own event loop can't keep up with completion-event volume. Check Redis latency next — a GC pause or memory pressure there stalls every SETNX status transition, which serializes the whole dispatch path behind one slow store. Finally, check whether one specific agent_type is saturated while others sit idle — the ready set may be entirely composed of sub-tasks needing that one bottleneck type, in which case the fix is scaling that type's pool specifically, not the fleet generally.

    Staff-level probe: "A task's final output was delivered, but a post-delivery audit shows a sub-agent sent an email to 200 contacts without ever triggering the pre-action confirmation gate. How did this happen, and how do you prevent it?" The pre-action gate only fires when a tool call routes through /internal/tool_call — if the agent's tool implementation made a direct external API call instead, the gate was never in the path to trigger at all. The root cause is architectural, not a missing check: every agent worker's tool implementations must be forced through the platform's tool execution layer, with no other route to the outside world. The fix is containment, not policy — revoke the agent worker container's direct internet egress entirely, running it in a network-isolated sandbox whose only permitted egress is the platform's own tool proxy, so that any agent code importing an HTTP client and attempting a direct external call fails at the network layer regardless of what the model believed it was permitted to do. This is the same lesson AI Coding Agent's sandbox security model establishes for arbitrary shell execution — a security boundary that depends on the model's own restraint is not a security boundary, and the only fix that survives a buggy or adversarially-prompted agent is one enforced outside the agent process entirely.

    A candidate who volunteers, unprompted, that this platform's job is to make Chapter 16's orchestrator-worker pattern (or Chapter 10's, or Chapter 17's) safe and cheap to run at scale — rather than to reinvent what any one of those chapters already does — and who can name the specific mechanism (SETNX, BFS failure propagation, the irreversibility-driven gate placement) behind each platform guarantee rather than describing it abstractly, is operating at the depth this chapter is designed to test.
