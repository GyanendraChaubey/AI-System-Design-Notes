    RAG System — System Design Case Study¶

    Every RAG-flavored chapter elsewhere in this section — Enterprise RAG Platform, Perplexity, Deep Research Agent, Glean-Style Enterprise Search — treats retrieval-augmented generation as an enabler of a product and spends its depth budget on the product's distinguishing problem: permission enforcement, live-web fan-out, multi-hour research budgets. This chapter is the one place in the book that treats RAG itself as the system: the reusable retrieval-augmented generation pipeline that could sit underneath any of those products, and the engineering decisions — chunking strategy, hybrid retrieval, query transformation, context assembly, index freshness — that determine whether it actually works. Enterprise RAG Platform is the deployment of this pipeline into an organization with access control and compliance as the dominant constraint; this chapter is the pipeline itself.

    The central claim this chapter makes, and returns to at every section: RAG quality degrades at every stage, and the stages compound multiplicatively, not additively. A retrieval system that returns the right chunk 80% of the time, feeding a context assembler that selects the right chunk for the prompt 80% of the time, feeding a generator that grounds its answer in that chunk 80% of the time, produces a correct answer only 0.8 × 0.8 × 0.8 ≈ 51% of the time — worse than a coin flip, from three components that each individually look "pretty good" in isolation. Tuning a RAG system end-to-end against one blended "quality" number hides exactly which of the three multipliers is actually broken. This chapter is organized so that every mechanism is traceable back to which stage's multiplier it improves, and the Interview Discussion closes with the diagnostic procedure for finding which stage is failing when a real system produces wrong answers.

    Requirements¶

    Functional

    • Ingest documents from heterogeneous sources (wikis, PDFs, tickets, code, transcripts), chunk and embed them at ingestion time, and index them into a hybrid store combining sparse (BM25) and dense (vector) retrieval.
    • Serve natural-language queries with sub-500ms P95 retrieval latency and return a generated, cited response with per-claim source attribution.
    • Support multi-turn conversational queries where later turns depend on earlier context (coreference, implicit scope).
    • Keep the index synchronized with source content on a bounded freshness SLO, without requiring a full corpus re-index on every change.

    Non-functional

    • Retrieval recall@5 > 75% on a domain-specific evaluation set.
    • Generation faithfulness > 90% (< 10% of claims unsupported by retrieved context).
    • Index freshness < 30 minutes from source change to queryable.
    • Retrieval throughput of at least 500 QPS with horizontal scaling headroom.

    Explicitly out of scope: fine-tuning the embedding model or generator LLM on domain data — an operationally separate concern; see LLM Inference System for the serving substrate underneath the generator and Section 12 for adjacent training-time approaches. User authentication, per-document access control, and multi-tenant isolation — this chapter's retrieval pipeline is domain-agnostic and assumes a single trust boundary; see Enterprise RAG Platform for the organizational-ACL variant of everything described here.

    Capacity Planning¶

    Sized for a production corpus, using order-of-magnitude assumptions in the spirit of GPU Sizing & Capacity Planning:

    Step Assumption Result
    Source corpus 10M documents, ~2,000 tokens average 20B source tokens
    Chunking ~300 tokens/chunk at 20% overlap (see Concept 1) ~80M chunks
    Vector storage 768-dim float32, ~3KB/vector 80M × 3KB = 240GB raw
    ANN index overhead HNSW graph adds 40–80% ~400GB total vector index
    Keyword index BM25/Elasticsearch, ~1.5–3× compressed text size ~90GB
    Query volume 500 QPS sustained at retrieval horizontally sharded across both indexes

    Two storage systems, both horizontally sharded, sized independently — this is the same "vector index and lexical index scale independently" pattern covered generically in Hybrid Search & Reranking, applied here at a concrete corpus size.

    Scale Estimation¶

    At 80M chunks, HNSW is the ANN algorithm of choice over IVF-PQ (better recall-latency tradeoff at this scale, and the corpus is large enough to need sharding but not so large it needs IVF-PQ's memory compression) — ef_search=100 gives ~97% recall@10 at ~2–5ms query latency on a 4-node cluster (60–100GB/node). Elasticsearch with 3 shards handles the BM25 side at ~10-20ms per query at this document count.

    Worked end-to-end retrieval latency at 500 QPS peak:

    • Dense ANN search: ~5ms (parallel with BM25)
    • BM25 search: ~15ms (parallel with dense)
    • RRF fusion: ~2ms (in-process, no network hop)
    • Cross-encoder reranking, 50 candidates batched on GPU: ~50ms
    • Retrieval + reranking total, P50: ~80–100ms
    • Generation (model-dependent): +500ms–2s

    Full pipeline P50 latency: 600ms–2.1s — retrieval and reranking are a small, controllable fraction of the budget; generation dominates, which is the same conclusion RAG Architecture reaches generically and this chapter confirms with concrete numbers at this corpus size.

    Detailed Design¶

    The five subsections below are the load-bearing mechanisms of this system. Each one is a direct lever on one of the three multipliers in the compounding-quality argument from the introduction — chunking and hybrid retrieval determine the recall multiplier, query transformation and context assembly determine the "right chunk actually reaches the prompt in usable form" multiplier, and the evaluation loop is how you measure each multiplier independently instead of guessing.

    Concept 1 — Chunking strategy: the precision-context tradeoff¶

    Chunking is frequently the highest-leverage decision in the entire pipeline, ahead of embedding model choice — see Chunking Strategies for the full treatment of fixed-size, semantic, and structure-aware chunking. The core tension worth restating here because every other decision in this chapter sits downstream of it: retrieval precision favors small chunks (a 100-token chunk about backpropagation matches a query about backpropagation cleanly), generation quality favors large chunks (the generator needs surrounding context to produce a coherent, complete answer). Every chunking strategy is a point on this tradeoff.

    Strategy Semantic coherence Structured content Index size Retrieval precision Generation completeness
    Fixed-size + overlap Medium Poor (splits tables/code) +10–20% (overlap) Medium Medium
    Semantic (embedding-boundary) High Poor Baseline, variable Medium-High Medium-High
    Structure-aware High (well-structured docs only) Good Baseline High High
    Hierarchical parent-child High Good (parent absorbs structure) ~2× (two representations) High High

    Hierarchical parent-child chunking is the pattern that resolves the tension directly, rather than picking a compromise point on the tradeoff curve, and is this chapter's default: index two representations of every document. Child chunks (~100–200 tokens) are the retrieval unit — small enough for precise embedding similarity, used for the similarity search. Parent chunks (~500–1,000 tokens, typically one document section) are the generation unit — enough context for the LLM to produce a grounded, complete answer. When a child chunk matches the query, the system returns its parent for context assembly.

    Concretely: a document is split into 40 child chunks of ~100 tokens each. A query about "gradient descent" matches child chunk 12 — a single sentence. The system resolves child 12's parent_id to the parent chunk covering the full "Optimization Algorithms" section (~600 tokens: gradient descent, SGD, Adam) and passes the parent to the generator. Retrieval was precise; the context is complete.

    Schema, stored in the metadata store alongside the vector index: {chunk_id, parent_id, document_id, position, content, token_count}. Retrieval flow: fetch top-K child chunks by similarity → resolve each to its parent_id → deduplicate by parent_id (two matched children sharing a parent contribute one parent, not two — otherwise the same content appears twice in the assembled context, wasting budget) → assemble context from the unique parents. This is the same deduplication discipline Chunking Strategies calls out as the most commonly skipped step in naive implementations.

    Concept 2 — Hybrid retrieval: BM25, dense vectors, and the fusion problem¶

    Dense-only retrieval fails on precise lexical matches — exact IDs, product codes, proper nouns underrepresented in the embedding model's training distribution. Sparse-only (BM25) retrieval fails on vocabulary mismatch — "cardiac arrest" and "heart attack" share no tokens. See Hybrid Search & Reranking for the full mechanism, benchmark tables, and cost analysis; this system runs the standard three-stage pipeline at production scale:

    1. BM25 retrieval (Elasticsearch) — top 50–100 candidates by keyword match.
    2. Dense ANN retrieval (HNSW) — top 50–100 candidates by cosine similarity.
    3. Reciprocal Rank Fusion — merge the two ranked lists with no score normalization required:
    \[\text{RRF}(d) = \sum_{r \in \text{rankings}} \frac{1}{k + \text{rank}_r(d)}\]

    With k=60: a document ranked 3rd in BM25 and 7th in dense retrieval scores 1/(60+3) + 1/(60+7) = 0.0159 + 0.0149 = 0.0308. A document BM25 never retrieves at all (rank = ∞) scores only its dense contribution: 0 + 1/(60+7) = 0.0149. RRF operates on ranks, not raw scores — it needs no calibration between BM25's unbounded scores and cosine similarity's [-1, 1] range, which is why it beats tuned linear interpolation (α·bm25 + (1-α)·dense) as a default: no α to overfit.

    1. Cross-encoder reranking on the top ~50 fused candidates — joint attention over query and document catches interaction signals (negation, sub-topic alignment) that independent bi-encoder similarity cannot. Latency math at ~10ms per query-document pair on GPU: reranking 50 candidates costs ~500ms sequentially, or ~50ms with batched inference — acceptable as a final pipeline stage; reranking 10,000 candidates unbatched would cost ~100 seconds, which is why the reranker is constrained to a small post-fusion candidate set rather than run as a first-stage retriever.
    2. Top-K selection — the final 5–10 candidates for context assembly.

    Reranker training data: human relevance judgments where budget allows, or LLM-generated synthetic training pairs (generate relevant/irrelevant document pairs from the corpus, train on the LLM's labels) at scale where manual annotation isn't affordable — the practical default for most production deployments.

    Concept 3 — Query transformation: fixing the query before it reaches the retriever¶

    Most naive RAG passes the user's raw query directly to retrieval. Production systems transform it first — see Advanced RAG Patterns for the full pattern catalog (rewriting, HyDE, decomposition, RAG-Fusion, step-back, Self-RAG); this section covers the three transformations this pipeline runs by default.

    Multi-turn context resolution. Turn 2 of "What is the transformer architecture?" → "How does it handle long sequences?" cannot retrieve meaningfully on "it." An LLM rewrite step, run on every turn after the first (~50–100 tokens in, ~10–20 tokens out, cheap), resolves references against conversation history before retrieval: "How does the transformer architecture handle long sequences?" Measured improvement on conversational workloads: 25–40% multi-turn retrieval recall.

    HyDE (Hypothetical Document Embeddings). The embedding distance between a question ("What are the side effects of ibuprofen?") and a clinical-vocabulary answer ("gastrointestinal bleeding, renal impairment...") is large despite semantic equivalence — question syntax and lay vocabulary sit far from declarative clinical prose in embedding space. HyDE generates a hypothetical answer with the LLM (no retrieval involved), embeds that, and searches with it instead of the original question — the hypothetical embeds near the real documents because both use answer-shaped, declarative prose. Measured improvement: 15–30% recall@5 on knowledge-intensive tasks (BEIR benchmark). Cost: one LLM call (~100–200 tokens, <$0.001) and +50–100ms latency — worth it for precision-critical queries, skippable for high-throughput keyword-style lookups where the original query already matches corpus phrasing.

    Query decomposition (multi-query fan-out). A query spanning multiple independent subtopics — "compare the training data, architecture, and RLHF approach of Model A and Model B" — needs at least six independent retrieval targets that a single query embedding will not jointly match well. Decompose into sub-queries, retrieve for each in parallel, merge and deduplicate by chunk_id. Fan-out adds only the decomposer LLM call to wall-clock latency (parallel retrieval means total latency ≈ single retrieval latency), but it multiplies the context budget requirement — the context assembler (Concept 4) must select the most relevant subset when the merged retrieved set exceeds the prompt budget. This is the same fan-out pattern Deep Research Agent runs at a much larger scale (dozens of sub-questions, iterative and agentic) — the mechanism is identical; the difference is whether it's a fixed single pass (this chapter) or a bounded iterative loop with a sufficiency check (that chapter — see the Agent Layer below for where that line is).

    Concept 4 — Context assembly and citation grounding¶

    Retrieved chunks must be assembled into a prompt that gives the generator what it needs and lets every claim be traced back to its source.

    The "lost in the middle" problem. LLM performance degrades for facts positioned mid-context — models attend most reliably to the start and end of a long context (see Context Rot & Failure Modes for the general mechanism). Liu et al. (2023) measured QA accuracy dropping from ~75% (fact at position 1 of 20) to ~55% (position 10) back to ~75% (position 20). Mitigation: place the highest-relevance chunk first, then remaining chunks in reverse relevance order, so the second-highest-relevance chunk lands last — the two strongest chunks bracket the weaker ones at both ends of the window, where attention is strongest. For conversational interfaces, placing the single highest-relevance chunk immediately before the query (recency bias) is a simpler variant.

    Citation tracking. Number every retrieved chunk in the prompt and instruct the generator to cite chunk numbers per claim:

    Context:
[1] {chunk_1_content}
[2] {chunk_2_content}
[3] {chunk_3_content}

Query: {user_query}

Answer using only the provided context. Cite source chunk number(s) after
each factual claim using [N] notation. If the context is insufficient, say so.

    Citation verification, two levels, run after generation and before the response is returned: a structural check — does every cited [N] correspond to a chunk that actually exists in the context set (a hallucinated [7] against 3 available chunks is caught instantly, no model call needed); and an entailment check — for each cited sentence, an NLI model (e.g., DeBERTa-NLI, ~400M params, ~20ms on GPU) verifies the sentence is actually entailed by the cited chunk's text. Run entailment on every claim for high-stakes domains; run it only on numerical claims, proper nouns, and dates for cost-sensitive serving — these are the claim types most prone to fabrication. This is the structural fix for the citation-hallucination failure mode cataloged in RAG Failure Modes.

    Context budget management. Hybrid retrieval plus fan-out can easily exceed the desired context budget (using the full context window on every request makes cost unpredictable, independent of whether the model technically fits it). Greedy relevance ordering — take chunks in reranker-score order until budget is consumed — is the simplest selection method. Maximal Marginal Relevance (MMR) is the better default: MMR(d) = λ · sim(d, query) − (1−λ) · max_{s ∈ selected} sim(d, s), with λ≈0.7 a common starting point. MMR balances relevance against redundancy, preventing a context window filled with five chunks that all restate the same fact from slightly different angles.

    Concept 5 — Index freshness, evaluation, and the feedback loop¶

    Incremental indexing. A naive nightly full re-index introduces up to 24 hours of staleness and reprocesses the 99% of documents that didn't change. The production pattern — content-hash-gated, event-driven, atomic-swap incremental indexing — is covered at full depth in Knowledge Base Lifecycle Management; this pipeline uses it directly: a change event triggers a hash comparison against the stored hash, and re-chunking/re-embedding only fires on a mismatch. Deletions are soft (tombstoned, filtered at query time) with weekly compaction, because HNSW does not support efficient in-place deletion — see the same chapter for why.

    The evaluation triad — not just recall@K. Retrieval recall alone is necessary but insufficient; see RAG Evaluation Metrics for the full metric catalog and the RAGAS framework. Three metrics, tracked independently because each isolates a different pipeline stage:

    Metric What it measures How to compute
    Context precision Are retrieved chunks actually relevant to the query? LLM judge or annotator rates chunk-query relevance
    Generation faithfulness Does the answer contain only claims supported by context? NLI entailment check per claim
    Answer completeness Does the answer fully address the query given available context? LLM judge vs. reference answer

    Run this as a regression suite on a golden set of 100–500 (query, reference answer, reference chunks) triples, on every change to embedding model, chunking parameters, reranker, context assembly logic, or system prompt. A change that improves one metric while degrading another is not an improvement — it's a tradeoff that needs a decision, not an automatic ship.

    Feedback loop. A user downvote or correction triggers a lookup into the retrieval trace log: original query, transformed query, BM25 and dense candidate lists separately, RRF fusion order, reranker output, assembled context, and generated response. This trace is the raw material for the diagnostic procedure in Interview Discussion below, and for building a labeled failure dataset — 50–100 traced failures per week, labeled by failing stage, is the most actionable input for prioritizing fixes. See RAG Failure Modes for the full failure taxonomy this trace data gets classified into.

    Retrieval Layer¶

    This is the core of the chapter, covered in full at Concepts 1–2 above. Tied back to the scale estimates: at 80M chunks, HNSW at ef_search=100 gives ~95–97% recall@10 at ~2–5ms query latency per the tuning curve in Indexing Algorithms — a 4-node cluster comfortably holds this index with headroom. Elasticsearch with 3 shards handles the BM25 side. The metadata store (PostgreSQL) holds chunk metadata, the parent-child mapping from Concept 1, content hashes for incremental indexing, and deletion flags — small enough (a few hundred bytes per chunk) to fit on a single primary with read replicas even at 80M chunks.

    Agent Layer¶

    This pipeline is deliberately not agentic — it is a fixed multi-stage pipeline (transform → retrieve → fuse → rerank → assemble → generate → verify), not a control loop that decides when it has enough evidence. Query decomposition (Concept 3) fans out to parallel sub-queries but runs exactly once, with no sufficiency check and no re-retrieval. The moment a system starts critiquing its own retrieved evidence and deciding whether to re-retrieve — Self-RAG, Corrective RAG — it has crossed into agentic RAG, covered in Agentic RAG Architecture and its iterative-retrieval companion chapter. Deep Research Agent is what this same retrieval substrate looks like once wrapped in that control loop: dozens of sub-questions, a sufficiency check, and bounded replanning, rather than one fixed pass. Enterprise RAG Platform sits in between — it layers a bounded decompose-and-synthesize loop on top of this exact retrieval stack specifically for multi-hop, multi-source enterprise queries.

    Model Layer¶

    Four models, each independently upgradeable and versioned separately:

    1. Embedding model — text-embedding-3-large (managed) or bge-large-en-v1.5 (self-hosted, MTEB-competitive). Self-hosting is cost-effective past ~1M documents; see Embedding Models for the full selection framework and re-embedding cost formula.
    2. Query rewriter — a lightweight, fast model (Haiku-class), ~50 tokens in/out, <50ms latency, since it runs on every conversational turn.
    3. Cross-encoder reranker — ms-marco-MiniLM-L-6-v2 (fast, self-hosted default) or a domain-fine-tuned BERT-base for precision-critical corpora.
    4. Generator — the calling application's LLM, served by LLM Inference System. This chapter builds the retrieval substrate that feeds the generator's context window; it has no opinion on which model the application chooses to generate with.

    Observability Layer¶

    • Retrieval latency, per stage (BM25, dense, RRF, rerank) at P50/P95 — tracked separately so a regression is attributable to one stage, not a blended "retrieval" bucket.
    • Reranker hit rate — the fraction of queries where the reranker's top-1 differs from RRF's top-1. Near-zero suggests the reranker isn't adding signal for this domain; a healthy rate confirms it's earning its latency cost.
    • Citation structural validity rate — fraction of responses where every cited chunk number exists in context; a drop signals a prompting or context-numbering bug.
    • NLI entailment pass rate, sampled — the faithfulness proxy; alarm below 85%.
    • Ingestion lag — time from source change event to chunk indexed and queryable; alert if P95 exceeds the 30-minute SLO.
    • Content hash cache hit rate — fraction of change events where content was actually unchanged; confirms the incremental-indexing gate is filtering wasted work rather than re-embedding everything.
    • Evaluation suite trend — context precision, faithfulness, and completeness (Concept 5) plotted over time, not just checked at ship time.

    Security Layer¶

    • Prompt injection via retrieved content. A malicious or compromised document in the corpus can contain "ignore previous instructions and..." text that the retrieval pipeline dutifully surfaces into the generator's context. Mitigate with instruction hierarchy (system prompt placed to dominate over retrieved content, never the reverse) and ingestion-time content sanitization that flags documents matching injection patterns — the same discipline RAG Architecture requires generically.
    • Data exfiltration via cross-tenant retrieval. In any deployment with more than one trust boundary, a crafted query must not retrieve another tenant's content. Enforce a tenant_id filter at the vector index and keyword index level directly — never as an application-layer afterthought — exactly as Enterprise RAG Platform argues for its ACL filters: the check belongs inside the retrieval query itself, not applied to results after the fact.
    • Embedding model poisoning. A self-hosted, fine-tuned embedding model can be adversarially trained so crafted documents land unnaturally close to many unrelated queries in embedding space. Mitigate with embedding anomaly detection — flag documents or queries with unusually high similarity to a disproportionate number of others.
    • PII in the source corpus. PII scrubbing and access controls belong at ingestion, before indexing — a document indexed without redaction is queryable by everyone until the control is applied retroactively, which is too late for anything already served.

    Cost Model¶

    flowchart LR
    ING["Ingestion: chunk + embed"] --> STORE["Vector + Lexical\nIndex Storage"]
    STORE --> RET["Query-Time Retrieval"]
    RET --> RR["Reranking"]
    RR --> GEN["LLM Generation"]
    GEN --> RESP["Response"]
    Cost component Driver Lever
    Embedding (ingestion) 80M chunks × ~300 tokens Self-host past ~1M docs (see Embedding Models); incremental re-embed only on hash change
    Vector + keyword storage ~400GB + ~90GB at this scale int8 quantization halves vector storage at <1% recall loss
    Retrieval + fusion QPS × candidate set size RRF is stateless, near-zero marginal cost; index sharding keeps per-query work bounded
    Reranking Candidates × cross-encoder cost Self-hosted MiniLM vs. managed rerank API is typically a 100x+ cost difference at volume — see Hybrid Search & Reranking
    HyDE / decomposition (Concept 3) One extra LLM call per triggered query Gate behind a confidence/ambiguity classifier rather than running on every query
    Generation Input tokens (retrieved context) dominate Context budget management (Concept 4) trims to the eval-verified minimum chunk count, not "8 just in case"

    The single highest-leverage lever, echoing RAG Architecture's general conclusion: generation input tokens are the largest recurring line item once the corpus is indexed, which is why context budget management (Concept 4) is a cost control, not just a quality one.

    Failure Handling¶

    Failure Degradation strategy
    Vector index unavailable Fall back to BM25-only retrieval rather than failing the request — degraded recall beats no answer
    Keyword index unavailable Fall back to dense-only retrieval
    Reranker timeout or unavailable Skip reranking, serve RRF-fused order directly — a quality regression, not a correctness failure
    Query transformer (rewrite/HyDE/decompose) fails Fall back to the raw, untransformed query rather than blocking the request
    Citation verifier flags widespread failures on one response Regenerate once with stricter grounding instructions; if still failing, return a hedged response rather than an unverified one
    Ingestion pipeline falls behind SLO Serve with a visible "as of" freshness indicator; alert on ingestion lag as a first-class incident, not a background job
    Embedding service outage (ingestion side) Queue and retry; do not block query-time serving on ingestion health

    Tradeoff Analysis¶

    flowchart TD
    Q1{"Chunk size?"} -->|"Smaller"| PREC["Better retrieval precision\nWorse generation completeness"]
    Q1 -->|"Larger"| CTX["Better generation completeness\nWorse retrieval precision"]
    Q1 -->|"Hierarchical"| BOTH["Both, at ~2x index storage"]
    Q2{"Reranker candidate depth?"} -->|"More candidates"| RECALL["Higher recall\n5x+ inference cost"]
    Q2 -->|"Fewer candidates"| CHEAP["Lower cost\nRisk of missing the right chunk"]
    1. Chunk size. Smaller chunks improve retrieval precision and worsen generation context completeness; larger chunks invert that. Hierarchical parent-child chunking (Concept 1) resolves this at the cost of roughly 2× index storage — a cost most production systems accept once they've measured the alternative's quality ceiling.
    2. Reranker candidate depth. Reranking 100 candidates instead of 20 improves recall but costs proportionally more cross-encoder inference. Default to 50; increase only where a domain eval shows the extra depth recovers meaningfully more correct answers.
    3. HyDE on/off. +15–30% retrieval recall, +50–100ms latency, +~$0.001/query. Enable for knowledge-intensive queries where corpus vocabulary diverges from question phrasing; disable for queries that are already precise keyword lookups, where HyDE adds cost with no recall benefit.
    4. RRF constant k. k=60 is the empirically robust default across corpora. For highly technical corpora with precise terminology where BM25 should dominate, lowering k for the BM25 ranking specifically increases its influence relative to dense — a tunable but rarely necessary knob.
    5. Online vs. offline evaluation. Automated NLI-based faithfulness checking is cheap and continuous but misses nuance a human catches; human annotation is accurate but expensive and necessarily sampled. Run NLI continuously and human annotation on a stratified monthly sample (by query type, citation count, response length) — neither alone is sufficient, matching the same conclusion RAG Evaluation Metrics reaches generically.

    Interview Discussion¶

    An interviewer asking "design a RAG system" is usually testing whether a candidate understands the failure modes at each pipeline stage, not whether they can recite the happy-path architecture. A candidate who describes chunking, hybrid retrieval, and reranking correctly but cannot answer "my RAG system gives wrong answers 30% of the time — what's going wrong and how do you find out?" has memorized the architecture without internalizing its dynamics — the gap this case study is specifically designed to surface. RAG Failure Modes catalogs each failure in full depth; the sequence below is the fast diagnostic path that should be the centerpiece of any answer to that question.

    Diagnostic framework: trace a wrong answer backward through the pipeline.

    1. Is the source document in the corpus at all? → No: coverage/ingestion failure, not a retrieval bug.
    2. Was the relevant chunk in the top-50 from BM25 or dense retrieval? → No: retrieval failure — check the embedding model's domain fit, the BM25 query, or a chunking boundary that split the answer.
    3. Was it in the top-10 after reranking? → No: reranking failure — the reranker isn't calibrated to this domain; check its training data.
    4. Was it in the assembled context sent to the generator? → No: context assembly failure — check MMR selection, context budget size, or lost-in-the-middle ordering.
    5. Does the generated response accurately reflect the context it was given? → No: generation faithfulness failure — check prompting, citation grounding instructions, or whether the model is defaulting to parametric memory.

    This is a strict backward trace: each step's "no" isolates the fix to exactly one stage, and each step's "yes" moves the investigation one stage downstream — never both at once.

    Staff-level probe: "Your context precision is 88% but your answer completeness is only 52%. What does that tell you, and what do you do?" High context precision means the retrieved chunks are relevant; low completeness means queries still aren't fully answered. That combination is a coverage or decomposition problem, not a retrieval-quality problem — the retrieved content is right but insufficient. Check whether the corpus actually contains the full answer (a coverage gap, not a retrieval bug), whether query decomposition (Concept 3) is enabled for genuinely multi-part questions that a single retrieval pass can't jointly satisfy, and whether the context budget is cutting off answering content before it reaches the generator.

    Staff-level probe: "High retrieval recall, low generation faithfulness — what's happening?" The retrieved content is relevant (recall is fine); the model is fabricating beyond it (faithfulness is not). Three causes, in the order to check them: the system prompt is too permissive, letting the model fill gaps with parametric knowledge instead of declining; context assembly is burying the relevant chunk mid-window (lost-in-the-middle, Concept 4); or the model itself is prone to hallucination under these prompt conditions regardless of context quality. Fix in that order — tighten grounding instructions and re-measure before reordering context, and reorder context before concluding the model itself needs to change.
